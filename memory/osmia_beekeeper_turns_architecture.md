description: How the Beekeeper's shadow-project turns must be dispatched and recovered to match the chief-of-staff's real path in osmia

In kpenfound/osmia, a registered project's chief-of-staff turn never runs synchronously inline: an owner message only calls `repository.EnqueueTurn` and returns (internal/service/conversation.go `send`). The turn actually runs later, when the registered project's persistent `reconcile.Controller` (built in `internal/service/service.go` `openReconciliation`/`stages`, run via `s.launch`) calls its `Schedule` hook — `scheduler.New(...).Pass`, which publishes a durable `thread.TurnOperation` — and then, in the same or a later `reconcile.Controller.Pass`, applies that operation through the `runnerAdapter`'s `RunnerBoundary` fallback, which is ultimately a `thread.Dispatcher` bound to `options.Threads`.

The Beekeeper's shadow project (`config.ShadowProjectID`) deliberately has no persistent background reconciliation loop (`Service.shadow` is outside `s.projects`/`s.pool`, see `internal/service/beekeeper/beekeeper.go` and `TestShadowProjectRunsNoWorkflow`). But the sealed spec for the "mason-bk-turns" unit still requires Beekeeper turns to run through the *same* reconcile-controller/scheduler/runner-adapter machinery chief-of-staff turns use, not through an ad hoc inline `thread.Dispatcher.Apply` call (that inline-Apply pattern is reserved for shed/debate/committee *sub-turns*, e.g. `internal/service/shed.go`'s `(d *debate) dispatch`, and a reviewer flagged reusing it for the Beekeeper's top-level turn as the wrong pattern).

**Resolution that satisfied review:** `internal/service/beekeeper/turns.go`'s `Continue` function builds a fresh `scheduler.New(repository, scheduler.Options{Now: now})` (Capacity/Admit/Priorities/Shared all nil — unbounded, since the shadow project shares no capacity pool) and a fresh `reconcile.New(repository, reconcile.Options{Worker: "beekeeper", Now: now, Adapters: {RunnerBoundary: thread.Dispatcher{...}}, Schedule: scheduler.Pass})`, then calls `controller.Pass(ctx)` **once, synchronously** rather than running `controller.Run(ctx)` in a background goroutine. Because `reconcile.Controller.Pass` runs its `Schedule` hook and then reconciles whatever became due in the *same* call (when no `Concurrent` filter is set), one `Pass` call both publishes and fully executes the one ready turn, so `Post`/`Continue` stay synchronous while genuinely going through the reconcile/scheduler code paths. `Post` now just calls `Continue` instead of hand-building a `thread.Dispatcher`+`TurnOperation` and calling `.Apply` directly.

**Continuation parity on recovery:** `recoverSessions` only ever gave registered-project chief-of-staff threads a crash-recovery continuation turn (gated on `th.Identity.Role == trace.ChiefOfStaff && s.options.Threads != nil`) — Beekeeper threads have `Identity.Role == beekeeper.AgentID` ("beekeeper", not "chief_of_staff"), so they never got one, leaving an interrupted Beekeeper turn stuck forever (busy, no auto-continuation) unlike the chief's. Fixed by adding a parallel `th.Identity.Role == beekeeper.AgentID && s.options.BeekeeperTurns != nil` branch that enqueues the same kind of continuation request (shared `recoverContinuation` helper, parameterized by profile) but resolves the Beekeeper's own profile (`cfg.NamedProfile(cfg.Beekeeper.Profile)`, not the registered project's chief-of-staff role profile) and — because there's no background loop to pick the continuation up later — runs it immediately via `beekeeper.Continue` right there in `recoverSessions`, before `Start()` returns.

**Test-fixture trap:** a test proving "the Beekeeper ignores a registered project's closed capacity" must not express "closed" as `capacity.masons = 0` etc. — osmia's config validation requires every capacity field to be positive (`internal/config/config.go`, "must be positive"), so that fixture fails validation at `start()` and the test never reaches its assertions. Use a runtime hard pause instead: `mutation(t, c, "PUT", "pause", PauseRequest{Target: runtime.Target{Scope: "project", Project: project}, Mode: "hard", ...})` after `start(t, opts)` — this is valid config and actually closes the whole project.
