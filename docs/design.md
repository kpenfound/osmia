# Osmia design doc

A personal software factory for long-running feature work on repositories you own or contribute to. It is configured at the user level, keeps its factory state outside the repository it works on, is driven by a person through one aide, and shares one pool of agent capacity across several workstreams on several projects.

Status: design v0.3, 2026-10-15. This document is the source of truth for feature proposals and implementation; an issue does not override the design. Osmia uses `github.com/kpenfound/agentcore` as a Go dependency and defines an optional Hearsay memory integration. Section 17 defines those boundaries and section 18 summarizes the feature guarantees.

---

## 1. Purpose

You want to land a large feature in a project like dagger. You are a contributor, so you cannot install a factory in the repository, label its issues, or push to its main branch. You have a design in your head or in a document, you want agents to plan it, argue about the plan, build it in pieces, review each piece, and hand you one feature branch on your repository or fork with a pull request you are happy to put your name on. You want to be asked when something needs your judgement, and otherwise left alone. You want the same machine working on three dagger features and a feature for another project at the same time, from one process, from your phone.

Osmia is that machine. It does not decide what to build. You hand it a feature. It does not run on the repository's issue tracker. It runs on a directory under your home. It does not push to anyone's main. It delivers a branch and a pull request, and stops. One exception exists, and only for a project you have opted in with `delivery = "jev"` that delivers through its own upstream: a clean workstream may land, which is a fast-forward of that project's base branch to the signed, checked commit, never a merge commit and never GitHub's merge API (section 5.5). Every other project, every fork and contributor project included, keeps the rule exactly as written.

### 1.1 Why a mason bee

Mason bees, the genus *Osmia*, have no hive. Each one moves into whatever cavity already exists, a reed, a hole in a wall, a tube someone left out, and gets to work. Orchards buy them by the tube and set them out where the pollination is needed, and a handful of them do the work of a hive. They are gentle and rarely sting.

That is the tool. It moves into an existing repository without changing it, is deployed where the work is, and is meant to be a good guest.

### 1.2 The shape of the design

Five choices give the design its shape.

1. The owner ratifies a feature's intent: required outcomes, acceptance criteria, exclusions, constraints and reserved tradeoffs. The factory proposes an execution plan alongside it; engineering choices in that plan remain revisable.
2. Units own coherent outcomes, with explicit boundaries and dependencies. Masons adapt implementation within their assignments. Reviewers judge outcomes using applicable evidence. The factory revises assignments and incorporates necessary discoveries without changing approved intent.
3. Every agent talks upward to the manager, which investigates and resolves engineering blockers, coordinates revisions, and raises intent decisions or concrete operational limitations it cannot resolve. The owner approves publication, except that on a project opted in with `delivery = "jev"` a confident Jev pick between landing and the pull request can stand in for that approval (section 9.6).
4. The transitions are Go. Models investigate, propose and judge inside turns. The service owns scheduling, capacity, credentials, version control, durable revisions and recovery.
5. Jev, TypeSafe's System One model, is the factory's decision maker. When a ratification, an intent amendment, an escalated question, an escalated contested unit or an escalated objection reaches the point where it would wait in your inbox, the service first asks Jev with what the card shows, and a pick at or above the decision threshold is recorded as your decision and carried out. Your own decisions are put to Jev the same way, held to a separate owner threshold: delivery approval, charter proposals and conflicts between charters, "no change needed" escalations, cancellation and your own objections. On a project opted in with `delivery = "jev"`, a confident `delivery-route` pick between landing and the pull request, held to the decision threshold, replaces the owner's delivery approval; nowhere else is there a landing. The manager asks Jev for its own bounded decisions the same way, through `decide`. Jev never reads code, never writes text, never replaces a reviewer's, the committee's or a final review's verdict, and picks an option that needs words only when the manager already wrote them. Below the threshold, or when Jev falls back, the decision is yours or the manager's exactly as it is without Jev (section 9.6).

| repo | The project's target repository, with its upstream, optional fork and clone. |
| workgroup | One feature request across an owner-selected set of projects, with one member workstream per project and exactly one shared manager. |
| brief | The distilled handoff from a design conversation, or the handed document on the fast path. Decisions, intent, tradeoffs and rejected options; it takes precedence over the attached transcript. |
| workgroup spec | The committee-debated, owner-ratified workgroup design: behaviour, cross-repo contracts and numbered criteria. |
| workstream slice | The part of the workgroup spec assigned to one repo's workstream. Contract sections are read-only to its roles. |

Acceptance never requires a whole-suite check pass or run; the service-owned check gate selects and runs checks and catches regressions. ### 2.2 Roles

Roles take names from the trade. All but the owner are agents.

| Role | Job |
|---|---|
| owner | You. Hands in features, sits in the shed, ratifies specs, answers questions, edits the charter, takes delivery. Talks only to the manager. |
| manager | The one role facing the owner. It works on one workgroup with a defined job, not as an open-ended assistant. Answers every member role's questions from the brief, workgroup spec, slices, entity map and repo state, with optional Hearsay context; rules on contested units on your behalf and escalates design changes or concrete operational limitations it cannot resolve, rephrases both ways, presents ratification, keeps the status that names the pull request's title. Works outside the state machine's loop to keep work moving: its moves, rulings, revisions and recovery tools are its own decisions (section 6.6). Never implements or reviews, and opens no work of its own, except that on a project with `flake_fixes` on it may open a flake-fix workstream for a recorded flake occurrence through the `flake_fix` tool (section 6.9). Holds the `Web` permission (§9.5). |
| architect | Drafts the workgroup spec, graph, slices and plans for every owner-selected project, answers the committee in the shed and drafts amendment deltas. Holds the `Web` permission on every turn path, a workgroup's project-spec draft and delta turns included (§9.5). |
| committee | Adversarial reviewers. In the shed they argue against the spec and plan, citing the spec, the charter and the recorded decisions. On a unit one of them is the reviewer, verifying the unit's work against its task and acceptance until the unit lands. At the end one reads the whole branch, at a high level, against the spec's intent and the charter. One role, three prompts. Holds the `Web` permission in plan and amendment debate rounds only; a unit review and a final review hold none (§9.5). |
| mason | Does one unit's task until its acceptance holds. May ask questions. |
| foreman | Runs the landing. Merges approved units onto the feature branch, rebases units still in flight, keeps the branch current with upstream, resolves conflicts against the sealed spec, flags entanglement, signs and pushes the branch and opens the pull request as a draft at assembly, then pushes every later commit to it. Mostly code, with a session only for conflict resolution. |

## 3. Principles

1. **No factory state is committed to the target repository.** No configuration, no specification, no workflow labels, no comments by bots. The repository sees the feature's code and tests on a feature branch in your repository or fork and a pull request under your name. This rule concerns repositories Osmia works on; Osmia's own source repository carries its design and development configuration.
2. **Work is handed, not mined.** The factory builds what you give it. It has no backlog of its own and idles when you give it nothing. One narrow exception exists: on a project whose `flake_fixes` setting you turned on, the manager may open a flake-fix workstream through its dedicated `flake_fix` tool, from a flake the service recorded in a check run (section 6.9). It exists because a flake that passed its rerun is the one piece of work the factory itself uncovers, and it would otherwise be forgotten once the run counted it as a pass. The exception adds no backlog and no discovery: the service records only flakes of check runs of work you handed in, the manager opens only a recorded occurrence, from a hand-in the service writes, and the workstream is an ordinary hand-in that you still ratify and whose delivery you approve. With the setting off, which is the default, the principle holds without exception.
3. **The owner talks to one role.** Every question, status, ratification and ruling passes through the manager. No other agent addresses you and you address no other agent.
4. **The outer machine is Go.** States, transitions, readiness, entanglement checks, landing order, capacity and pause are code. What happens inside a turn is a model. Nothing on the scheduling path waits on a model.
5. **Agents never touch version control.** Sessions get a directory of files. The service creates workspaces, snapshots, rebases, merges and pushes.
6. **Agents are durable threads.** A role on a workstream is one persistent conversation that receives turns and keeps its context, not a fresh session each time.
7. **The trace is the record.** Trace databases under the Osmia root hold everything that happened and supply context on their own; every document is a revision in its trace's database, not a file on disk. When enabled, Hearsay distils them into decisions and serves them back as additional memory. It is never required to make progress.
8. **One session, shared capacity.** One process runs every workstream on every project against one pool of slots. Focus is an ordering, pause is a switch, and neither restarts anything.
9. **Gates are transitions, not messages, and Jev decides the ones it is confident about.** Agents message each other freely through fixed routes. The owner gates intent ratification, intent amendments and delivery. The factory owns engineering revisions. Contested units are gated too: the manager rules on them for the owner and raises the ones it cannot resolve. A gate that would land in the owner's inbox is first put to Jev, the factory's decision maker: a confident pick is recorded as the gate's ordinary decision, with Jev as its actor, and the flow continues as if the owner had chosen it; anything else reaches the owner as a card. The owner's own decisions (delivery approval, charter proposals and conflicts between charters, "no change needed" escalations, cancellation and the owner's own objections) go the same way, at their own owner threshold. Jev never writes text: an option that needs words is offered only when the manager already wrote them (section 9.6). On a project opted in with `delivery = "jev"`, Jev may also decide the route of a clean delivery, landing on the base branch or marking the draft pull request ready, through its own `delivery-route` decision at the decision threshold, and the owner may land with "Approve and land". On every other project there is no landing, and Jev's answer on a state change never crosses the delivery gate.
10. **Clients run sessions; the service owns everything else.** A model session may run on any machine on the tailnet that connected to the service. That machine holds the session's files and its saved session, and nothing else: every trace record, schedule, git write, capture, delivery, check run, tool handler, audit entry and span stays with the service, and no secret leaves it.

## 4. Documents

Each project owns one repo, its charter, entity map and repository settings. A workgroup holds its brief, workgroup spec and graph; each member has its slice, spec and plan. All factory documents live under the Osmia root, outside target repositories, as revisions in the trace databases. None is a file on disk. Codebase context comes from reading the repos and their entity maps, not from keeping delivered specs as standing project knowledge.

Each project's dedicated trace holds its authoritative charter, entity map and decisions. Each workstream has an independent trace. A cross-repo workgroup has a dedicated trace outside every member trace for its membership, workgroup spec, shared conversation and group decisions. Direct one-repo workgroups keep their manager thread in the workstream's trace. When a design brief excludes its session project, the workgroup trace adopts the original conversation even if only one member is allocated. Nothing is authoritative in two places.

### 4.1 Charter

Your guidance as a contributor to this project, written as Markdown the way you would write an AGENTS.md: the scope you will and will not touch, dependency policy, how a change must be tested, what a pull request to this project must look like. The repository's own contributor documents are always binding, so the committee can veto against the project's contributing guide without you restating it; the charter only adds to them. It is optional: a new project's charter is the template, an HTML comment, and an empty charter never stops a project from taking work. Every agent's briefing carries the charter's Markdown without its HTML comments. A numbered list item is a rule the committee can cite.

You edit it with `osmia edit charter <project-id>` or in the web UI; each edit is a new revision. The manager proposes an amendment when a ruling you gave is really a standing rule, and you ratify or decline. Each entry records the ruling that caused it. A charter change becomes a notice in every in-flight bundle on the project.

Each member's charter governs its slice, plan and units. The architect, committee and manager receive every member's charter for the workgroup spec and contracts, which must satisfy all of them. An unqualified `charter#n` cites the member's own rule; `<project>/charter#n` cites another project's rule. Validation refuses unknown projects or rule numbers. A conflict between member charters goes to the owner and cannot be dismissed by the manager. A proposed charter amendment is recorded and decided in the project whose rule it amends.

Keep factory settings out of it. Budgets, capacity and models are configuration. If they leak into the charter, agents start debating whether "two masons" is a principle.

### 4.2 Project knowledge

What a new contributor learns about where things are and what was decided. It has two parts, and no agent writes either of them.

- **The entity map.** The map from how people talk about the code to where it is: entities with stable local identifiers, aliases, path patterns, owners and part-of edges, computed from CODEOWNERS and the repository's directory structure, plus one root entity, `repo`, whose path is `**` and which covers the whole repository (`repo-root` when a directory already takes `repo`). Its local record is the `kb/entities.json` document in the project's trace database; when Hearsay is enabled, these seeds are mapped into its code entity namespace. Footprints name these entities, or name raw path globs, and remain resolvable without Hearsay.
- **Decisions.** Constraints and choices about each subsystem, recorded as rulings and decisions in the trace with provenance. When Hearsay is enabled, it also represents them as stances. Local bundles include the relevant decisions without requiring an external service.

The service computes the entity map by itself, as a pure function of a commit's tree: the directory listing plus the CODEOWNERS blob, in GitHub's precedence order (`.github/CODEOWNERS`, `CODEOWNERS`, `docs/CODEOWNERS`), read from git objects without a checkout. Registration records the first revision from the clone's tracked files. After that one re-seeder per project runtime regenerates the map from the project's upstream default-branch head at three kinds of moment: when an architect draft of a workstream starts, before the owner's plan edit, a ratification or an amendment draft is validated against the map, and just before a sealing, whether first seal or amendment re-seal, resolves the plan's footprints. The triggering path fetches the upstream ref first and hands the fetched head over, never the workstream's own base, so a directory that landed upstream after drafting is accepted by the edit, the ratification and the amendment draft, and resolves at sealing. A footprint the refreshed map still does not resolve is refused. The re-seeder seeds a commit once however many workstreams trigger it, never seeds a commit older than the last one it seeded, merges nothing with the previous map (an entity whose directory is gone leaves it), and records a new revision only when the encoded map differs from the latest one. A failed fetch or seed never blocks drafting or sealing: it is logged once per distinct reason and the path goes on with the latest recorded map. Sealed workstreams keep the footprints they were sealed with.

The repository's `CLAUDE.md`, `AGENTS.md` and `CONTRIBUTING.md` carry what a contributor must know beyond that; the factory does not copy them. Every role can retrieve the entity map and decisions: the architect plans against the real structure, the committee cites decisions, and the mason uses its footprint to select context.

### 4.3 Workgroup spec and workstream slices

The shared design is called the **workgroup spec**. This displayed name leaves stored document paths and API fields unchanged, including `project-specs.json`, `project_spec` and `project_spec_revision`. The CLI flag remains `--project-spec-revision`.

The manager follows the same rule. Its stored identity is `chief_of_staff`: traces keep writing and reading that agent ID, role and thread ID, the thread directories on disk keep that name, and values derived from it, such as the `decided_by` of the manager's own decisions, an archive actor and the `ended` of a dependency drop, stay as written. Its saved decision documents keep their short `chief` keys: the shed rulings at `shed/<round>/chief.json` with a record ID derived from `chief`, and the contest decisions at `units/<unit>/chief-<event ID>.json` with event IDs derived from `chief`, with the manager's notices drawing their event IDs from the same key. The router's recorded triggers `contest.chief_ruling` and `objection.chief_decision` are stored names too. Saved traces hold all of these and the readers find decisions by them, so new manager decisions are written under the same names and nothing is migrated or translated on read. They are stored names, not display names: everything an owner, agent or API client sees, including role and decider values in API responses and CLI output, says `manager`.

What must be true when the feature is done: the intended behaviour, what it must not do, and acceptance criteria as a numbered list. The architect drafts the workgroup spec from the brief, using the repos and their entity maps. It includes intended behaviour, cross-repo contracts and numbered acceptance criteria, alongside an acyclic workstream graph and a slice and plan for every selected project. The committee debates these together; one owner ratification covers the workgroup spec, graph and every slice. A one-workstream packet retains the same ratification steps. Before ratification you edit the spec and plan freely with `osmia edit spec|plan <workstream-id>` or in the web UI; each edit is a new revision and the next debate round argues it. After ratification it changes only by amendment.

This spec describes the request's intended outcome. The repository does not carry it and nobody upstream maintains it as ongoing codebase documentation. It is the statement of intent that everything downstream is argued against: the plan turns it into units with acceptance a reviewer can check, the mason builds its unit against it, and the final read judges whether the assembled feature delivers it. The flow is spec, then plan, then implementation, and the owner approves intent and an initial working plan before a mason starts. What is not enforced is coverage as arithmetic. Each unit's reviewer verifies the criteria it serves in detail; the final read judges the feature as a whole, and you decide at delivery.

Before approval, the service refreshes a cross-repo workgroup spec's slice text from the members' latest recorded specs and plans, appending a revision without an agent turn. The shared behavior, contracts, graph and slice contract criteria remain unchanged. The packet identifies its workgroup spec revision; ratification carries that revision back and refuses if it has changed or the slices are still catching up with member revisions. Refresh and approval are serialized, and an existing group approval stops refreshes. In the CLI, `osmia packet <workstream>` displays the workgroup spec and the revisions to approve. Cross-repo ratification requires those owner-read pins as `--project-spec-revision N --spec-revision N --plan-revision N`; it never substitutes a fresh packet for them. Without those flags it reports the current pins, asks the owner to read the packet again and records nothing. Single-workstream `osmia ratify <workstream>` uses its packet as usual.

Before approval, a change to the text of a numbered contract criterion, including its removal, holds that member's slice instead of refreshing it mechanically. Ratification names the workgroup, member and criterion, says the contracts are being redrafted and asks the owner to read the packet again. The existing architect workgroup spec turn appends a redraft, choosing contract numbers against a durable snapshot of member specs and plans. A resumed turn reads the same revisions; changes during the turn are refreshed or guarded on the next pass. A failed contract redraft retains the guard, its member revisions and its failure message, and is asked for again on a later service pass with the refusal's problems, up to three redrafts in a row since the last recorded draft or requested one. After that the service asks for no further redraft on its own and tells the manager through the workgroup leader's events. A move of any member to sketched, by the manager or the owner, then asks the architect for another redraft with the note and starts a new run of three. No refresh or redraft starts or records once a group approval exists.

The first workgroup spec is drafted once every member is sketched, and no member's committee review starts before it is recorded. The architect's view names each member charter's rule numbers, or says it has none to cite, and its delivery verdict names every problem the service would refuse, unresolvable charter citations included. A refused first draft is asked for again with the refusal's problems, up to three drafts in a row. After that the service asks for no further draft on its own and tells the manager through the workgroup leader's events. A move of any sketched member to sketched, by the manager or the owner, asks the architect for another draft with the note and starts a new run of three. A move of such a member to in-shed is refused with where drafting stands. When a draft or redraft is recorded after the manager was told its drafts were refused, the manager is told, once, through the same events that the workgroup spec is recorded.

A slice's contract sections are read-only to its workstream roles. A contract change from a question, revision or drift amendment becomes a workgroup amendment; it is never applied locally to one slice. Units cite the slice criteria they implement.

Retention has two levels. When a workstream resolves (merged or cancelled), its own slice, spec, plan and workspaces leave active state and new bundles. The workgroup spec remains active for the shared manager and every unresolved member until every member resolves, including dependents waiting on or repairing after an upstream merge. Then it leaves active state. At both levels traces, workgroup spec history, rulings and owner decisions are retained until archive; delivery or resolution never deletes them. Active worker bundles are refused for resolved members, and the manager's staged view omits their own spec and plan. The historical documents remain available through trace context readers.

A member resolves only through recorded cancellation/abandonment, or delivery with merge evidence. Merge evidence is an owner's outside-factory merge record (`osmia merged`) or a recorded merged outcome whose PR number matches the current publication. Ready PRs, drafts, closed but unmerged PRs, outcomes for earlier PRs and delivery without evidence remain unresolved and keep the workgroup spec active. Publishing, marking ready, archiving and cleanup do not establish a merge. This rule also applies to one-member workgroups; their existing delivery cleanup is separate from workgroup resolution.

New drafts, amendment revisions and workgroup deltas cannot require the whole project check suite to pass or run in a spec criterion or unit acceptance item. Admission problems name the criterion or unit item and ask for the observable behaviour or tests the unit adds instead. Mentions, quoted examples, prohibitions and universals scoped to a package or test set remain valid. Revisions check only added or changed acceptance text; unchanged wording in stored records stays valid.

### 4.4 Plan

The plan is the factory's working approach, not the definition of workstream scope. Each unit owns a coherent outcome described by its task, observable acceptance criteria, spec criteria served, dependencies and scheduling footprint. Optional constraints record the owner's hard limits, boundaries describe neighboring responsibilities and interfaces, and guidance records adaptable implementation suggestions, assumptions and file-level pointers. An explicit method in the owner's spec remains binding; a suggested method in guidance does not. A constraint never names files or line-level changes: a mason that needs a different file than the plan expected simply changes it.

Start with one unit when the profile can complete and review the outcome. Split for useful parallelism, reviewability or practical capacity, not file count or subsystem count alone, and size each unit so one mason turn can complete it. A unit can span implementation layers. When a feature has several units, one of them owns connecting their work in the running product, with acceptance that exercises the whole path rather than each part against fixtures. Detail future work progressively. Bounded investigation is valid work whose outcome is evidence and a revised approach.

Masons adapt implementation and make the necessary supporting changes their outcome needs, wherever those are. They consult neighboring assignments and ask for coordination before taking over another unit's outcome; touching code another unit's footprint names is not that, and needs no revision. The manager can commission a revision without an existing question. The architect proposes revisions and focused debate tests them. The manager decides a plan-only revision with recorded reasoning against approved intent. Go requires the spec to remain identical, preserves merged history, validates the graph and footprints, versions assignments, and invalidates affected reviews. Changed tasks, acceptance, constraints, boundaries or dependencies return affected work to implementation. A revision waits until affected running workers have returned before it takes effect. Started identities are retained; completed units change through follow-up work. Unstarted work can be split, combined or removed.

Newly discovered necessary work is recorded under discoveries/ with its criterion and a durable disposition: open, assigned to an unmerged unit, declined with a reason, or retained as an optional suggestion. Workers record discoveries without ending their turns; the manager coordinates dispositions. Assigned work remains necessary until its unit lands. Open discoveries and pending revisions prevent assembly and delivery. Completing the initial unit list is insufficient when necessary work remains unresolved.

In-flight workstreams adopt current factory authority through an idempotent reconciliation recorded in the trace. Adoption and the manager's reassessment notice are committed together, so acknowledged historical blockers can be investigated again without duplicate notices after restart. New workstreams record their policy at intake. Delivered and abandoned workstreams are untouched. Every subsequent role turn, including a queued or resumed turn, receives current operating instructions alongside its original task. Adoption preserves sealed documents, completed work, explicit owner holds, escalations and decisions; it neither rewrites plans nor grants ratification or publication. Any restructuring uses the ordinary revision workflow.

### 4.5 Where they live

```
~/.config/osmia/config.toml      profiles, capacity, budget, Hearsay, listen addresses; read, never written by Osmia
<root>/                          default ~/.local/share/osmia
  runtime.json                   profile overrides, pause states, workstream priority, archive records
  project-store/                 the ordered project registry and each project's settings, as revisions
  skills/                        clones of the skills roles name, and their generated plugins
  projects/<project-id>/
    trace.db (+ -wal, -shm)      the project trace: charter, entity map, lasting decisions
    osmia.lock                   process lock
  workstreams/<project-id>/<workstream-id>/
    trace.db (+ -wal, -shm)      the workstream trace
    osmia.lock                   process lock
  workgroups/<workgroup-id>/
    trace.db (+ -wal, -shm)      a cross-repo workgroup's trace: membership, workgroup spec, shared manager thread, decisions
    osmia.lock                   process lock
  workstreams-staging/           a workstream's trace is built here, then published by one atomic rename
  workstreams-deleting/<project-id>/  a trace archive cleanup moved aside, durably marked for removal
```

No other trace file exists on disk. Each trace is one SQLite database. Its records are addressed by logical paths: a workstream's `handed/` input, its `spec.md` and `plan.json` revisions, `shed/round-<n>/` contributions, `amendments/<n>/`, `questions/<n>/`, `units/<u>/` records, each agent's `agents/<id>/log.jsonl` of turn requests and final responses with provenance, `events.jsonl` transitions with who and why, and the `ledger.jsonl` of costs, all under `workstreams/<workstream-id>/`; the project's `charter.md` and `kb/entities.json`. Recorded data cites these paths, and they keep resolving. Every write is one database transaction whose cost depends on the size of the write, not the size of the trace.

A Hill Climb workstream's trace also holds one immutable document per attempt at `climb/attempts/<n>.json`, which every role reads through `factory_context`. The record carries the attempt's number, the commit it started from, the hypothesis, the scores and their change from the best, the outcome and its cause, the diff summary and the full output and parsed values of every measurement run. The service writes it once when the attempt ends; recording the same attempt again changes nothing, and a different record under the same number is refused. The code that measures an attempt (the evaluator contract, schema 1; the measurement runner; the median, calibration and keep/discard arithmetic; the protected-path gate) lives in `internal/climb` and decides without any agent.

`workstreams/<project-id>/` is separate from `projects/<project-id>/` and every other repo's: a workstream's trace never shares a parent directory with the project tree. `workstreams-staging/` and `workstreams-deleting/<project-id>/` are working areas of the service, not a stable public layout: a directory listing of `workstreams/<project-id>/` never observes a workstream before its trace is complete, and never observes one once cleanup has begun removing it.

The defaults follow the XDG base directories: the top-level configuration is `osmia/config.toml` under `$XDG_CONFIG_HOME`, and the root is `osmia` under `$XDG_DATA_HOME`, falling back to `~/.config` and `~/.local/share`. Everything else Osmia keeps is in the root. An explicit `--root` is self-contained and holds its own `config.toml`.

Each workstream's trace records are its decision trail, and `osmia trace` walks them in either direction: criterion to unit to turns to review to commit, or commit back to the ruling that shaped it. Each project trace keeps its decision trail and owns its charter revisions, and the cross-repo workgroup trace keeps the shared workgroup spec and conversation history.

A trace directory with no `trace.db`, such as one holding only a `.git` directory, holds no trace: the service and `osmia doctor` treat its project as having none. A record, kind or file the trace does not recognise is refused with the trace's own error for it.

Startup preserves each one-repo project's ID, paths and authoritative charter. Every existing non-session workstream, including building, delivered, abandoned and archived records, appears in its own one-workstream workgroup with its existing manager thread. Exploratory sessions appear under the project outside all workgroups, with their session kind, thread and exclusion from factory passes unchanged. This step requires no owner action, preserves traces, rulings, decisions and archive records, and is resumable and idempotent across crashes and repeated starts.

State updates and their outbox entries form one database transaction: after a restart both are visible or neither is. Every write is a transaction. Durable operation identifiers connect an intended side effect to its result, so recovery can inspect a workspace, branch or existing pull request before retrying. Each consecutive failed attempt of an operation doubles the wait before the next, up to five minutes, so a persistent failure does not become a retry storm. A landing, rebase or publication that keeps failing is bounded and always ends in a result (section 7.3.1). A change that must write both project knowledge and a workstream's trace, such as a charter revision and its notice, or a ruling promoted to a project decision, stays recoverable as a whole: after a restart neither store ever shows half of it. Writes to one workstream's trace do not serialize behind another workstream's, beyond the project's own brief bookkeeping of which workstreams exist. Revisions and records remain available after delivery or abandonment; removing a project from active configuration does not delete its trace or the owner's clone.

## 5. Workgroup and workstream lifecycle

Every feature request runs as a workgroup over the owner's chosen projects. A hand-in names an ordered `projects` list through the API; `project` is a one-element shorthand. `osmia handin <project-id> <doc> --with <project-id>` adds projects, and the web form offers a multi-select of every active project. The first project is home and hosts the shared manager and conversation. Go refuses empty or duplicate lists and inactive projects; paused projects are allowed. A single-project hand-in retains the ordinary workflow. Several projects create exactly one member workstream each through the same allocation and join path as design start, without a model selection turn.

The owner can discuss a feature in a design session first. Its brief starts with the session's project and may include other active projects under owner confirmation (§6.7). Start pins the brief text, revision and ordered project list together durably. It either completes with exactly that input and stable member identities through recovery, or remains safely retryable without allocation. The architect drafts every selected member's spec and plan plus the workgroup spec, contracts and graph. A judgment that a selected project needs no change is escalated to the owner; the architect cannot drop it.

The project set stays fixed from hand-in or design start until ratification. No owner or agent control can add or drop a member in that interval; to choose a different set, abandon the work and hand it in again. After ratification, amend and cancel keep their existing rules. `--base` must name a workstream in a selected project and applies only to that project's member. `--skip-debate` applies to all members. Pause, capacity caps and `git_operations` stay per project: one project's held member does not hold the others beyond their graph edges.

The workgroup has one shared manager thread, opened at Start from the brief and the design transcript. For design intake it stays at the session's project even if that project is absent from the brief's list. The original address and every member's conversation and feed reach that thread. After a resolved member is owner-archived, surviving members retain the same authority and active workgroup spec across cleanup and restart. Reading the shared thread needs no live member: once every member is archived the original address still reads it, while sending to it needs a live member to supply context. Archive records preserve verified resolution and group identity; missing history alone proves neither resolution nor merge. Consolidated inbox entries retain their original question and ruling links. An effect needing unavailable retired history stays pending with a recoverable diagnostic, and no surviving member waits on it.

An archived member never holds up the survivors' workgroup changes (§5.4). An amend or cancel is requested, drafted, debated, decided and applied while some members are archived. The change reads each archived member from its archive record: its terminal state, merge evidence and pull request, with its slice taken from the approved workgroup spec. An archived member's slice is frozen. A delta that changes it is refused with a reason naming the member, and a delta that omits it carries the approved slice forward. An archived member gets no turns, rework units or cancellation, and only live members need effects. A member archived after the owner approved a change is recorded on that change as receiving no effect. Its slice stays as ratified, and the change applies to the survivors.

Retirement cancels an unclaimed member delta dispatch while preserving the
shared decision. A running shared turn retains its claim and captured response.
After capture, the retired dispatch settles through the ordinary outcome of the
shared turn, allowing the retired member's archive cleanup to finish.

For several selected projects, one ratification approves the workgroup spec, graph and every slice. A durable group decision pins every revision; seal preparation resumes after interruption without another approval. Until all pinned seals complete, the whole group stays pending and no member builds or releases a contract edge. A member whose sealing fails holds the group pending, and the manager is told what failed. Ratifying the workgroup again at the approved revisions, by the owner or as the manager's proposal the owner accepts, records the pinned ratification of every member whose latest sealing failed again, so the sealer seals that member afresh, as it does for a single workstream. The group approval itself does not change, and no member's spec or plan is redrafted, debated or amended while any member is unsealed: a footprint the entity map does not resolve resolves once what it names exists upstream, and a plan that must change needs the workgroup cancelled and handed in again. Each member retains its own final-review acceptance, delivery approval and owner signing.

A hand-in or design start records its project selection durably with the handed input.

### 5.1 Feature states

```
handed -> sketched -> in-shed -> ratified -> building -> assembled -> delivered

revisions adapt the plan in building or assembled; the owner decides intent changes

terminal: delivered, abandoned, and for a Hill Climb that kept no attempt and whose evaluator-only pull request the owner declined, concluded (no improvement)
```

| State | Meaning | Handled by |
|---|---|---|
| handed | You gave the factory a document, a design, an issue link, or a paragraph. Copied under `handed/`, never modified. | owner |
| sketched | The architect has drafted the spec and plan against the handed design, the charter and the entity map. | architect |
| in-shed | Committee members read the spec and plan in parallel and object with citations. The architect answers once per round. Rounds are capped by `max_shed_rounds`. When debate ends, the manager decides each committee objection that stands before the packet reaches you. You may object, rule, edit the spec and plan with `osmia edit` or the web UI, or ratify as handed and skip debate for small work. | committee, architect, manager, owner |
| ratified | Your ratification of intent, with any charter or owner objections explicitly resolved and the current execution plan recorded. The seal is recorded: upstream main commit and spec hash. Footprints are taken from the plan, entanglement advisories issued, the feature branch created. | owner, foreman |
| building | Units move through their own states below. Amendments may arrive. | mason, committee, foreman |
| assembled | Every unit has merged. The service records which merged units serve each criterion. The branch is rebased, signed, pushed and opened as a draft pull request with no approval, and Dagger Cloud's statuses of the pushed commit are watched. One committee member then reads the whole branch at a high level against the spec's intent and the charter, and reports findings, each blocking or advisory, with the check result as evidence. The manager triages blocking findings into a plan revision or leaves them to you; you can accept them as they are when you mark the pull request ready. | committee, manager, owner |
| delivered | You approved **Mark ready for review** and the draft pull request, under your name, with a description the manager drafted and the delivery brief's "Before you ship" items, was marked ready; or you marked the draft ready on GitHub yourself; or you merged the branch into upstream yourself and recorded it. Terminal. | foreman, manager, owner |

The stored workflow state `delivered` records a pull request marked ready for review as well as an owner-recorded merge. It is distinct from workgroup resolution and the project pane's labels: an open, unmerged PR is **PR open**; **delivered (merged)** requires merge evidence, whether live or archived. Neither a draft nor a ready pull request resolves a member or releases a merge edge. Cancellation uses the recorded abandoned terminal state and displays **cancelled**. A workgroup resolves exactly once, when every member is merged or cancelled. Archive and cleanup do not supply a merge or turn unresolved publication into resolution. Archive records preserve the verified merge commit and reference, or the current pull request lookup identity, so a dependent can observe its upstream merge after archive, cleanup and restart. Retained history remains readable to the edge resolver; a missing merge record never becomes a release signal.

The service observes every delivered member's own current PR, with or without a same-repo base or downstream edges, at most once per configured `pull_request_poll` interval. A matching merged or closed outcome stops observation. Open responses and failed lookups record no outcome; failures retry on the next cadence. A closed-without-merge outcome stops observation but leaves the member unresolved. This observation is distinct from dependency-edge release.

Within the ordinary build loop feature states move forward. An approved workgroup amendment can reopen affected open-PR work on its existing branch (section 5.4), and a workstream move (below) can return work to building or to final review. An assembled feature whose final review finds something blocking remains assembled. Nothing is built from a finding on its own: the manager groups the blocking findings that need code into one plan revision, whose units use the normal implementation, review and landing loop, and the final review runs again after they land. The manager leaves a finding that is mistaken or not worth building to you, and you can accept any blocking finding when you approve delivery. Once final reviews of a workstream have found something blocking three times, further revisions of its assembled plan are yours to decide. Changes to ratified intent require an owner amendment; changes to the execution plan use a factory-approved revision. Neither a failed final review nor the end of a debate cap authorises delivery.

The owner may abandon an undelivered workstream. Abandonment stops new turns, cancels active turns while retaining their recorded work, releases capacity and preserves the trace. It does not delete the owner's branch or close an existing pull request. A drift rebase still pending at abandonment ends as skipped, whatever gate held it, so it never defers archive cleanup. A landing, rebase or publication still pending is released from its dependency edge wait, so it reaches a result and does not defer the cleanup either. Abandoned workstreams are terminal, and so are delivered workstreams whose pull request is merged or closed, or whose merge the owner recorded. A concluded workstream, a Hill Climb that kept no attempt and whose evaluator-only pull request the owner declined (section 5.7), is terminal too. It is not an abandonment: nothing is cancelled, and the draft pull request is closed with a comment saying why.

The state machine can also leave a workstream itself stuck or wrong: a final review that failed and will not run again on an unchanged branch, blocking findings on a delivered pull request that drift has broken, a stage that needs to run again. So the owner can move a workstream to any feature state, with a note. Each move goes through the path that state already has, so no move bypasses a gate. Before ratification, a move to sketched asks the architect for a redraft with the note, a move to in-shed asks for one more round of debate, and a move to ratified ratifies the latest packet. A move to abandoned abandons the workstream. A move to assembled asks for a fresh final review of the branch as it is, with the note for its reader. It moves a building workstream whose units have all merged, reruns the review of an assembled one, and returns a delivered workstream whose pull request is open to final review. A move to building reopens an assembled workstream, or a delivered one whose pull request is open, on its existing feature branch. It stays building until a revision filed after the move is decided and its units land, or until it is moved to assembled, and its final review then runs again. A move to delivered returns a reopened workstream to delivered while its branch is still what its open pull request carries. An open pull request is updated only after a fresh final review and that workstream's own delivery approval (section 5.5). A move to building, assembled or delivered and its note are recorded together with the change of state; the other moves record themselves as the owner's own actions do. The manager's `move_workstream` is its own decision (section 6.6): the router enters the move it names after the hard prerequisites, except ratification and abandonment, which stay owner gates. The manager records an owner's move as the owner's only when the owner asked for it in the message the turn answers.

The owner may permanently archive a terminal workstream: delivered, abandoned, or concluded with no improvement, the state of a Hill Climb whose owner declined its evaluator-only pull request (§5.7). Archive keeps a small archive record outside the deleted storage: the project, the workstream ID, the title, the outcome (delivered, abandoned or concluded), the archive time and, where one exists, the delivery link, the pull request URL or the recorded upstream commit for an owner-recorded merge. Archive cannot be undone; the UI states this before submission.

The owner's manual archive remains available for any terminal workstream. The manager also archives a workstream on the owner's behalf, automatically, when its own pull request merges. A workstream qualifies when it is `delivered`, not archived and not a session, and the factory has durably recorded the own-pull-request outcome `merged` for the same pull request number as its current opened publication. An open, closed-without-merge or unobserved pull request, a merged outcome of an earlier pull request than the current publication's, an owner-recorded merge with no pull request of its own, an abandoned workstream and a workstream reopened out of delivered all stay as they are. Each reconciliation pass picks the qualifying workstreams from that recorded evidence alone. It adds no pull request lookup: merge detection stays with the existing own-pull-request observation. A merge recorded before a restart is archived by the first pass after it, and so is one recorded before this behaviour existed. The pass archives through the owner's archive, with the same guards, workgroup snapshot, resolution evidence, merge pin, delivery link and cleanup deferrals. The qualification is checked again on the snapshot that commits the archive: if the current publication or its outcome changed since the pick, nothing is written and a later pass tries again. So is an archive refused while a workgroup change holds the archive, or after the workstream's state changed. An archive that already exists, including the owner's, is never replaced. The archive record stores its actor as `chief_of_staff`, the manager's stored name, for an automatic archive, and nothing for the owner's, which older records also read as. The archive response, the status of an archived workstream, the workgroup member summary and the CLI's `osmia status` show it as `archived_by` (`owner` or `manager`), and the web pane labels it. The manager conversation shows the action as a manager entry saying the workstream was archived because its pull request merged, with the pull request link (section 6.6).

The archive also pins `resolution_evidence` from the member's history as `merged`, `cancelled` or `unresolved`; `resolved` is true only with merge or cancel evidence. The service polls an unresolved delivered archive's exact pinned current PR at most once per configured `pull_request_poll` interval, even without a downstream dependency observer and after cleanup and restart. A matching observed merge or durable dependent edge merge receipt updates that evidence. Polling timing survives reload and may reset on restart; polling stops once merge evidence is recorded. Failed lookups supply no evidence and retry on the next cadence. An archived member without merge or cancel evidence keeps its workgroup unresolved and the workgroup spec active. The pane shows it as **blocked**, naming the missing pinned merge or cancel evidence. Retirement alone is never resolution, and missing history is never recreated to claim it.

Delivery and abandonment alone preserve the trace and remove temporary workspaces. Archive cleanup then deletes the workstream's independent storage, its own trace directory and its temporary workspaces: the workstream's database is closed, its directory moved aside by one atomic rename, then deleted. Cleanup is deferred, with a logged reason, while the workstream has unfinished turns, pending or unacknowledged operations, or a temporary workspace still being cleaned; while any retained workstream still depends on it as a base (an archived base can leave together with its archived dependents). Once every deferral clears, and when Hearsay publishing is configured, the service keeps the workstream's records that are not yet posted in the project's own trace without contacting Hearsay ([Hearsay integration](hearsay.md#pending-publication-survives-cleanup-and-removal)); it then records durable cleanup intent before moving the trace repository aside by one atomic rename. Its removal then runs without holding any repository lock, so deleting even a large trace never delays a read, a write or reconciliation of any other workstream. The archive record is marked clean only once the storage is confirmed gone; a later pass reconciles whether an earlier attempt was interrupted by a crash or is simply still in flight, so a half-deleted trace is never mistaken for a live one. Archived workstreams receive the same cleanup automatically, with their title, outcome and delivery link filled in while the trace is still present. Other workstreams, project records and target-repository branches remain intact.

Each archive cleanup pass with archives awaiting cleanup, and each trace removal it leaves running in the background, reports itself through the backend activity record (section 10.1), so cleanup's progress is visible while it runs and a failed removal stays visible until a later pass retries it. Projects with no archives awaiting cleanup emit no cleanup activity events.

### 5.2 Unit states

```
planned -> ready -> implementing -> checking -> reviewing -> approved -> merged
                        ^              |            |
                        +--------------+------------+ checks failed or changes requested, bounded by max_bounces

any state may also be: waiting (a question is open), contested (send-backs, a mason clean-turn decision or a move)
any started unit that has not merged may be moved by the owner or the manager
```

| State | Meaning | Handled by |
|---|---|---|
| planned | In the plan, dependencies not yet merged. | scheduler |
| ready | Every unit it depends on has merged. Eligible for a slot. | scheduler |
| implementing | A mason works in the unit's workspace until its task is done and its acceptance holds, then ends its turn with the outcome: what the work does and how it checked the acceptance. For a project with the verification setting, the mason's bundle also names the feature files that apply to the unit, and its report may list the lever invocations it verified with ([Verification](#97-verification)). | mason |
| checking | The service runs the project's Dagger checks on a fresh export of the exact candidate before review. Passing checks, including a flaky check that passes its one rerun, send it to review with their result. Failing checks send it back to implementing with the failures and their output, as a send-back counted with review's toward `max_bounces`. A run that does not complete holds the unit here, tells the manager and runs again later; three in a row contest it. | service |
| reviewing | The unit's reviewer reads the unit's task and acceptance, the mason's outcome, the recorded check result and the unit's diff against the feature branch, with the sealed spec as background, verifies the acceptance and decides. The reviewer runs no checks. Material findings send it back to implementing with the findings. A finding is material when the task or an acceptance item does not hold, when the change reaches beyond what the task needs, or when it breaks a written rule: the project's charter, its AGENTS.md or contributor documents, or a skill configured on the reviewer role. Every task is carried out under those rules, so a breach is reported as a failing part of the task, naming the rule and where it is written, in the verdict's existing finding fields; the verdict schema is unchanged. A code-smell judgement call that breaks no written rule never blocks and goes in a satisfactory verdict's summary, and formatting and lint stay with the checks. The reviewer's review method comes from the skills configured on its role, such as `pr-review` and the code-style skills; its system prompt keeps only Osmia's protocol (the exact candidate, the check evidence, the rebase and drift scope, `ask` and `verdict`), which overrides a skill's own output format and any instruction never to stop and ask. The same reviewer re-reviews the revised candidate, always an exact commit. For a project with the verification setting the reviewer also has `verify` and a bundle section of service-recorded reruns, flow coverage, notes and flags, which are evidence it judges and never decide the verdict by themselves ([Verification](#97-verification)). | committee |
| approved | The reviewer is satisfied. Waiting for the foreman. | scheduler |
| merged | Squashed to one commit on the feature branch, message generated from the unit's title and the criteria it serves. Units still in flight are rebased. | foreman |
| waiting | A sub-state of any of the above: the unit's role asked a question and its turn ended. Nothing else on the unit moves until the answer arrives. Other units continue. | manager, owner |
| contested | Send-backs by failed checks and review reached `max_bounces`, the mason gave up or exhausted its clean-turn bound (counting its clarify turns and its continuations after refused reports and failed turns), a role's turn failed on every retry, a reviewer's turn ended or failed without a verdict, its reviews were refused as stale, three rebases of its workspace onto one feature branch commit were refused, its check runs did not complete or its role's turns were interrupted too many times in a row, or a move held it for you. The manager rules on it first (section 6.6), and its ruling or move takes the unit out of a contest whoever raised it; a unit you moved here is yours to move out of, and a manager move for it waits as a pending owner decision; what it cannot resolve is raised to you with its findings. Nothing on the unit moves until a ruling. | manager, owner |

Waiting and contested preserve the underlying unit stage and any candidate under discussion. An answer or ruling resumes that stage through a recorded transition; it does not bypass review or landing checks. A ruling of review on a unit contested by failed checks sends the candidate to its reviewer with those failures as evidence; it does not make them pass.

The state machine can still leave a unit stuck or wrong: checks that never complete, a block the service reports and cannot clear, a stage that needs to run again, a send-back you disagree with. So you can move any started unit that has not merged, from implementing, checking, reviewing, approved, waiting or contested, to implementing, checking, reviewing, approved or contested, with a note. The move and its note are recorded together. A move to implementing gives the mason a turn with the note and a fresh clean-turn allowance in its existing workspace. A move to checking runs the checks again on the recorded candidate, even if a run of it already completed. A move to reviewing gives the reviewer a fresh review of the recorded candidate with the note, and the review still starts from a completed check run of that candidate. A move to approved records your approval of the recorded candidate in place of the reviewer's verdict, and the foreman lands it with the usual landing checks. A move to contested holds the unit for you. A move into the state the unit is in restarts that stage. A unit that has not started moves only to ready, once every unit it depends on has merged, which kicks a ready unit, or back to planned while one has not; its mason starts it when it is ready. A merged unit has landed and is changed only through a follow-up, and a unit does not move while the foreman is landing or rebasing it. A move from waiting leaves the question open; its answer still reaches the role. A unit waits only on a question its role's latest turn asked, so a question asked before a move, or while the unit was contested, does not send it back to waiting once the move's turn follows it.

A check run is bound to its candidate, the feature branch commit it was built on and the diff between them, and recorded under the unit with the checks it ran, why they were chosen, the command, its exit status, a bounded diagnostic excerpt and its complete captured output, including failures and runs that did not complete. The service extracts failed-check diagnostics deterministically and classifies failures from the complete output. Agents can retrieve the captured output in chunks through factory_context; excerpt limits never discard the underlying evidence. A check that fails is rerun once by its own link, on the same export and within the same `checks_timeout`. One that passes its rerun is a flake and counts as a pass: the run goes on to finish whatever the failed run cancelled, skipping that check, and the record, the feed and the reviewer's evidence name it, with the diagnostics of its failure. One that fails its rerun, or whose rerun reports no result, stays failed. Dagger caches a failure under the address that ran it, so a check that first ran as its own exact link replays its failure and stays failed. A review starts only from a completed run of the exact candidate it reviews; a candidate that changed, through a revision or a rebase, is checked again first. A judgment of Jev chooses the checks the change can affect from the project's check links and `dagger check` runs those; when Jev is unconfigured, the listing is skipped and every check runs, and every check also runs when the judgment falls back (section 9.6). Dagger refuses addresses with different filters in one command. Selected links combine only when one address selects exactly the same checks; other links run in sequential commands, each with `--parallel 4`. The commands share one export, one check slot, one result and one `checks_timeout`, and stop at the first failed or incomplete part. At most four checks run at once across that run. The record keeps the chosen links, the commands actually started and their combined output. A refusal is judged on one command, so even a later command refused after earlier ones passed triggers the existing fallback to every check; the finished record describes the full run and its output keeps the earlier reports. Passing checks are evidence for the review and never an approval. A mason contest has no candidate, so the owner can only return it to implementing with a note and a fresh clean-turn allowance. Plan dependencies must reference existing units and form an acyclic graph. Invalid plans cannot be ratified, and an amendment must preserve those properties.

### 5.3 The shed

The shed challenges the initial intent and engineering approach, and holds focused debate for revisions. Members review from correctness, integration and scope perspectives and cite evidence. The architect answers objections and can revise the draft. Charter violations and explicit owner objections block ratification. Fit, unit size and acceptance-method disagreements are engineering advice; they receive an architect response but need not converge unanimously.

When debate concludes, or you skip it, every committee objection that still stands goes to the manager first. It dismisses on your behalf, with a recorded note, each objection the record answers: the architect's reply or the drafted documents address it, the charter rule it cites does not apply, or it is advice the plan can carry. That includes charter vetoes. It escalates to you what would change approved intent, needs an owner-reserved tradeoff, or what it is not sure the record answers. The ratification packet reaches your inbox once every committee objection is decided, and shows you only the objections it escalated and your own; its dismissals stay in the dissent record, the trace and its conversation. Your ruling on any objection takes precedence over the manager's. The manager presents the intent, recommended approach, assumptions and the dissent that needs you for ratification.

Debate is bounded. Further engineering work uses a focused revision or investigation rather than repeating a full committee merely to obtain agreement. A small feature may skip initial debate at the owner's request. Owner ratification remains required.

### 5.4 Revisions and amendments

The manager routes a question or commissions a revision for new evidence, discovered work, ownership changes or dependencies. The architect drafts against the recorded spec and plan, and a bounded shed round examines the proposal. The manager may decide a plan-only revision with an explanation of how it preserves intent. The owner decides changes to the spec, constraint exceptions and owner-reserved tradeoffs. A model's assertion cannot authorize a spec change: the service compares the proposed spec with the current approved text. Charter and owner objections to a revision remain owner decisions, which Jev decides for the owner only at the owner threshold (section 9.6).

The existing documents govern until a revision is applied. Revisions are pinned to the source seal.

While a workstream is building or assembled, the service retires every undecided amendment whose sealed spec or plan no longer matches its filing seal, including requests being drafted or debated. It records a rejection atomically as the service, with the reason and replacing seal, stops further draft attempts and debate rounds, delivers one ruling to the requester and resumes its waiting unit. Turn enqueue and claim are serialized with retirement: a turn claimed earlier may finish, but its result cannot advance the retired amendment. The manager receives a notice; the change can be filed again against the current seal if still needed. The owner receives no card and makes no decision on a stale amendment, and approval or overrule remains refused. Retirement leaves the sealed documents unchanged and reconciles across restarts. An upstream base move alone preserves the seal identity and retires nothing.

An amendment that has not been presented can also be withdrawn, whatever drafting or debate state it is held in: a debate round that cannot finish leaves it neither presentable nor decidable, and an open amendment keeps the workstream from assembly. The owner (`osmia amendment <workstream> <n> withdraw`) or the manager, as its own decision with its reason (section 6.6), withdraws it. A withdrawal is recorded and reconciled the way a retirement is, attributed to whoever withdrew it: a rejection with the note, its queued draft and debate turns cancelled, the sealed documents unchanged, one ruling to the requester and its waiting unit resumed. A presented amendment is rejected instead.

Amendments on the current seal keep their decisions and gates, and their cards recommend “approve” or “do not approve yet”; ratification packets recommend “ratify”.

Application versions the documents and records affected units atomically with the seal; subsequent recoverable steps update assignments, invalidate reviews and notify workers. Active affected turns finish before resealing. Changed approved intent invalidates the corresponding evidence and requires fresh review. A rejected proposal preserves the existing documents and returns its reason to the requester. Nothing edits target code as a side effect of a plan revision.

The owner can request an amend in the workgroup's manager conversation,
including the continued design chat. The architect and committee debate only
the delta against the approved workgroup spec and slices. The service compares
the proposed text and presents one impact summary with the proposed intent,
affected workstreams and unit assignments. That summary is the amendment's
only owner approval. Contract changes re-evaluate dependents along the graph.
Unchanged units retain their state and commits; changed completed units get
revision units, removed sections get code-removal units and new sections get
new units. Reworked units wait for their revised dependencies.

A member that has not started receives its new slice before building. Active
members stop at a safe unit boundary before rework. An open, unmerged pull
request retains its feature branch and is updated on the same pull request
only after fresh review and that member's own delivery approval. Changed
sections of a merged member become a new follow-up member in the same
workgroup; merged branches and historical decisions remain intact. An archived
member's slice is frozen and the delta leaves it unchanged; the impact summary
shows that member unchanged.

A change whose draft or debate turn ends without recording its result, or that
is ended from its recovery card, fails before it is presented and changes
nothing. A role whose request became the change receives the failure as its
ruling, the way it receives a rejection, and its waiting unit resumes against
the recorded spec. The manager is told once per failed attempt, with the
failure and whether `retry_change` applies, through the events of the
workgroup's leading live member: in that member's own project for a cross-repo
workgroup.

The owner can also cancel a workgroup or a member in that conversation. One
impact summary includes cancellation of its transitive dependents and asks
whether open pull requests should be closed or left as drafts. Cancellation
holds unstarted landing and publication operations while repository effects
already begun reconcile to a whole-unit boundary. Unlanded work remains on
unit branches through the ordinary abandonment cleanup. Merged work is kept,
including a pull request that merges while cancellation is being applied.

### 5.5 Delivery

The pull request opens as a draft when the workstream is assembled, with no approval, and every later commit is pushed to it without one. Your delivery decision is **Mark ready for review**. A delivered workstream's open pull request that a drift refresh or a post-merge dependency update changes still needs that workstream's own fresh delivery approval of the description and commit messages before the service pushes the update or marks the pull request ready. There is no workgroup-wide approval or pre-authorized publication.

At assembled, the foreman rebases the feature branch onto upstream main one last time, the service signs and pushes it and opens the draft pull request (below), it watches the Dagger Cloud statuses of the pushed commit, and the committee's final read runs against the check result as evidence. The service drafts the pull request title and description from the trace: the title is the workstream's title (the status goal you see for it, or, before one is set, a fallback from the sealed spec's first heading or the handed issue's title), and the description a short summary of the sealed spec, closing the GitHub issue the workstream was handed in from when one is recorded. The draft carries them from the start. Your decision is the **Mark ready for review** card. It shows the final report's findings, the recorded check result and the manager's delivery brief, the title, and a collapsed read-only "What will be published" section with the description, including the brief's "Before you ship" items, and each commit message. It has no editor and one button, except on a project opted in with `delivery = "jev"`, where **Approve and land** sits beside it (see Landing below): **Mark ready for review**, **Accept findings and mark ready for review** when the final review has blocking findings, or **Update pull request** for a delivered workstream being maintained. The page sends only the pinned review identity (the final review, its revision, the reviewed commit and the draft's hash), so the service publishes the text it previews: the text of an earlier approval when the decision is offered again after a refused marking, and the draft otherwise. The API and CLI still accept an edited description; the commit messages were fixed when the commits were pushed and cannot be edited. To change published text afterwards, edit the pull request. The pushes go to your repository or fork under your name. Per repo, the branch lands either with one commit per unit, the default because reviewers on a large project want reviewable commits, or squashed to one.

**Draft pull request.** After the foreman's final rebase, the service signs the rebased commit (one commit with `landing = "squash"`, one per unit otherwise) with the drafted messages, pushes the feature branch and opens the pull request against the upstream base as a draft, with the drafted title and description. No approval gates this, and the workstream stays assembled. The description carries no "Before you ship" items yet, because no delivery brief exists before the final read. While the pull request is open, draft or ready, every later final review, whether it follows a revision for blocking findings or failed checks or a drift rebase, signs its rebased commit and pushes it to the same pull request, again without an approval. `final/publication.json` records each push before it happens and records it opened once the pull request is verified at the pushed commit: the push number, the final review, the rebased commit and the signed commit that reached the branch, when it did, and the pull request number, so later records can name the push they concern. A final review that finds the pull request merged or closed pushes nothing: it fails with the reason, recorded in its report, and the manager is told. A retry reads the recorded push, the remote branch and the pull requests again, so a restart leaves one push of the commit and one pull request. Without a GitHub token the service pushes nothing and asks GitHub nothing: the final review waits at publication, the workstream stays assembled, no check record is written and the final read does not start. The wait reason, which names `GITHUB_TOKEN`, shows as the workstream's wait in the status and in one notice to the manager. A restart with the token retries the review, which signs, pushes and opens the draft, then waits and watches the checks as for any other push. Mark ready only ever acts on a commit that has a recorded push, and is refused with its reason otherwise.

**Mark ready for review.** The card is offered for the current final review once the manager's turn for it has recorded the brief or ended without one. Approving it pins that review, its revision, the reviewed commit and the draft's hash, so an approval made before a later automatic push replaced the commit is refused as stale and marks nothing. The approval puts the approved title and description, with the brief's "Before you ship" items, on the open draft, marks the pull request ready for review and moves the workstream from `assembled` to `delivered`, recorded in `final/ready.json` with the approval and the pull request. It opens no pull request and pushes nothing. The card is first put to Jev at the owner threshold (section 9.6): a confident approval pins the same review identity, publishes the same text through the same path and is recorded as Jev's, and the commits stay signed and pushed under your name and key; otherwise the card reaches you with Jev's pick and confidence as its recommendation. It is refused, and the workstream stays assembled, when the pull request is merged or closed, no longer at the pushed commit or against the reviewed base; the card is then offered again. When a merge-order dependency has not merged, the approval is recorded and the workstream is delivered, but the pull request stays a draft with the dependency stated in its description; once the dependency has merged and the update has been reviewed, you approve again and the service marks it ready. If you mark the draft ready on GitHub yourself, the pull-request poll notices it at the `pull_request_poll` interval, when the draft is open and at the current push's commit, and records the workstream delivered by you, without an approval.

**Landing.** On a project whose `delivery` is `jev`, a workstream can instead land on the upstream base branch. One service entry point serves the owner's "Approve and land" and Jev's binding `land` decision, and it reports one of landed, held, fell back, base moved, refused before the push or pending. It refuses, before anything is pushed, unless checks passed on the exact signed commit of the current push, the workstream is assembled with a current final review and nothing waits to merge before it. It then records the landing as a `land-delivery` operation, which the router applies as a pinned move whose trigger is `ws.landed`: the router holds the move while another operation of the workstream is in flight or work is paused or out of budget, and a held landing pushes nothing and is applied once the hold clears. The service fetches the base branch first. If the base already holds the signed commit, even after moving past it, the landing happened. Otherwise it records its intent in `final/landing-intent.json` (the signed commit, the upstream remote and branch, the base commit before and who decided), then fast-forwards the base branch to the signed commit with a plain push that is never forced and never makes a merge commit. A push the upstream rejects as not a fast-forward, or a fetched base that no longer holds the base the review read, is a moved base: the existing rebase is asked for and the decision to land is kept, in `final/landing-route.json`, with who decided (the owner, or Jev's binding `delivery-route` pick with its judgment). Checks and a new final review run on the rebased branch as they do for any push. While the route is pending, neither the delivery presentation nor the delivery card treats the owner's approval to land as stale or asks again, and Jev is not asked a second `delivery-route` judgment for the new push. Once the rebased workstream is assembled again with a current final review and a new push whose exact signed commit passed checks, the service's landing-retry pass lands that push through the same entry point and router, under the same decider, with no second approval; a conflicting rebase and failed checks keep the existing repair path, and the pull request is not marked ready. The retry rechecks every landing gate: when the new final review leaves blocking findings to the owner (the earlier acceptance is not carried over), checks did not pass on the new commit, a hard-block or merge-order dependency waits, or the project no longer lands, the route is dropped and the ordinary delivery card appears. Each retry lands a different, newly signed and checked commit, so no landing is pushed twice, and a retry whose base moved again keeps the decision for the next push. A push the upstream explicitly refuses, as a branch protection, a hook or a missing permission does, is recorded as refused in the intent; the draft pull request is then marked ready under an approval of its drafted title and description that the service records for the decider, the workstream is delivered, and a notice says why it did not land. No new pull request is opened and no owner card is raised. Any other failure (a timeout, a dropped connection, a lost response, a crash) leaves the outcome unknown: the next attempt, under the bounded recovery every operation has, fetches the base branch and settles it before it does anything else, so a landed commit is never pushed again, rebased or marked ready, and one that did not land is retried. A confirmed landing writes `final/landing.json`, the branch, the landed commit, the upstream remote and branch, the base commit before, the base commit a fresh fetch confirmed, the time and who decided, and in the same commit the `final/merge.json` record every dependency edge, archive and presentation already read as a merge, and the move to `delivered`, so the workstream resolves and its hard-block, merge-order and follow-up edges release without waiting on GitHub. The feature branch stays on the push repository. A landed workstream's pull request is still open at the next pull request poll when GitHub did not already close it, as it does once the base holds the pushed commits; the service then closes it with one comment naming the landed commit and the base branch, and records the outcome in the own-PR outcome so that later polls and restarts neither look at it nor comment again. A pull request the host already shows merged or closed is left alone, only its outcome is recorded, and neither that outcome nor the closing ever changes the landed workstream's delivered and resolved state: the landing record, not the pull request, is its merge evidence. The owner gets a notice recording the landing, and one notification through `notify.webhook` naming the landed commit and base branch, once, including for a landing a restart completed. Status and the delivery presentation show the workstream as landed with its commit (`delivered (landed <commit>)`, and a `landing` field in the presentation), not as a merged or ready pull request.

The final read is high level. Each unit was already reviewed in detail against its own task and acceptance, and the checks cover style, formatting and lint. The service gives the reader every criterion with the merged units that serve it; a criterion no merged unit serves is blocking. The reader follows how the units' work connects in the running product and checks the whole against the spec's intent and the charter. It records a summary and findings. A finding is blocking only when the feature as a whole fails the spec's intent, its units do not work together, or it breaks a charter rule; anything else is advisory, shown to you and building nothing. The branch the reader sees was rebased onto upstream. Changes a rebase or drift resolution needed so that both upstream's behaviour and the feature's stand belong to the branch whatever the sealed spec, plan or footprints name. Upstream's own changes are not the feature's. Neither is a finding on its own. A later final review starts from the previous one: it reads what changed since, says whether each earlier blocking finding is resolved, and raises a new blocking finding only where a change since then breaks the feature or a criterion plainly fails.

For a project with the verification setting the final reader also gets a regression sweep, the flows of the feature map read from the feature-branch head, and runs it with `verify` ([Verification](#97-verification)). The results are evidence the reader judges, and never change the workstream's state.

**Delivery brief.** When a final review is recorded as reviewed, the manager's notice for it also tells the manager to record a short delivery brief with `record_delivery_brief`, naming the review number and the review revision (the revision of `final/report.json` the notice gives). The brief answers whether what was built matches what you asked for: how the approved intent shows up in the product, at most one line on how it was implemented and a note on any departure, never tests, files or commits, with at most 3 `preview` screenshots of the reviewed commit for a visible change, or one line when a capture is impossible. Its text is at most 800 characters; an optional "Before you ship" list holds one-line items, at most 400 characters in all, for what deploying the change needs (secrets and environment variables, required or changed config, migrations, new services or permissions, manual steps, breaking changes for callers), and the manager checks every delivery for these; the service detects none of it. The service accepts a call only while the named review is the member workstream's current reviewed final review awaiting your delivery approval, and stores the brief with the review number, revision and reviewed commit in the member's own trace, one record per review, so a later call for the same review replaces it and a brief for an earlier review is never current. A call naming an earlier review, a review you already approved, or over a limit, or with a screenshot that is not a `preview` capture of that member at the reviewed commit, is an ordinary `recorded:false` result with a reason and stores nothing; nothing is truncated, and a shared manager names the member. The delivery inbox entry for a review waits while the manager's turn for its notice is queued or running without a brief, appears once a brief is recorded, and appears saying "No brief was recorded for this review" when that turn ended without one or no manager turn can run; a brief recorded afterwards, before approval, replaces that message. Approval never waits for the brief. The delivery presentation's `brief` field carries the text, items, screenshot image IDs, the review number, revision and commit it covers and a state of `waiting`, `recorded` or `none_recorded`, and only from the brief for the presented review. The drafted pull request body carries the brief's "Before you ship" items, and nothing else of the brief, as a `Before you ship:` list after the draft-dependency sentence and before `Assumptions:`, only when the brief for the presented review has items; the list is part of the draft and its hash, so a brief recorded or replaced after you read the presentation makes an approval of the earlier presentation conflict. With no brief, a brief for an earlier review or a brief without items, the title and body are unchanged.

**Final checks run on Dagger Cloud.** The final stage runs no check of its own: it takes no check slot, makes no smart or Jev selection and starts no local `dagger check`; unit checks keep their local smart-selected runs. After each push the service reads no status for 2 minutes, then reads the combined commit statuses of the pushed head commit in the upstream repository through the GitHub API, at the project's `pull_request_poll` interval. The verdict and the counts come from those statuses alone. A status's `target_url` is a link to its Cloud page, recorded and shown as a link and never fetched, and no check is polled. A missing or failed `load` is as described below. A "Run Dagger Checks" status that is absent or pending means the run is pending; `success`, `failure` or `error` means it is complete. The per-check statuses are every context except `load` and "Run Dagger Checks". They give the counts: total is their number, passed those in `success`, failed those in `failure` or `error`, and a check in any other state (pending, or no result) is unaccounted. GitHub statuses have no cancelled state, so a new result's cancelled count is always zero; an older record may still carry one. A completed run is failed when the run status or any per-check status is `failure` or `error`; it passes only when `load` and the run are `success`, there is at least one per-check status and every one is `success`. Otherwise it is incomplete: the run reports no checks, or some checks have no result, and the record says which and how many of how many. A run status of `success` alone is never a pass. On a failure the failed checks' names and `dagger trace` ids come from the failing per-check statuses of the same read, and a failed `load` status is itself a failed result. A status read that fails, because the answer cannot be decoded, is not a success or could not be read in full, is reported with the HTTP status code, the response content type and any decode error, and never with credentials, response bodies or text from GitHub's error body. Every failed check reaches the workstream with the command `dagger trace <id>`, the id taken verbatim from its own status description: in the final reader's check evidence, in the manager's notice for a final review whose check result failed (whatever the reader found), and in the result of the manager's `pull_request_checks` poll; a failed `load` is the failed check `load`. A failed check whose description names no trace id is listed by name with a statement that none was posted and its status link, and a failed run with no failing per-check status reports its counts, the run's status URL and that no failing check status was found. The commands and links carry no credential; Osmia gives the command, and the manager and the final reader can have the service run the trace fetch for them with `read_cloud_trace`, which returns the scrubbed, bounded output of the named trace, whole or narrowed to one check, and records it under `traces/`. When the service records a failed result, it also fetches the output of each failed check that names a trace ID, narrowed to that check, and records it as that check's own `traces/` document (checks sharing a trace ID each have one); a fetch that fails or times out is recorded with its reason as a `-failed` document and never fails the review or changes the result or the rerun. Each trace ID and check is fetched once across restarts and retries, and an interrupted record is completed with only the missing pairs before the reader's view is built. The final reader's read-only view holds the review's recorded `final/checks-<k>.json` for the reviewed commit, any output file that record names, and, for a failed result, the recorded trace output or failure of each failed check under `final/checks-<k>-traces/`; its prompt lists them under "Your view holds". The prompt carries the check result in its own "Check result:" section before the criteria, and every file the evidence text names is in the view; a review of a delivered workstream writes no record and its evidence names no file. The reader has no check-status tool and cannot run checks. Its system prompt says that a recorded pass satisfies the criteria that need passing tests, that a recorded failure is evidence it may cite, and that continuing without check results is not a finding by itself; the unit reviewers' check gate wording is not part of it.

If the first read finds no `load` status, the manager gets one notice for that push, and watching goes on. The notice names the push, and the manager can act on it with two tools that name the push they concern. `pull_request_checks` with action `poll` reads the combined statuses of the pushed commit at once and says what they show, and makes the watch read them again at its next attempt instead of at the end of `pull_request_poll`; with action `rerun` it asks Dagger Cloud to rerun every check of the pull request (`dagger cloud checks rerun --all --pr <N>`, from the workstream's checkout, with the API token `cloud_api_token_env` names and the same `--org` rule). `ask_owner_about_checks` brings you a `Checks missing` inbox entry with two answers, keep waiting or continue the final review without check results, and is also the way for a project that has no Cloud Checks. Both tools act only on the workstream's current push: a call naming a superseded push is refused, naming the current one. Only your answer continues without check results: no manager or Jev call can, and the API, `osmia checks` and the web inbox are the only way to give it. Keep waiting leaves the watch running and records no result. Continue lets the final read start on that pushed commit alone, with evidence stating that no check results exist and that you chose to continue. The entry and your answer name the push, its pull request and pushed commit and the push record, and a later push (a revision or a drift rebase) closes the entry as obsolete: an answer to it is refused as stale, and the later push waits for its own results or for a new choice about itself, also after a restart. A completed result closes the entry too. If `load` ran but no completed "Run Dagger Checks" arrives within `checks_timeout` of the push, or a completed run reports no checks or has checks with no result, the run is recorded as incomplete and watching continues after a wait that doubles with each further run, up to an hour. Once three runs in a row have not completed, the final review shows in the inbox with the last failure and when the statuses are read next. It takes no decision, and the entry closes once a run completes. A run is never recorded as passed when it reports no checks or any check has no result. The next scheduled read records the result the statuses settle on.

On a completed failure the service records the rerun request (the push, the time, and the identity of the failing "Run Dagger Checks" status and its failed checks) in `final/checks-<review>-push-<push>-rerun.json`, then runs one `dagger cloud checks rerun --failed --pr <N>` from the workstream's checkout with the Dagger Cloud API token `cloud_api_token_env` names. That token is separate from the compute token `cloud_compute_token_env` names, which runs engines and cannot rerun checks or read traces; the API token cannot run engines, and no agent receives it. A project without a fork adds `--org` with `dagger.organization`, the organization the API token belongs to, since an organization token cannot rerun checks without naming it; a project with a fork reruns without `--org`, because its pull request's checks run in the upstream's organization, which the token is not assumed to belong to. Reruns therefore cover one organization. The rerun runs on the same commit, so the original failure keeps showing; only a "Run Dagger Checks" status with a different status id, created no earlier than the request (less 30 seconds of clock difference), settles it. Until then the failure stays on the record as the pre-rerun result and decides nothing. A fresh completed result classifies each originally failed check as a flake only when it passed: the fresh run has no failure, or that check's own status was reposted as a success after the request. The others stay failed. If no fresh completed result arrives within `checks_timeout` of the request, the run is incomplete. At most one rerun that Dagger Cloud accepted is made for a push. When no API token is available the rerun cannot be requested: the final review keeps waiting, with the reason that the variable `dagger.cloud_api_token_env` names must be set, and records no result for the failure. A request Dagger Cloud refuses, such as one made with a token that is not an API token, is not a rerun: the rerun record keeps the refusal, the run is recorded as incomplete with it and the token to check, and once that run's wait has passed the next read that still shows the failure requests the rerun again.

The completed result is recorded in `final/checks-<review>.json` with the source `pull_request`, the pull request number, the push, the pushed commit, the status URL, the counts, the failed checks with their trace ids and the rerun (request time, original and fresh status ids, flakes). The final read starts only on a completed result for the exact pushed commit of the current push, and its evidence carries that result. A restart resumes from these records: the wait is measured from the recorded push, and no rerun or notice is repeated. Records written by earlier local final check runs, with their selection, command and output, remain readable. Reviews of delivered workstreams (maintenance) push nothing and read without check results.

You approve delivery with the findings in view. Approving a report with blocking findings accepts them as they are, and the approval records what it accepted; without that acceptance, a report with blocking findings authorises nothing.

Local snapshots, unit commits and the rebased commits a final review reads may use Osmia's unsigned identity. With `landing = "squash"`, the delivery commit combines the whole workstream into one commit on the reviewed base. Squashing and review do not require signing credentials.

Before every push, including the first one that opens the draft, the service performs a pre-publication step: it amends the delivery commit using the owner's Git identity and signing configuration on the service host, including configuration scoped to the project's clone. It sets both author and committer to the owner and uses the drafted commit message, removing model or runtime-agent co-author trailers such as `Co-authored-by: Claude ...` while preserving human co-author trailers. It adds the owner's `Signed-off-by` trailer, then signs with the owner's configured key and signing format so the signature covers the final message. With `landing = "commit-per-unit"`, it applies the same requirements to every outgoing unit commit. No approval gates a push: the owner's decision comes later, on the pull request that is already open. Missing identity, an unavailable key or a signing failure blocks the push, with no unsigned fallback. Runtime agents never receive signing credentials.

Ordinary delivery completes implementation; a workgroup dependent can still repair its post-merge update within its slice, an approved amendment can reopen an unmerged member, and a workstream move can reopen a delivered workstream whose pull request is open (section 5.1). Your approval is tied to the final reviewed branch revision, the pushed commit, and the PR title and description you saw. If any of them changes before the pull request is marked ready, the affected review and approval must be refreshed; a status goal set after approval does not change the title an already approved description publishes. The pre-publication amendment changes commit IDs but must preserve the reviewed tree and base, and the drafted message apart from agent co-author cleanup and the owner's sign-off. The trace links each reviewed history to the signed history that was pushed. A change to the content or base makes a fresh final review, a fresh push and a fresh approval. The service durably records each push before it happens. Pushing is resumable: a retry reuses the recorded signed commits and finds the recorded branch and any already-created pull request instead of signing again or opening another one. The host moves a pull request's head shortly after its branch moves, so an open pull request that otherwise matches but is still at a commit an earlier publication of the workstream recorded leaves the push pending for another attempt rather than refusing it. Without a GitHub token the service pushes nothing and asks GitHub nothing: no draft opens, the final review waits for a restart with the token before any final read, and an approval to mark ready shows in the inbox at once, waiting for a restart with the token. A publication whose last three attempts failed, such as a marking ready that GitHub refused, shows in the inbox with its last failure, including the host's explanation of a refusal, and when it is next attempted. It takes no decision: the owner fixes the cause, such as a token without pull request access, and the entry closes once an attempt succeeds. These requirements also apply to delivery maintenance for dependent workstreams and owner-requested drift checks of delivered pull requests.

You may instead merge an assembled feature's branch into upstream yourself, outside the factory, for example while the service runs without a GitHub token. The factory still delivers through a pull request; this path only records a merge you made. You record it as the owner: the service fetches upstream's base branch and checks that it already holds the changes of the feature branch tip, meaning their merge is clean and changes nothing, so fast-forward, merge, squash and rebase merges all count. One commit then records the merge, naming the branch tip and the upstream commit that holds it, and moves the feature to delivered with a notice for the manager. Nothing is pushed and no pull request is opened. The merge needs no final review or delivery approval: merging was your delivery decision. It is refused for a feature that is not assembled, and while upstream lacks or conflicts with the branch. A publication waiting for a GitHub token is refused in the same commit. A publication the service could still carry out refuses the merge until the publication has an outcome. Descendants treat a base delivered this way as integrated upstream.

When Hearsay is enabled, upstream review feedback can later arrive through its GitHub connector. The manager presents it as a notice or question (section 12.4). For a workgroup, an owner-approved amendment can rework an open, unmerged pull request on its existing branch; changed merged work instead gets a follow-up workstream (section 5.4). Other additional code work requires you to hand in a new workstream, referencing the delivered trace and, when appropriate, its branch as the base. Without Hearsay you may hand in that feedback yourself.

### 5.6 Workstream kinds

A workstream has a kind. `feature` is the kind this document describes everywhere else: a ratified spec and plan, built as units. A kind is Go code in the registry of `internal/kinds`, not a plugin or a setting. A stored empty kind reads as `feature`, so no existing workstream is migrated. Exploratory sessions (`session`) and design sessions, which the `design-session` subject marks, are not kinds and are never looked up in the registry.

Every kind shares the outer states of §5.1: handed, sketched, in-shed, ratified, building, assembled and delivered. Only the inner machine that runs while a workstream is `building` belongs to the kind. Delivery, final review, pause, budgets, `move_workstream`, the stall watchdog, the recovery card, archiving and the API state fields therefore work the same way for every kind, with no per-kind top-level state.

**What a kind supplies.** One registry entry holds:

- the documents the architect drafts, the committee debates and the owner ratifies, and the building loop with its inner states;
- fixed capability flags: has units and a plan, can join a multi-project workgroup, allows upstream drift while building, can be a base or have dependency edges, can target a brand-new project;
- a pull-request section, a one-line progress summary that reads the kind's progress, and the web panel that draws it;
- the names of the extra manager tools it adds, and the skills and `[kinds.<kind>]` settings table it owns.

`feature` supplies today's behaviour through these hooks: the spec and plan, the units loop, no extra pull-request section, the units progress bar, `move_unit`, and no settings.

**Choosing the kind.** The owner chooses it, explicitly and once, at hand-in. It is never inferred, and the architect never picks it. There is no kind picker in the web interface.

- `osmia handin --kind <kind>` and the hand-in API field `kind` default to `feature`. The service refuses a kind it does not register, with a reason that lists the registered ones, and records the kind in the commit that creates the workstream.
- In a design session, the design agent chooses the kind through the optional `kind` parameter of `draft_brief`, an enum taken from the registry. Omitting it keeps the brief's current kind, and a brief that never set one hands in as `feature`. The brief panel shows the kind next to the project list. The agent's instructions carry the registry's catalog: each kind's name, a one-line use-when and the drafting-time limits its flags set, and the agent says in its reply which kind it chose.
- Start pins the kind into the start intent with the brief revision, checks it against the kind's flags again, and records it on every member in the same commit that records the handed brief.
- A recorded kind never changes: any later attempt to set another kind is refused.

**Flags are consulted, not assumed.** Code that iterates workstreams is one of two things. A shared place reads, accounts or notifies, and takes every workstream that is not a session whatever its kind: the event and question deliverers, the status, inbox and activity reads, and the pass that raises the unrecognised-kind notice. A kind-specific place moves work: drafting, debate, sealing, building, scheduling a turn, landing, drift, delivery and the watchdogs. It lists the workstreams this build runs and consults the kind's flags instead of assuming `feature`: a brief or hand-in the flags forbid is refused with a plain reason, a base or dependency edge on a kind that cannot have one is refused, and upstream drift is not applied to a building workstream of a kind that disallows it.

**One kind per workgroup.** A workgroup holds one kind. A kind that cannot join a multi-project workgroup has exactly one member, and a workgroup of mixed kinds is refused.

**A kind this build does not register.** A workstream whose stored kind is not registered waits: nothing moves on it except its manager's own thread, the manager gets exactly one notice for it however many passes run, and it is never run as `feature`.

**Adding a kind.**

1. Add its entry to the registry in `internal/kinds`: name, one-line use-when, flags, documents, building loop, pull-request section, progress, manager tools and settings. Set only the hooks the kind uses.
2. Set the flags from what the kind can do. The checks at hand-in, in `draft_brief`, at Start, for bases and dependency edges, for workgroup joins and for drift read them, and the design agent's catalog lists the limits they set.
3. Implement the kind's inner machine for `building`, and make seal and build admission ask the kind which sealed documents it needs.
4. Add its `[kinds.<kind>]` table: validate the table in the kind's settings hook, name the skills it loads and the turns that load them, and document the keys in [configuration](configuration.md).
5. Supply the kind's progress summary and web panel, and its pull-request section.
6. Add its manager tools to the registry entry and the manager's grant.
7. Document the kind here and in the CLI and OpenAPI documents, and add the kind to the tests that list the registry.

The kind is chosen at hand-in and fixed after it, so a new kind adds no migration: workstreams that record an older kind, or none, keep reading as they did.

**What a kind says about its documents.** The registry entry says which document sits in a workstream's spec slot, where it is recorded, whether the kind has a plan beside it and how many committee rounds it gets. Seal and build admission ask the kind rather than assuming a spec and a plan. A seal of a kind with a plan records positive revisions of both and is admitted into `building` by recording each unit of the sealed plan, exactly as before. A seal of a kind without a plan records the spec-slot revision alone, with plan revision 0, and records `kind` in `seal.json`; a Feature seal records no `kind`, so it is unchanged. The service refuses to seal a plan revision for a kind without one and a missing plan revision for a kind with one.

### 5.7 Hill Climb

`hill-climb` is the second kind: it improves one measured number by repeated attempts, in one existing project. Its flags are all off: it has no units and no plan, cannot join a multi-project workgroup, takes no upstream drift while building, cannot be a base or have dependency edges, and cannot target a brand-new project. `draft_brief` refuses a `hill-climb` brief of more than one project or with a `new_project`, with a reason the design agent can act on, and Start checks the same again. A workgroup of this kind has exactly one member.

**The climb spec.** For this kind the architect drafts one document, `climb-spec.json`, in place of a spec and a plan. It is recorded in the spec slot of the ratification, so every shed record, the ratification packet and the seal pin it as `climb spec revision <n>` with no plan revision. It is a JSON object with these fields, and a draft that misses a required one or carries an invalid value is refused with every problem listed:

| Field | Meaning |
| --- | --- |
| `version` | `1`. |
| `goal` | Required. Prose. |
| `evaluator` | Required. The name of the function in the dev module, the module that `dagger.toml` marks `main = true`, that measures one run. Each climb may create its own. |
| `metric` | Required. `name` is the primary metric as the evaluator reports it, `direction` is `higher` or `lower`, and `min_improvement` is the absolute improvement above zero, in the metric's units, an attempt must reach over the best to be kept. |
| `repeats` | Optional. The measurements per attempt, k. It defaults to `[kinds.hill-climb] repeats`, and that to 1. |
| `guardrails` | Optional. `checks` lists project checks that must still pass. `limits` bounds secondary metrics: each names the metric, the `direction` the evaluator reports it with and a `min` or a `max`. The primary metric is never limited. |
| `protected` | Optional. `fixtures` declares the files the evaluator reads and `add` names further paths to freeze. The protected paths are always the dev module, `dagger.toml`, `dagger.lock`, the fixtures and the additions. |
| `stop` | `max_attempts` is required and a hard limit. `max_cost_usd` and `max_wall_clock` are optional hard limits. `plateau`, the attempts without improvement, and `target`, a score that ends the climb, are optional and soft. |

**One metric round.** The shed gives a climb spec exactly one committee round, which looks only at the metric: whether it can be gamed, whether it is too noisy to climb on and whether a path the measurement depends on is missing from the protected paths. A committee member's objections are of kind `metric`, which is advice to the owner, or `charter`, a veto, and concern a part of the climb spec as `climb#goal`, `climb#evaluator`, `climb#metric`, `climb#guardrails`, `climb#protected` or `climb#stop`. The architect answers once, and the owner ratifies the revision the packet names. The owner cannot ask for further rounds or for a redraft that is debated again, and `--skip-debate` goes straight to ratification. A change after ratification is an amendment: the architect revises the climb spec, one metric round debates it, the owner decides it, and approving it versions the climb spec and the seal on the same base. An amendment to a climb spec changes approved intent, so the manager does not decide it.

**Seal and admission.** A ratified climb spec is sealed, which creates the climb branch, and the workstream moves to `building` without a plan and with no unit states recorded by the build. The building loop reads the sealed climb spec through the seal's spec-slot revision. A Feature workstream without a ratified plan is still refused by its seal.

**Building: evaluator, calibration and the owner's approval.** While a Hill Climb workstream is `building`, its inner state is the workflow subject `climb`, which holds one of `evaluator`, `calibrating`, `held-broken-metric`, `held-too-noisy`, `awaiting-approval` and `climbing`. The inner machine moves it as the trace records each step, so a restart reads the state back and resumes in it without repeating a step that was recorded.

1. **Evaluator.** When the machine first reads the sealed climb spec it exports the climb branch and looks in the dev module for a function that matches: its sources name the evaluator, take a `run` argument and name the primary metric. A match skips the evaluator unit and the function is reused. Otherwise the evaluator unit, the one unit this kind has, runs as a normal unit: a mason writes the evaluator function and the fixtures it reads with the kind's skills loaded, the service runs the project's checks, a reviewer judges it against the climb spec and it lands as the first commit on the climb branch. The workstream has no sealed plan for the unit machinery to read, so the unit is made from the sealed climb spec each time it is read (`climb.EvaluatorUnit`), and the mason and reviewer bundles, the unit lookups and landing read it the same way. Its footprint is the whole repository, because it is the only unit in flight.
2. **Calibrating.** Once the evaluator unit has landed, or at once when it was skipped, the service runs the evaluator `[kinds.hill-climb] calibration_runs` times on the evaluator commit through the measurement runner, each run in a fresh export with the approved copy of the protected paths restored. It records `climb/calibration.json` with the baseline, the unit of each required metric, the run-to-run spread, the protected paths and the evaluator diff. A run that fails, is invalid, lacks the primary metric or a metric a guardrail limits, or reports another direction or unit, holds the climb as `held-broken-metric` and raises a notice to the manager that the metric, not the code, is broken. A spread at or above the minimum improvement holds it as `held-too-noisy`. A calibration that could not run at all, such as one a stopping service cancelled, records nothing and runs again. A held climb calibrates again when its climb spec changes by an amendment.
3. **Awaiting approval.** A calibrated climb opens the owner's approval card, an inbox entry of kind `climb-approval` that shows the evaluator diff, the protected paths the approval freezes, the baseline and the spread. Its one option is `approve`, answered by `POST /v1/climb/{workstream}/approval` with the evaluator commit and the climb spec revision the card shows, and an approval of any other commit or revision, of a card an amendment retired, or of a climb branch that has moved on from the calibrated commit, is refused. Only that explicit owner decision approves the card. It belongs to no owner gate, so the gate worker never asks Jev about it, `jev.KindClimbApproval` is owner-only and `Decide` refuses it, and no result of Jev, however confident or binding, approves it or starts climbing.
4. **Climbing.** Approval records `climb/approval.json` and moves the climb to `climbing` in one commit. The record holds the baseline, the calibrated units, the noise band and the approved copy of the protected paths, snapshotted from the evaluator commit and frozen from then on. The attempt loop starts from it.

**Amending a climb spec after approval.** Calibration, the approval and its card, the frozen copy of the protected paths and every attempt record carry the climb spec revision they were made under, and an approval or an attempt also carries its epoch: the number of the approval whose baseline it was measured against. When an amendment is applied, `climb.Compare` classifies each changed field of the climb spec. The evaluator function, the primary metric's name, direction and minimum improvement, the repeats, the secondary metrics a guardrail limits and the protected paths and fixtures are calibration-dependent. The goal, the stop rules, the guardrail checks and the bounds of a secondary limit apply in place, and the climb keeps its calibration, approval and best. An attempt kept under the old guardrail checks or limits is decided again before it is reviewed or squashed: when the climb spec revision its keep decision was made under is older than the sealed one and the guardrail checks or the bounds of a limit changed since, Go recomputes the decision from the recorded measurement against the amended limits and runs the checks again on the candidate when they changed. A candidate that no longer keeps is discarded through the attempt journal with the cause of the failing condition, whatever its reviewer answers, and one that still keeps goes on to review and promotion. An attempt already promoting or promoted finishes as before, and a change of only the goal or the stop rules leaves an open attempt as it is.

A calibration-dependent change sends the climb back to `calibrating` on the commit its branch holds, which is the current best. A climb that waits for the approval returns at once, and its card leaves the inbox. A climbing climb first brings its open attempt to a safe phase boundary: an attempt before `promoting` is discarded with the cause `amended` through the attempt journal, so it has its one terminal record and counts once against the budgets, and an attempt whose squashed commit was prepared finishes promoting and recording first, so the branch tip is the best that is really committed. The loop starts no attempt and measures nothing while the approval's climb spec revision differs from the sealed one after such a change, and neither does the machine. The recalibration records a new baseline and the owner approves it on a new card, never Jev. That approval starts a new epoch whose baseline is the best that later attempts are compared with: attempts of an earlier epoch are neither compared with it nor counted toward the plateau, and the panel draws only the current epoch's series and the attempt table marks the revision boundary. The attempt budgets and the wall-clock and cost origins carry on across epochs. The transitions and records are durable, so a restart part-way through resumes without a second terminal record or budget charge for the open attempt, without reviving the retired card and without starting an attempt before the new approval.

**Climbing: one attempt at a time.** While the inner state is `climbing`, a worker off the scheduling path runs the loop (`climb.Loop`), one attempt at a time. Every attempt is the unit `climb-attempt-<n>`, built over the unit machinery but on one mason thread, `mason-climb`, for the whole climb, so what the mason learns in one attempt is in its session for the next. There is no lead thread, no fresh thread per attempt and no parallel attempt.

1. **Mason turn.** The attempt's workspace is built fresh from the climb branch's tip, the current best, and the mason's turn carries the unit bundle (the sealed climb spec and the charter's context) and the attempt brief: where the climb stands, the log of the attempts so far, the manager's steering notes and the reviewer's notes from the last attempt when it was rejected. The mason's `done` takes a hypothesis, the change and the expected effect. A turn that ends without a report is continued, and an attempt whose mason ends `mason.max_clean_turns` turns without one is discarded as `no-candidate`; three in a row raise a notice to the manager that the climb is stalled.
2. **Gate, guardrails, measurement.** The workspace is taken as the attempt's candidate. A diff that touches a protected path is refused before anything is measured. The climb spec's guardrail checks run next, through the check runner and a `capacity.checks` slot. Then the measurement runs `repeats` times through the runner of the measurement core, and Go keeps or discards by `climb.Decide`. No agent turn decides it.
3. **Review.** A kept candidate goes to a reviewer, who reads it for metric gaming, breaches of the written rules and scope. Approved, it lands as one squashed commit on the climb branch and becomes the best. Rejected, it is recorded as discarded, and the reviewer's findings are in the next attempt's brief. A reviewer that ends three turns without a verdict rejects the candidate, so no candidate lands unreviewed.
4. **Discarded attempts.** A discarded attempt keeps its branch, `osmia-unit/<workstream>/climb-attempt-<n>`, at the candidate, so it can be inspected, and its workspace is dropped.

**Durable attempts.** An attempt's phase is the value of the workflow subject `climb-attempt-<n>`, and each move is one commit that also holds the journal `climb/journal/<n>.json` and `climb/running.json`: `started` (parent fixed, workspace built), `captured` (candidate and report recorded), `measured` (Go's decision recorded; a kept candidate goes on), `reviewed`, `promoting` (the squashed commit prepared and recorded before the branch moves), `promoted` (the climb branch is at it), `recorded` (the terminal `climb/attempts/<n>.json` is written in the same commit as the move) and `cleaned` (the workspace is dropped). A restart reads the phase and the climb branch back and reconciles before it retries a side effect: a measurement that was interrupted runs again whole; a promotion whose branch already moved is recorded, not moved twice; a record written is never written again; a cleanup retried drops the workspace and never the branch. The budgets are counted from the records, so an attempt is charged once, and the best is the climb branch's tip, which is always the last kept commit. A recorded attempt counts as progress for the loop guard; the climb budgets, the per-session cost cap and the daily budget still hold work back.

**Stopping.** After every attempt the stop rules are evaluated from the records: `max_attempts`, `max_cost_usd` and `max_wall_clock` are hard, and `plateau` and `target` are soft. A firing rule raises the `climb.stop` router exit with the targets `conclude`, its default, and `continue`. The `continue` target is legal only for soft rules and is entered by Jev at its strict bar; a spent budget cannot be continued past by Jev, the manager or a restart, only by an owner budget extension recorded before it. A continued stop is recorded as `climb/stops/<n>.json`, so a plateau counts from it. Concluding moves the climb to `concluding`: an attempt still in flight is discarded, and the one rebase, the measurement after it and the delivery of the branch follow, as the next section describes.

**Controls.** The manager is told of every kept attempt and of every plateau. Its kind tools are `climb_steer`, which leaves a note the next attempt carries, and `climb_conclude`. The owner pauses and resumes as for any workstream, and has two more controls, both pinned owner moves through the router: `POST /v1/climb/{workstream}/conclude` and `POST /v1/climb/{workstream}/extend`, which records an extension of attempts, cost or wall-clock time in `climb/budget.json`. Upstream drift is never applied to a climb while it is building, because the kind's `UpstreamDrift` flag is off: the schedule asks for none, and an owner's request for a drift rebase of a building climb, or of the project, is refused or skipped with that reason.

**Concluding.** While the inner state is `concluding`, and once the last attempt has settled, a worker off the scheduling path carries the climb through its conclusion (`climb.Concluder`) in four recorded steps. The record of each is a commit of the trace that also holds the revision of `climb/conclusion.json` it rests on, and the workflow subject `climb-conclusion` holds the phase, so a restart reads the phase back and reconciles it against the climb branch before it retries a side effect.

1. **Pinned.** The service resolves the upstream commit the branch is rebased onto, as it does for every workstream's final review, and records it as the conclusion target with the branch tip it replays (`before`) and the commit that tip sits on (`base`). It records the final before the rebase: the best score the climb reached, the attempt that made it, the commit on the climb branch that holds it and the candidate commit the evaluator measured. A climb that kept no attempt has the baseline on the evaluator commit as its final. Nothing reads the upstream again, so the target never follows an upstream that moves later.
2. **Prepared.** The foreman's replay makes the rebased commit from the pinned target and the recorded time, and the commit is recorded before the branch moves. A replay that conflicts records the conflicting paths in phase `conflicted`, raises one notice to the manager and leaves the branch where it is for the owner to decide.
3. **Moved.** The climb branch moves from `before` to the rebased commit. A restart that finds the branch already there records the move and does not make it twice; a branch at any third commit is refused.
4. **Measured.** The evaluator measures the rebased commit `repeats` times with the approved copy of the protected paths restored, through the same runner as an attempt, and the final after the rebase is recorded with the commit it was measured on. A measurement that is invalid is recorded as the final with its reason, and the manager gets a notice; it is never retried until it scores, because the owner decides delivery with it in view.

The climb branch is therefore rebased at most once, onto the target pinned when concluding began, however many times the service restarts and wherever upstream is by then, and the post-rebase measurement belongs to the commit on the branch that delivery publishes. A conclusion with both finals recorded moves the workstream from `building` to `assembled`, as the last merge of a Feature's last unit does, with no kind-specific top-level state.

**Delivery.** From `assembled` the shared machinery delivers a climb as it delivers a Feature, with these differences, all supplied by the kind's hooks and its lack of a plan:

- *Final review.* The reader gets the sealed climb spec, `climb/conclusion.json`, every attempt record, the charter, the check result and the branch, and reads the branch against the climb spec: whether the kept changes serve its goal without gaming the metric, whether the guardrails and protected paths are respected, and whether the results the pull request reports follow from the attempt records. The report cites no criteria, because a climb spec has none, and records plan revision 0. The review's rebase is the conclusion's: when the branch it was asked to read is the rebased commit, it records that rebase as its own and rebases nothing again, so upstream moving after the conclusion changes nothing. Waiting for units to land is skipped, since a climb has no plan.
- *Pull request.* The draft opens through the same publication path, with its record written before the push and the pull request found and adopted, not opened again, when a restart left one open before its record was written. Its body begins with the climb spec's goal and carries the kind's pull-request section: the metric and the minimum improvement; a results table with the baseline, the final before the rebase and the final after it, each with the commit it belongs to, its score and its change from the baseline; the line `Baseline → final: 101 → 90 before the rebase, 101 → 91 after it`; and, for each kept attempt, its commit, hypothesis, score and delta from the best it started from.
- *Owner approval.* The owner approves marking the draft ready exactly as for a Feature, with the same pinned review, report revision, commit and draft hash, and Jev may approve the card at its bar.
- *No improvement.* A climb that kept no attempt opens a draft pull request that holds only the evaluator and the files it reads, and its section says so. The delivery card then offers `decline` beside `approve`: `POST /v1/delivery/{workstream}/decline`, pinned to the final review the owner read. Declining closes the draft pull request with a comment and moves the workstream to `concluded`, with the reason "no improvement". `concluded` is a terminal feature state beside `delivered` and `abandoned`: it archives the same way, cancels no turn and is not an abandonment. Jev is never offered `decline`.

**Settings and skills.** `[kinds.hill-climb]` configures `skills`, the calibration run count, the default repeats and the measurement timeout, as [configuration](configuration.md#workstream-kind-settings) describes. The configured skills load on the architect's turns that draft, answer for or amend the climb spec, on the committee's turns of the metric round and on the evaluator unit's mason and reviewer turns, and on no other turn. The intended entry is the skills project's `hill-climb-evaluator` skill; Osmia names it in configuration and here and never bundles it.

**Progress, panel and API.** Hill Climb's one-line summary is its `Progress` hook: the number of recorded attempts, the attempt in flight with its phase, and the best score's change from the baseline, such as `14 attempts · attempt 15 measuring · best −18.4%`. The workstream list shows it with a sparkline of the best score after each attempt, oriented so that a rising line is always an improvement, and `osmia status` prints the same line. Both read it from the status of the workstream (`work_kind` and `progress`); a Feature workstream carries neither and shows its units as before. The kind's web panel replaces the nest tube and reads `GET /v1/climb/{workstream}/progress` and `GET /v1/climb/{workstream}/attempts`, both listed in `service.Routes` and refused for any other kind. The panel's data comes from the sealed climb spec, `climb/calibration.json`, `climb/running.json`, which says which attempt is in flight and in which phase, the workstream's cost records and the attempt records. The page redraws the panel when a `climb.*` event names the workstream, and draws the chart as inline SVG under the page's unchanged content security policy.

## 6. The manager and questions

### 6.1 One persona, one thread per workgroup

Each workgroup has exactly one manager, with no independent member managers. Every role's `ask` and each member's events reach that shared durable thread. Messages sent through any member reach it too. It reads the brief, workgroup spec, slices, each repo's entity map and code directly. Its persona also carries owner rulings, project decisions and optional Hearsay memory. Factory-wide controls work from any thread.

Questions from several members can remain open concurrently. Each answer resumes the original asking role and turn in its own repo's trace, preserving asking and response links through restart and bounded replay. One-workstream workgroups retain their existing manager thread. Shared-manager turns hold no exclusive trace lock across the model call, so owner conversation, feed and workgroup spec reads remain responsive.

### 6.2 What it does with a question

Every role has an `ask` tool. Its question always goes to the manager, never to another agent. The manager does one of five things, and the choice is recorded.

1. **Answers it** with an engineering decision within approved intent, supported by documents, code and evidence. The bundle for the question's scope arrives with current stances, conflicts and open questions, each with a pointer. A ratified stance answers a question, cited. Redirecting is a valid answer: "the code answers that, look here" is what a good manager says to a builder who did not look.
2. **Escalates it** when it changes approved intent, relaxes a constraint, needs an owner-reserved tradeoff or contradicts an owner ruling. It rephrases for you: which unit, which criterion, what is blocked, the options, its recommendation. Several open questions are batched into one ask.
3. **Routes it as a revision** when assignments, dependencies or the spec must change. The manager decides engineering revisions; the owner decides intent changes.
4. **Proposes a charter amendment** when your answer is a standing rule rather than a decision about this feature.
5. **Rephrases your answer** for the asker and decides its scope: local to the asker, or a notice in every in-flight bundle on the project when it applies wider than the question.

Worker escalations state the spec section, conflict, options and recommendation. Only a contradiction or extension of agreed design needs an owner design ruling; the manager resolves engineering choices from the record. A genuine gap pauses only affected units or workstreams, and becomes one consolidated owner question with options and a recommendation. The ruling resumes all and only its paused origins. Judgment calls within intent are logged through `log_assumption`; each workstream's drafted PR description includes its local assumptions and the shared manager's judgments affecting it. The manager can name affected member IDs with `workstreams`, or omit that selector for a workgroup-wide judgment. Shared judgments stay in the workgroup trace and remain readable after restart.

The manager investigates a question first, then calls `decide` for its routing (section 9.6): Jev picks to answer within the approved intent, to route an amendment, or to escalate. A confident pick binds the outcome tool; otherwise the manager chooses.

Every question lands in the trace as `questions/<n>/`: the question as asked, the decision, what you were sent, what you said, what went back, and what it changed. With Hearsay enabled, your answer is ingested under your principal through the owner source, which authority makes a ratified stance. The local ruling is authoritative and durable before external ingestion. An optional immediate assertion must reconcile to that same ruling.

### 6.3 Waiting

Nothing on the scheduling path waits on a model, and a session blocked on a tool call for the hours you are asleep would hold a slot and hit its timeout. So asking is non-blocking. Calling `ask` records the question and ends the turn with the outcome `waiting`. The workspace is intact. The unit parks in `waiting`, its slot is freed, and the rest of the factory carries on. When the answer arrives it is delivered as the asker's next turn, with the thread's context intact, so from the asker's side it asked and then it heard back. An answer that arrives after the asker's unit merged stays recorded but is not delivered: the unit's workspace is gone, and a merged unit changes only through a follow-up. A committee member's answer is delivered only to the debate round that asked. When that round is over before the answer runs (the plan was ratified or the debate concluded, or the amendment's round was decided or withdrawn), the answer stays recorded and its queued turn is cancelled, with the reason, before the member's next turn, so it never holds the member's later rounds or final reviews behind it. For unit masons and reviewers, the service follows the question named by the wait and verifies that its answer has been delivered to the asking thread, regardless of which turn is now last or whether delivery preceded the move to waiting. A completed done report then proceeds to checks; a reviewer verdict applies only to the exact current candidate, base, spec and plan, or the candidate is reviewed again in a fresh turn. Ordinary passes reconcile these waits after restart without rewriting history. If a delivered answer cannot be associated safely with the wait, the service contests the unit with a recorded reason for the manager and the owner.

The manager runs as a singleton per workgroup, one turn at a time, so its record stays coherent and it can batch. A question waits with no timeout. When an escalated question reaches the gate, Jev, the factory's decision maker, is asked once among the options the manager wrote; a pick at or above the decision threshold is recorded as the decision and relayed like your ruling, and the question never reaches your inbox. Otherwise it sits in the inbox until you answer. An escalation that reports a conflict between charters, or the architect's judgment that a project needs no change, is yours, so Jev decides it only at the owner threshold. Jev picks only among the options the manager wrote, so an escalation without them goes straight to you. Nothing answers on your behalf under a deadline. You asked to be asked, and a wrong guess silently built on is worse than a parked unit.

### 6.4 Status

The manager keeps a status per workstream, rewritten fresh whenever the answer to one of three questions changes: what is being worked toward right now, what happened since you last looked that changes the picture, and who is doing what.

- **Goal.** One sentence. Changes when the objective changes, not when a step completes.
- **Attention.** Only a concrete action or decision you must take now, with enough context to act. Otherwise empty.
- **Note.** A few sentences on what changed that matters and where things stand. Translated, not compressed: what a worker's result means for the feature, not its identifiers.
- **Agents.** One line per active agent in your own words.

Identifiers stay out: commit hashes, branch names, file paths, session ids, model names. The status is the thing you read for a few seconds after time away. Its goal heads every view, and each revision appears in the workstream's feed beside what prompted it.

### 6.5 Events

The service tells the manager what happened: a unit finished, a review came back, a question was raised, a landing succeeded, upstream moved. Events are written to a durable outbox in the same transaction as the state change, coalesced over a short window, and delivered as one turn, retried until delivered. Routine progress, such as a unit starting, passing its checks, being approved or landing, or the workstream changing state, asks for no judgment: it waits for a longer window, `events.progress_window`, or goes out with the next event that does. While an event turn is queued or running, new events wait for the next one rather than queue another turn. Event turns may run on a lighter profile than the turns that answer you. After the first failed delivery, the service retries immediately; repeated failures wait thirty seconds, doubling up to fifteen minutes. The delay is recovered from durable turn results, does not acknowledge undelivered events, and does not delay new events. When the owner's start of a design workgroup completes, the service raises a notice, not routine progress, that asks the manager to title the started work through its status goal (§6.7); it is delivered after `events.window` once per start, on the manager thread that continues the conversation. Only the manager receives events. Workers receive turns from the scheduler and nothing else, and are never told to wait for another agent.

Events tell the manager what the state machine did; they are the cue for its work outside the loop. Transitions stay the scheduler's and the router's, and the manager changes state only through its tools: moves, rulings, revisions, retries and dependency drops that are its own decisions (section 6.6), and the decisions you could take, applied as yours are. It never implements, reviews or holds version control.

The manager acts on events to keep work moving, and never takes an accepted action for started work. The result of each of its action tools (`move_unit`, `move_workstream`, `resolve_contested`, `resolve_objection`, `request_change`, `decide_change`, `route_amendment`, `decide_amendment`, `record_discovery`, `answer`, `relay_ruling`, `hand_back_drift`, `triage_finding`, `pull_request_checks`, `drop_dependency` and `retry_change`) says, computed in Go from the workstream's records after the action took effect, what work is now queued or running: `queued` lists each worker turn queued or running, each operation in flight that nothing holds, each unit in a state the scheduler starts work for, each answer awaiting delivery and each filed amendment awaiting its draft, with its role, unit and what it is. When the list is empty, `nothing_will_run` says until when: a pause lifts, a hold clears, the owner decides an open card, or the manager gets another turn. The manager tells you work is under way only when a result shows it queued, and otherwise checks back with a follow-up (section 6.6) instead of promising it.

### 6.6 Acting for you

The manager works on one workgroup with a defined job, not as an open-ended assistant. It takes the workstream decisions you could take when that resolves an issue or a conflict, and raises to you only what it cannot resolve or is not sure of. The service holds it to the same rules as you, records it as the actor, and shows each of its actions in the workstream's conversation.

A committee objection that stands at the ratification gate goes to the manager first too (section 5.3): it dismisses what the record answers and escalates the rest.

A contested unit goes to the manager first. Its view includes state, recent transitions, role outcomes, refused tool calls and candidate evidence. It investigates, rules review or revise with actionable reasoning, and commissions replanning or investigation when necessary. Repeated contests remain engineering blockers; escalation is an explicit decision about changed intent, a reserved tradeoff or an operational limitation it cannot resolve. The service budget and loop guard bound execution. The owner may intervene at any time.

A review or revise ruling on a unit held at `shed.max_bounces` is recorded together with its move out of contested. Review sends the candidate to reviewing with the ruling’s note, running checks first when no completed run matches it. Revise sends it to implementing with one mason turn carrying the send-back findings and the note. The service reconciles recorded rulings and pending turns through restarts, including a saved ruling whose unit is still held on the same contest. A manager’s decision is recorded in the same change as its ruling and move.

The manager works outside the state machine's loop: Jev decides inside it, at each exit, and the manager smooths what the loop leaves stuck or wrong. Its `move_unit`, `move_workstream`, contested-unit rulings and requests for a redraft or another round of debate are its own decisions, never proposals Jev judges: each is a pinned move the router enters exactly, after the hard prerequisites (a candidate exists where the target needs one, no landing, rebase or publication in flight, budgets, pauses and the loop guard), with the manager recorded as the transition's `decided_by` and no request to Jev. The result says what happened: the state moved, a prerequisite refused it, or the move belongs to the owner and is pending on a card. A manager never has to ask the owner to say or type anything to make a move: it reports in plain words what it did, or points to the card where the move waits. When the state machine leaves a unit stuck, the manager can return it to implementation, checking or review, kick a ready unit (ready), hold an unstarted one as planned, take it out of any contest, or hold it for you (contested). A unit you moved into a contest is yours to move out of, so the manager's move waits as a pending owner decision on the recovery card. A move that approves a candidate never carries the authority to: independent review or you approve, so it too waits on the recovery card. When the manager finds the workstream itself stuck or wrong, it can ask for a fresh final review (assembled), reopen it to building for repair (on an assembled branch or a delivered one whose pull request is open), ask for a redraft (sketched) or another round of debate (in-shed) once debate concluded, or return it to delivered, however many final reviews found something blocking. Ratification and abandonment are owner gates: a manager move for either commits nothing and waits on the ratification card or the recovery card. A deliberate move to contested holds work for the owner with the recorded reason. Owner-requested moves and rulings retain owner attribution.

The manager commissions a revision of any member at any time with `route_amendment`, naming the member with `workstream`: a building workstream whose units have all merged, an assembled one, or a delivered one whose pull request is open. Its citations resolve against that member's spec and plan. A revision for an assembled or delivered workstream first reopens it to building on its existing feature branch as the manager's own move, in the same tool call, so no separate move is needed; the revision then goes through the architect's draft and the committee's bounded round like any other, and its units are built, reviewed and landed, after which the final review runs again. Nothing limits how often the manager starts one; budgets and the loop guard bound the work it causes.

Two more recovery tools are the manager's own decisions. `drop_dependency` drops one dependency of a member that waits on an upstream that will not merge, whose changes already reached upstream another way, or without which the member works: the same waiver the owner's drop records (section 9.6), with the manager as its decider and `chief_of_staff`, the manager's stored name, as its stored `ended`. `retry_change` starts a stuck workgroup change's drafting and debate again: a change still drafting, debating or answering, or one that failed before it was presented, returns to drafting with its hold cleared and its debate emptied, under a fresh attempt whose turns are queued afresh. A failed change no longer blocks the drafting of a later one. `decide_amendment` with decision `withdraw` ends a project amendment that has not been presented and whose drafting or debate cannot finish, or should not (section 5.4): it needs no packet and no request to Jev, keeps the sealed spec and plan in force, and frees the workstream for a fresh final review. A refusal that an open revision causes names this lever.

The manager checks back on its own. `follow_up(after, reason, workstream?)` records a durable wake-up of its thread, the workgroup's shared thread for a shared manager, `after` from 5 minutes to 24 hours ahead. It is recorded in the thread's own trace, so it survives restarts, and each thread keeps one per workstream it names (none naming the whole workgroup): a newer follow-up replaces an unfired one. When it comes due the service queues one manager turn on that thread, and records the follow-up fired so it fires once, including across a restart between the two. When that turn ends failed or interrupted, the follow-up is pending again, due 5, 10 and then 20 minutes after the turn ended, and it fires at most three more times. One follow-up that cannot fire does not hold back the thread's others. The turn's prompt states the reason, when it was scheduled, and what changed since on the named workstream, or on each member: its state, its transitions since then and the work queued or running now; an archived member, or one whose trace is gone, is named archived instead. Owner pauses do not stop it, as they stop no manager turn. The project context of every manager turn lists the pending follow-ups. After a manager turn in which an accepted action reported nothing queued and the manager scheduled no follow-up, the service schedules one itself, once per turn, `[loop] stall_after` later (45 minutes while the watchdog is off), with the reason that an action started no work; a follow-up already due sooner stands, and the manager's own follow-up in the same turn withdraws it. A follow-up turn's prompt, and a stall notice (section 9.6), tell the manager the turn must end with an action whose result shows queued work, a follow-up, or a `set_status` attention item for you; a turn on a stall notice that ends with none of them gets the service's check-back in the same way. None of this adds an owner gate.

When a workstream's own pull request merges, the manager archives the workstream for you (section 5.1). It needs no model turn, and the owner's manual archive remains available. The archive records the manager as its actor, and the conversation shows an entry saying the workstream was archived because its pull request merged, with the pull request link. The entry is read from the committed archive record, so it exists exactly when an automatic archive committed and appears once, including after a restart between committing the archive and a read. A refused attempt and an archive the owner made first have none. A shared manager thread keeps the entry for as long as it exists, including after the archived member's cleanup. A solo workstream's conversation holds it until archive cleanup removes that conversation.

Charter changes and the approval to mark a pull request ready for review are owner decisions: the manager never takes them, and Jev decides them for the owner only with a pick at or above the owner threshold (section 9.6). Intent ratification and spec amendments are the owner's gates too: they reach the owner unless Jev decides them first with a confident pick. Plan-only revisions are factory decisions and remain out of the owner inbox unless they require an owner exception, or final reviews of the assembled feature have already found something blocking three times. The manager triages a final review's blocking findings one by one, with Jev deciding each when confident: it groups those that need code into one plan revision, and the delivery card shows you any it judges mistaken or not worth building, with the reason, which you can accept at delivery. For a delivered workstream with an open pull request, it first reopens the workstream to building.

The manager has an investigation and recovery mandate. It reads workstream documents and their history through factory_context, inspects a mason's recorded candidate or a service snapshot of its idle captured workspace with inspect_code's unit selector, retrieves referenced GitHub text with read_remote_file, and commissions bounded investigation through plan revisions. Remote sources are resolved to commits and recorded under sources/ with provenance and source citations; credentials remain in the service. Missing verification or factory capabilities are operational limitations, not intent decisions. Current assignments and evidence remain retrievable after context truncation. Assigned discoveries enter the unit's reviewer context and review identity; changing that work invalidates an older review. A shared manager names the member a tool concerns with `workstream`. factory_context, record_discovery and inspect_code, and its unit moves, contested-unit rulings, workstream moves, amendment and objection decisions and drift handbacks, then read and act on that member's own trace and repo; a workstream outside the workgroup is refused.

The manager can show built work with `preview(workstream, call, port, unit?, path?, timeout?, viewport?, full_page?)`. A shared manager must name the member. By default the service captures that member's feature-branch head; `unit` selects its recorded candidate as `inspect_code` does. The manager finds the Service call and HTTP port with `inspect_code` in that member's committed Dagger configuration and module source, and supplies them on each request. No project setup is needed. In the preview tool request, `call` must be non-empty and `port` from 1 to 65535. `path` must start with `/` and defaults to `/`; `timeout` defaults to `5m` (from `1m` to `30m`). Invalid arguments, no built source or an unresolved unit return a limitation the manager can explain, without failing its turn.

Go exports the exact source and starts the requested Service through the Dagger CLI, passing accepted arguments unchanged without a shell. New requests refuse CLI options, URI/provider schemes, client environment variable names, paths beyond the exported source (including symlinks), and host-writing or interactive chain steps. Checks include assignment values and comma-separated elements with Dagger's quote removal and trimming. Checks fail closed, so a legitimate value containing `:` may be refused; the manager can use the module default or explain the limitation. Only a decoded engine Service ID reaches the capture command. A durable operation with an owner-pinned argument list finishes from its pins without agent-argument or symlink checks. A pinned Chromium image, also run through Dagger, captures one path at a `desktop` or `phone` viewport, optionally full page. The manager runs no commands itself. There is no host browser, host port publication, interaction or live proxy. Preview runs share `capacity.checks`, appear as `preview` waits in capacity views, respect engine maintenance and cancellation, and start their timeout only after admission. Their client gets the check client's PATH, engine selection and redacted Cloud compute token, without provider, GitHub or SSH credentials.

Each preview is a durable operation keyed by manager turn and call. Its image is recorded in the shown member's trace, with only a reference in the shared conversation. Retrying or restarting reuses a recorded image and completes any missing shared reference, read-only-view copy and tool completion exactly once; an interrupted capture without an image runs again. Failures return bounded, redacted diagnostics without failing the manager turn. The result names the image ID for the manager's reply, and that turn's images are copied into its read-only view. Storage, deletion and rendering follow section 11.

Beside `preview` the manager has `verify` when the project has the [verification setting](configuration.md#verification): it runs the project's lever against the member's feature head or a named unit's candidate, and a shared manager names the member the same way. `preview` is unchanged. [Verification](#97-verification) describes `verify` and the contract it runs under.

### 6.7 Project design conversations

An owner opens a design session from one project before handing work to the factory. The session's agent is the `designer` role, a role like the others with its own profile, sandbox, image and skills; unconfigured, it runs on the `default` profile with sandbox `none`, never on the manager's settings, and it takes no `events_profile`. Its turns are recorded on a design thread of its own, apart from the manager's thread. A session opened before the designer role existed keeps its earlier messages on the manager's thread, where they are still read and shown, and its new turns go to the design thread. The brief's ordered project list starts with that project; a brief with no recorded list also means only the session's project. The agent sees a catalog of every active project with its name, upstream and whether it is in the brief. Brief projects' charters and entity maps are in context; other active projects' charters and entity maps are files in its scoped view. Its tools are exactly `file_read`, `read_repo`, `draft_brief` and `set_title`. `read_repo` reads committed source from any active project and refuses inactive or unknown projects. The agent has no write, VCS or credential access. File-based context supports the whole conversation without Hearsay.

`set_title` gives the session a title. The agent calls it once the session's context is clear, which need not be the first message, and again to replace the title when the subject changes materially; the latest call is the title. A title is one non-empty line of at most 200 characters, checked like a status goal: it holds no Osmia, backend or session identifier, commit hash, model name, URL, file path or branch name. A refused title records nothing and returns an ordinary tool result with the reason, so the turn continues. Each accepted call is a new revision of a document in the session's own trace, so the latest title survives a restart and destroy removes it with the rest of the trace. The tool is reachable only from a turn of a session whose design-session marker is `open`, and it writes nothing but that session's title: it starts no work, and it changes neither the brief nor its `brief_revision`, so it never conflicts with a Start pinned to that revision. No title is required; a session without one is listed by its workstream ID everywhere. The design list and read responses return the latest `title` (omitted when none is set), the status API's workstream entry for a design session carries it as its `title`, and `osmia design read` prints it. Ordinary manager turns, exploratory sessions and started designs never reach the tool; a started workstream's title is its status goal.

When Start completes, the manager titles the started work. The service records, in the same durable steps as the start, one notice that names the handed brief (`handed/design-brief.md`) and asks the manager to call `set_status` with a goal that is the title of the started work: one sentence written for the owner from the brief, under the status rules it already follows. The notice goes to the thread that continues the conversation, which depends on who owns the conversation after Start and not on how many projects were selected. When the session's own project is the sole selected member, the session becomes that member and keeps its own manager thread, so its own thread receives the turn. Otherwise, whether several projects were selected or the owner excluded the session's project and selected exactly one other, the conversation is adopted into the workgroup's shared manager thread and the session's local manager retires: the first member carries the notice, so the shared thread receives the turn, and the retired local manager receives none. The notice is an ordinary notice, so it is delivered within `events.window` and does not wait for `events.progress_window`. It is keyed by the start, so a start interrupted at any of its durable steps and recovered after a restart, or retried, records and delivers it once. It adds no owner gate and no tool: the manager's `set_status` and its rules are the means, the goal is the title of the started work and is the status goal the started workstream, or the workgroup and its members, report, and delivery drafts the pull request title from it. A start from a design that was never titled behaves the same.

`draft_brief` accepts optional `projects`. Omitting it keeps the current list; a supplied list must be nonempty, ordered, unique and active, unless the brief also describes a new project. Paused projects are allowed. The session's project may be removed while another remains. An owner's request to add or remove a project is confirmation. An inferred addition or removal is a readiness question with a recommendation and is applied only after the owner agrees.

`draft_brief` also accepts an optional `new_project`: a display name, a repo name GitHub accepts, a visibility (`private` unless the brief says `public`), a description and a first charter. A refused field names itself in the tool's refusal report: an invalid repo name, an empty display name, an empty charter, a visibility other than `private` or `public`, or a description over 350 characters. Omitting `new_project` keeps the latest one, a new object replaces it and `null` removes it. The new project is stored in the design draft record beside the brief, so the latest brief carries it. A brief is valid with a `new_project` and any number of existing projects, including none, and is refused with neither. The agent is told that a new project's repo starts with only a README, that the new project's first unit must set up `dagger check`, that visibility stays private unless the owner confirms public in the session, and that it creates nothing and holds no credential; its tools are unchanged. A session opened for a new project is hosted in an existing project's records, the project whose card opened it or else the first active project, and its default project list is empty, so the host project joins the brief only when the brief names it. Opening one with no active project is refused. The design view returns the latest brief's `new_project`, and the page shows its name, repository, visibility and description before Start.

The readiness pass asks about expensive-to-undo choices, genuine forks without a signal and tension with owner intent. Questions include recommended answers; other assumptions are collapsed and can be overridden by replying. The brief records decisions, intent, tradeoffs and rejected options, taking precedence over the reference transcript.

The design read API returns `brief_revision`, `brief` and `projects`. A read-only **Brief** panel above Start shows the latest revision, ordered project names with the home project marked, and the brief text collapsed by default. It refreshes when the agent records a new brief; the list is not editable on the page. Start sends the displayed `brief_revision` to `POST /v1/design/{workstream}/start`. A stale revision returns `conflict`, starts nothing and refreshes the panel with the error visible. The API accepts an optional pin; web and CLI clients always send the revision they read. `osmia design read` prints the revision and project list; `osmia design start` reads them, prints the list it is starting with and sends that revision.

Start records the brief's project list, followed by the new project when the brief describes one, as the owner's decision and creates one member per project, with no architect selection turn. The handed text, revision and list remain bound through every durable start boundary and retry: recovery completes that exact start once, or leaves it retryable without allocation. It never pairs handed text with a newer brief's list. The conversation remains at the session's project even when that project is no longer a member, and the shared manager's thread, which Start opened from the brief and the design transcript, serves it from then on. The design conversation stays on the session's design thread and reads ahead of the manager's thread; no manager turn resumes the design session's backend session. Answered escalations retain one owner-ruling action with the exact answer and recorded time. The original design address continues to serve conversation and ratification. One ratification covers the workgroup spec, contracts, graph and every slice; no member builds until every pinned seal completes. Each keeps its own trace, branch, delivery approval and signing.

**Creating a new project at Start.** When the pinned brief has a `new_project`, Start creates that project before it allocates any work. Creation is on only when `[projects]` has both `repo_owner` and `clone_dir`. Start is refused, recording nothing and creating nothing on GitHub, when creation is off, `GITHUB_TOKEN` is missing, the token's authenticated account is not `repo_owner` (compared case-insensitively, because GitHub creates a repository for the token's own account), the repo name is taken under `repo_owner`, or `clone_dir/<repo>` exists. Otherwise Start records its intent with the brief revision, the existing projects and the `new_project` pinned, together with the creation identity: the project ID the new project will have, reserved from the service before any GitHub write. A later `draft_brief` cannot change what is created.

The creation runs in the service under that identity and keeps its plan in the `project add` journal, saved before any GitHub write: the owner and repo, visibility, description, clone path and charter, and that a create call is about to be sent. The repo is created for the authenticated user with only a README and the brief's description, private unless the pinned brief says `public`. As soon as GitHub answers, the journal records the repository's numeric `id` and full name; a name other than `<repo_owner>/<repo>` stops the creation. The service clones from the SSH URL GitHub returned into `clone_dir/<repo>`, using the host's git and SSH configuration with `GITHUB_TOKEN` removed from every git command's environment. It then makes sure the README commit is on `main` and that `main` is the repo's default branch, without touching the account's default-branch preference, registers the project through the `project add` steps with upstream `<repo_owner>/<repo>`, no fork and base branch `main`, records the drafted charter as its first revision and removes the journal last. The service never deletes a repository.

Every reconcile pass looks the creation identity up before it acts. A complete creation proceeds; a pending one resumes under the same identity; one that never started runs under it. One that never started can still be refused when it runs, because the token, the repo name or the clone path changed since Start checked them. The refusal is recorded on the design start once per distinct reason, the owner's inbox shows it with a retry, and the manager of the design's conversation gets a turn that names it, so it can tell the owner what to fix. The start stays where it is and every pass tries the creation again, so a cause put right, such as a token set again, lets it go on. A restart at any handoff, including after the journal is removed and before Start records its selection, therefore finishes the same creation once, and startup recovery of the journal and the design-start reconcile may run in either order. Once the identity reports complete, Start records its selection as the brief's existing projects followed by the new project and allocates the new project once, as an ordinary member. With only the new project, the design conversation moves into the workgroup's records and only a retired starting stub stays in the host project. The new project member's handed input opens with a fixed line saying the repository is new and holds only a README, and that its first unit must set up `dagger check`; Osmia generates no Dagger module and picks no toolchain.

A retry reuses a repo only when the journal holds the repository `id` this creation's own create call returned. A repo of that name with no recorded `id`, with another `id`, or one GitHub refused to create because the name is taken, means the repo's ownership could not be established: nothing is cloned, registered or adopted. When a create's outcome is unknown and no repo of that name exists, the service may send it again.

A creation that cannot finish appears in the owner's inbox as a `project-creation` entry, whether Start, `osmia project create` or the API began it. It says what is stuck. A clone failure names the host git credential as the likely cause. A stop for ownership, or a repository whose identity differs, says that the repo's ownership could not be established and that the owner must resolve the other repo on GitHub before retrying. The one decision offered is retry, which runs the creation again under its identity, reusing only the repo this creation made, and completes registration and, for a Start, allocation. It never offers adoption. The web page lists the entry on the project pane; `osmia inbox` prints the command that retries it.

### 6.8 Sessions

A session is a workstream kind for exploratory work rather than a planned feature: a direct chat with one agent on its own worktree, with none of the rest of the factory around it. A session never runs the shed, the architect, a manager, a mason, a reviewer, the committee or delivery; it never gets a spec, a plan or units; and the scheduler never runs the pre-review check, base refresh or drift-rebase passes for it. The chat is one durable thread and one turn at a time, but a session belongs to a registered project, has a worktree the agent can change, and runs on the profile the owner chose when opening it.

The owner opens a session by naming a registered project and a profile, the same kind the service already runs mason turns on for that project, and may add a title. An unknown project or an unknown or missing profile is refused, and nothing is recorded. Opening records the session's kind, its fixed profile, the base commit (the project's default branch head at opening time) and its branch, and creates a dedicated worktree at that base commit through the same workspace machinery a unit's worktree uses, under the service root and outside the target repository. Sessions appear in the project's workstream list marked as sessions, with their profile and a state of `idle`, `working` or `ended`.

The profile is fixed for the life of the session: opening is the only operation that takes one, and nothing changes it afterward. A resumed backend session belongs to one runtime, so working on another profile means opening another session. The first turn on a session starts a model session on the profile's runtime, which the service records for the session; every later turn resumes it instead of replaying the whole thread, with input limited to the owner's new message plus whatever the service itself recorded since the previous turn, such as a commit or a check result. That model-session state is kept per session under the service root, outside the worktree and the target repository, and survives a restart. If a runtime reports a session's model session missing or unresumable, the turn falls back: it starts a new model session on the same profile, seeds it with the thread's history through the same bounded window a manager turn's replay gets, records the new model session for later turns, and adds a thread entry saying its context was rebuilt from history. A message to an idle session starts exactly one turn; a message sent while one is already running is refused as busy and recorded nowhere, since there is no message queue. The owner can stop a running turn, which is recorded as stopped with whatever worktree changes it had already made kept, returning the session to `idle` for the next message to resume the same model session.

The session's agent runs in a sandbox whose workspace is the worktree, so its changes persist into the next turn, with the same reading, writing and command-running tools a mason's sandbox has. Charter rule 5 still holds: the agent has no version-control access, no delivery credentials and none of the factory tools (`done`, `amend`, `ask`), so nothing it does can commit, check or push on its own. Those become the owner's controls instead. The owner can read the worktree's uncommitted changes against the session head and the branch's commits against the base commit. A commit takes a message, stages every current worktree change onto the session branch, moves the head and adds a thread entry naming the commit; it is refused, recording nothing, while a turn is running, on an empty message, when the worktree has no changes, or once the session has ended, and a retry carrying the same request key, including one that crosses a restart, produces exactly one commit rather than a second. A check runs on the session head, one at a time: it is a smart check, the same smart-check selection a unit's own check run uses, scoped to the changes between the session's base commit and its head, which runs every check, as the pre-review check run does, when Jev is unconfigured or does not select. Either way the service records the commit checked, whether the run was smart or full, with its selected checks when smart, the status, exit code and output, and adds a thread entry summarising the result and naming the commit. Pushing sends the session branch to the project's remote under the session's own branch name with credentials the service holds; it never pushes to the default branch, never forces, and never opens a pull request, and is refused when the remote branch already carries commits the session branch does not. Ending is refused while a turn is running; once a session has ended, its messages, commits, checks and pushes are all refused, its worktree and stored model-session state are released, and its branch, commits, thread and trace stay readable, with the session listed as `ended`.

The owner can permanently destroy an exploratory session, open or ended, or a design session whose marker is still `open` before workgroup start. Destroy removes its dedicated trace (conversation, thread, documents and check records), any worktree, and stored model-session and turn state. It also removes an exploratory session's local `osmia/session/<id>` branch, including unpushed commits, or a design session's one-workstream workgroup entry. It cannot be undone and keeps no archive record, title or tombstone. Pushed branches remain on the remote; destroy never pushes or affects remote branches, pull requests or issues. Destroy is refused without changes while a turn is running or starting, while commit, check, push or end is in progress, or while a design's workgroup start is in progress. Started designs, ordinary workstreams and workgroups cannot be destroyed. Before removing anything, the service records durable removal intent and fences the session against reads, lists, controls and background writes. Startup finishes pending removal before workgroup wrapping, resolution or scheduling, then removes the temporary intent record. See [destroying sessions](running.md#destroying-sessions).

A session must never acquire a spec, a plan, units, a manager or delivery, must never change its profile or run a turn on any other one, and must never replay its whole thread while the recorded model session can still be resumed. The owner opens it and works its commit, check, push, end and destroy controls from the command line (section 11.2) or any API client; the agent's own chat happens only through the web page and the API, never through the command line.

An exploratory agent can attach an image with `show_image(path)`. It reads a PNG or JPEG from the agent's active worktree view during the current turn, including a screenshot written earlier in that turn, and records it in the session's trace and feed. Paths resolving outside the worktree, including through symlinks, are refused. The tool adds no execution grant. Destroying the session removes its images along with its trace; ending it retains them until destruction. Image validation and presentation follow section 11. Owner-to-agent image input is outside this interface.

### 6.9 Flake-fix workstreams

A flake never blocks the workstream whose check run met it (section 5.2). On a project with `flake_fixes` on, the service also records it, tells the manager once per run, and lets the manager open a separate workstream to find and fix the cause. This is the one narrow exception to "work is handed, not mined" (principle 2) and to the manager opening no work of its own (section 2.2); the project's setting is off by default because the workstream's pull requests go out under your name.

The service turns every unit or final-review check run whose record lists a flaky check into flake occurrences, one per flake group, in a per-project flake record in the project's trace. It does so from the durable run records, not from the run's progress, so a restart, a unit that moved on or a final review that finished loses none and repeats none. Session check runs trigger nothing. The originating workstream is never held, gated or given a dependency: nothing it does waits on recording a flake or on a notice. The manager gets one notice for the run that lists each occurrence, split into those awaiting its decision and those that joined a workstream already open for the group. [Flaky checks](smart-checks.md#flaky-checks) describes the groups, the record and the notice.

For an occurrence awaiting its decision the manager calls `flake_fix`:

- `open` reserves the occurrence's decision with the group's hand-in key, has the service write the hand-in from the recorded evidence and the manager's notes, and hands it in through the ordinary hand-in path of the project whose check flaked. The hand-in is an ordinary one: it branches from the upstream base, runs at normal priority, skips no debate, goes through the architect, the committee and your ratification, and needs your delivery approval. It is never pre-ratified. Its records name the manager, not you, as having opened it and name the originating workstream. If the group already has an open flake-fix workstream, `open` adds the occurrence to it and tells that workstream's manager instead.
- `decline` records a required reason. A later flake in the same group notifies the manager again.

The tool is not a general hand-in tool: it takes an occurrence and optional notes or a reason, and the manager cannot add other content or open anything that was not recorded as a flake occurrence. Jev is not asked whether to open; the choice is the manager's, and ratification and delivery stay where they were. Each occurrence has one durable decision, and asking again returns it without acting, including after the workstream it opened was delivered or abandoned and after a restart. A project has at most one open flake-fix workstream per flake group; when it is delivered or abandoned the group's next new occurrence can open the next one with the group's earlier history.

A flake-fix workstream is scoped to the cause of the flakiness, which may lie anywhere. The flaky link is where it showed up, not necessarily where the fault is, and the hand-in requires neither a change to the named test nor a deterministic reproduction. Flakes in a flake-fix workstream's own check runs are recorded but send no notice and open nothing.

## 7. Version control and landing

### 7.1 Fork and upstream

Each repo names an upstream repository, a local clone and an optional fork. The canonical base is upstream's configured base branch. When a fork is configured it receives feature branches and pull requests target upstream. Without a fork, feature branches and pull requests live in upstream. An explicitly identical fork is normalized to omission. The clone needs remotes matching the configured repositories by URL; a single origin remote is sufficient without a fork.

Delivery records the resolved push repository, target repository and base branch before publication so retries preserve the approved destination. Osmia pushes only its feature branches, never the project's base branch or a protected branch, and never merges a pull request. Delivery credentials remain with the service.

### 7.2 Agents hold no tool

Sessions get a plain directory of files. The service performs every version control operation: create workspace, snapshot, rebase, squash, merge, push. A mason improvising a rebase is not acceptable, and an agent that never holds the tool cannot damage history. Enforcement belongs to the execution boundary: agents receive neither VCS tools nor writable VCS metadata nor inherited GitHub credentials. A core profile flag or prompt alone is insufficient. Read-only roles cannot acquire execution or write capabilities through repository-provided tools.

Role execution supports confined host modes (`none` and `claude`), containers,
and Docker Sandboxes (`sbx`). The same scoped files and tools apply in every
mode. An sbx role may select an agent-specific template; provider credentials
and network policy belong to the sandbox proxy, while delivery credentials stay
with the service. The runner allows each service-owned MCP listener's exact
port for that sandbox's lifetime; no global localhost allowance is required.
A sandbox that cannot enforce the requested grants fails the
turn without silently selecting another mode, except that a turn granted
`Web` runs without web tools when only they cannot be held (§9.5). An sbx
role's web fetches follow the owner's sbx network policy; the service adds no
allowed domains for them.
A sandbox outlives its turn only when the service stops during the turn; the
service removes such sandboxes when it next starts.

### 7.3 Workspaces

The feature branch is one workspace on the workstream's repo clone. Each unit gets a workspace of its own descending from the feature branch. Workspaces sit behind one interface with two backends: git worktrees, and Jujutsu colocated so plain git can still read history. Jujutsu adds change IDs that survive rebases, a snapshot on every command so an interrupted session never loses work, stored rather than blocking conflicts, and an operation log the service can restore from. The workflow does not depend on which backend a project uses.

A workspace lasts as long as the work it holds. A unit's workspace is removed once the unit merges, since its work is on the feature branch. When a workstream is delivered or abandoned, the service removes its remaining workspaces: it first commits the files of each unit that did not merge to that unit's branch, so abandonment keeps the work. Every branch stays, so each candidate the trace records remains in the clone. Workgroup dependent repair and approved open-PR rework use the same feature branch through the ordinary workspace loop; retiring temporary workspaces never authorizes deleting the trace. A workspace stays while a turn on it is unfinished or, on a finished workstream, while an operation is pending, and a unit's workspace stays while a replay is in progress in it.

Git worktree creation, removal and pruning share a lock keyed by clone. Other
Git commands on different refs run independently. Each operation has its own
replay scratch worktree, and a fetch that collides with another fetch updating
the same ref retries.

A Jujutsu local step holds the clone lock from its checkpoint through its local
commands and settlement, including any short durable progress write. Copying a
completed turn's files back and snapshotting them is one checkpointed local step;
an interrupted copy is retried from the turn's surviving view before its claim
is released. Fetches,
pushes, GitHub calls, model turns and checks run outside that span. No checkpoint
is outstanding when the lock is released. Cancellation restores the interrupted
step before unlocking; a process crash leaves its checkpoint for startup
recovery. Recovery retains its whole-repository restore semantics, so a completed
step of another operation is always older than the interrupted step's checkpoint
and remains intact. Retries inspect durable progress and branch effects before
repeating local work.

Workspace steps honour the context that runs them. Waiting for a clone lock ends
with the context: the step returns a contention error naming the clone and the
wait before any recovery or checkpoint runs, so the clone's files and
checkpoints are untouched. Commands a step starts stop with its context, with
their process group, and are waited on until they exit. Restoration and
settlement run under their own cleanup deadline, a code constant, and the lock is
released only after every command started under it has exited. A command that
does not exit after it is stopped does not hold the step: the step returns and
the lock stays held until that command exits, so later steps on the clone give
up through the same contention error. A restoration or settlement that fails or
times out keeps its checkpoint, marks the clone as needing recovery and returns
a recovery error. The next step on that clone recovers first and is refused when
that fails, so no work runs on a dirty checkout. `workspace.CloneQuiescence` and
`Jujutsu.Quiescence` report a clone as not quiesced while a started command
runs or the clone needs recovery; a deadline clears neither. A read of a clone
that must reflect what earlier attempts did goes through `workspace.Quiesced`: it
takes the clone's lock, waiting only until the context ends, and recovers any
interrupted step before it reads. A clone that another owner or a surviving
command still holds, or whose recovery fails, is refused with the contention or
recovery error, and nothing is read.

### 7.3.1 Operations that always reach a result

A landing, a rebase and a publication (including a delivery maintenance
publication) never stay in flight without a result. The reconcile controller runs
each Inspect and each Apply of these operations under an attempt deadline of
fifteen minutes, a code constant and not a configuration key. An attempt that
runs into it while the service is still running is recorded as an ordinary
retry whose reason names the deadline; one that gives up on a clone lock, or
whose recovery of the clone failed, is recorded the same way with a reason that
names lock contention or the recovery failure. When an attempt returns it
releases its workflow lane and its `git_operations` permit, even though a clone
lock may stay held by a process that has not exited yet; the next step on that
clone gives up at its own deadline instead of waiting.

Inspection reads a clone's branches only once the clone is quiesced; otherwise
the effect is not yet observable, and the attempt is a retry. A durable outcome
the operation's own code recorded, including one recorded before a restart,
always wins: it completes the operation and is never overwritten.

An operation that has failed five times in a row, the first of them at least
the give-up window ago (45 minutes, the default of `[loop] stall_after`), and
whose inspection finds no durable outcome, is ended instead of attempted again.
The adapter runs a bounded, read-only reconcile under a deadline of its own and
records the result through the operation's own paths: a landing or a rebase
whose commit is already on its target is recorded as done, a publication whose
pull request already shows the approved effect (ready for review, or the draft a
merge-order dependency keeps) is recorded through the same path that delivers it,
and none of them repeats the effect. An effect that is confirmed absent is
refused through the operation's refusal, with the last failure as its reason; a
landing's reason says it gave up after repeated failures, so the router can tell
it from a stale approval. When the clone or the remote cannot be read, the result
says that the outcome could not be determined, never that the effect did not
happen, and nothing more is pushed, committed, updated or marked ready. Each
ending sends the manager one notice. The reconcile asks Jev nothing. A
landing or a rebase also tells the manager once, at its third consecutive
failure; a publication opens its inbox entry then. A refused unit rebase does
not count as done: the foreman asks for it again on a later pass, and once
three rebases of the unit onto the same feature branch commit are refused it
contests the unit instead. A ruling or move that takes the unit out of the
contest gets it a fresh rebase.

`reconcile.StatusOf` reads an operation's failure count, the time of its
first failure and of its latest action, and its last failure reason, which
includes a recovery failure; `reconcile.GiveUpLimit` is the one shared failure
count and window, which the service reads through `Service.GiveUpLimit`.

### 7.4 Landing a unit

On approval the foreman squashes the unit's workspace to one commit on the feature branch with a message generated from the unit's title and the criteria it serves, then rebases every unit still in flight. A conflict goes to a mason session in the conflicting unit's workspace with the sealed spec and the instruction that the tree carries conflict markers to resolve against it. A session never discovers conflict markers by accident. Reviewers never see them.

An approval records the reviewed candidate, its base and the governing spec and plan revisions. Landing first checks that those inputs are still current. If a rebase changes the candidate or its base, that unit returns to checking and review after any conflict resolution and before landing. The foreman never silently transfers approval to a different candidate. The reviewer of a rebased candidate treats the changes the rebase needs, so that both the feature branch's work and the unit's task stand, as in scope whatever the task or footprint names. A resolved path outside the task is not, on its own, a finding. Active file writers must finish or be stopped and snapshotted before their workspace is rebased; the scheduler owns this coordination.

### 7.5 Upstream drift

Upstream main moves daily on a busy project. On a cadence per repo, and on demand, the foreman fetches upstream and rebases the feature branch onto it, then every unit in flight onto that. A rebase that changes what a sealed criterion means files an amendment. The seal moves with the branch.

A rebase that conflicts goes to a drift mason, and a reviewer reads the resolution against the sealed spec. Send-backs are bounded by `max_bounces`, as a unit's are. A resolution sent back that many times, or one whose drift mason or reviewer turn fails or ends without a verdict, holds the drift rebase: the branch and the seal stay, and the workstream takes no further drift rebase, on the cadence or otherwise, until you ask for one or the manager hands it back. A handback asks for the next drift rebase with a note its drift mason and reviewer receive, so the manager can return the work to the role that can resolve it, as it moves a unit. Engineering handbacks remain internal, with budget and loop controls bounding repeated attempts. A drift rebase in progress holds back only its own workstream's landings and drift rebases. Other workstreams can land or drift concurrently.

The drift mason works in its own resolution workspace, which it may read, write and execute in; it has no version control tool, so the service records its work and goes on with the rebase. It may also ask its workstream's manager about the drift rebase it resolves, read factory context, record a discovery, file an amendment citing the drift rebase's upstream commit, and call done. The drift reviewer reads a read-only export of the resolved candidate, with no write or execution capability; it may ask the manager, read factory context, record a discovery, read the diff with `workstream_diff` and record its verdict. Waiting on the manager's answer leaves the drift rebase pending, not held: the wait counts toward none of the interrupted-turn, marker-reminder or send-back limits, and the resolution resumes once the answer arrives, including across a restart. Conflicted paths, and any other change the rebased branch needs so that both upstream's and the feature branch's behaviour stand, are in scope of the drift rebase whatever the workstream's sealed spec, plan or unit footprints name; a resolved path outside the workstream's original scope is not, on its own, a reason to reject it. The reviewer checks that both sides are kept, that nothing of the feature branch's change was lost or altered, that no change goes beyond what the rebase needs, that no conflict marker remains, and that the sealed criteria still hold.

Delivered workstreams with an open pull request retain **Check for drift**. An explicit owner request checks that pull request and runs the same drift rebase and bounded conflict resolution against the sealed spec. Ordinary delivered workstreams receive no cadence-driven drift checks. Workgroup dependency polling still detects merges; merge waits are separate from drift maintenance. A changed branch or base requires a fresh final review and owner approval of the delivery commits and description before the service signs and pushes the branch with its existing remote-tip safety check. Publication updates the existing pull request, rechecking that it is open before pushing. An unchanged branch needs no new approval or push. Requests, conflict resolution, reviews, approvals and publication recover from the trace after restart. The feature stays delivered and no implementation units restart on their own. Blocking findings that need code reopen it through a workstream move to building, with a revision of repair units on the same branch and pull request (section 5.1). A change to approved intent requires a new owner-requested workstream. A merged, closed, archived or owner-recorded-merge workstream cannot take this maintenance path.

### 7.6 Entanglement and dependencies

Two units in one workstream are entangled when the plan makes one depend on the other or their code footprints intersect. Entangled units run in sequence. Workstreams on the same repo can overlap in code entities, even when a workgroup supplies a shared spec, and the foreman warns when both are in the same subsystem before both pull requests are open.

Footprints name entities from the workstream's own repo and resolve through its local entity map even without Hearsay. A footprint entry that names no entity and holds a `/` or a glob character is a raw path glob, validated in Go as an entity path pattern is; it may match paths that do not exist yet, so the first unit of a new repository can name the directories it creates. A unit whose footprint names the `repo` entity overlaps every other unit and runs alone. They schedule work; they do not bind it. A mason changes whatever its outcome needs, and widening a footprint never needs a plan revision. A unit's review does not hold its diff to its footprint: a reviewer who finds the work wandering beyond its task says so as a finding, and a change outside the footprint that the task needs is not one. Unknown or ambiguous mappings cannot be treated as proof of disjointness. Within a workstream the scheduler serializes such units until their footprints are resolved. Across workstreams overlap is advisory by default; the owner can pause or reprioritise the affected work.

A workstream may declare another on the same repo as its base. It then rebases onto that workstream's branch instead of upstream until the base change is integrated upstream. Its dependent pull request is opened in the push repository against that branch. Once the base is integrated, the service prepares an upstream pull request from the descendant's branch, refreshing the affected review and owner delivery approval before publishing it. With a separate fork, the trace retains both requests and their relationship. Without a fork, the service retargets the existing pull request to the configured base branch and updates its approved description after fresh review and owner delivery approval. The operation records the prior request identity and expected contents, reconciles interruptions before retrying, and refuses an unexpectedly edited or closed request. The trace retains both publication records and the request relationship. This is how one large change lands as a sequence of pull requests. Stacking inside one workstream is not supported.

Delivery of a base means its pull request is open, not merged upstream, so descendants continue to use that branch after delivery. Once the base is integrated upstream, the service can rebase descendants onto upstream and publish their upstream requests. For an already delivered descendant, this is a separate delivery-maintenance operation: the feature stays terminal and no implementation unit restarts. Conflicts can use owner-requested drift resolution; changes to approved intent need a new owner-requested workstream. Base relationships must remain acyclic. An abandoned or unavailable base parks descendants for an owner decision; they are never silently moved to another base. A parked descendant enters your inbox. When its own base was abandoned after its changes reached upstream by any route, such as a merge outside the factory, you can move the descendant onto upstream: the service checks that merging the base commit the descendant holds into upstream changes nothing, then records upstream as the descendant's base, and its next drift rebase replays only the descendant's own commits there. Osmia never merges the upstream pull requests itself.

### 7.7 Workgroup edges across repositories

A workgroup graph must be acyclic and name only its member workstreams; invalid graphs cannot be ratified. It may carry contract (the preferred default), hard-block and merge-order edges. Merge is the only release signal. A contract edge resolves on ratification of its workgroup spec. A hard-block edge starts no dependent unit until the upstream pull request merges. A merge-order edge permits both workstreams to build, but keeps the dependent pull request a draft until the upstream merges. The service polls GitHub and also accepts an owner-recorded merge. Agent completion, tags and package versions are not release signals. Workstreams never merge pull requests or push a base branch.

While waiting, roles receive the upstream branch or commit in their file-based context. After its own delivery approval and owner signing, a dependent may publish a draft that states and links every unresolved upstream pull request. If an upstream pull request is not yet known, publication waits instead. Waits are status, not inbox decisions or webhook notifications: for example, `waiting on owner: repo-a#123 merge`.

After a merge, an ordinary unit on the dependent's existing branch updates its dependency reference to the merged upstream commit. The dependent re-runs checks and final review. Blocking findings from that review become one follow-up unit that repairs them within its ratified slice; only a contradiction or extension of the design needs escalation. This does not change the separate same-repo base-dependency maintenance rule in §7.6. The dependent and shared manager retain the ratified workgroup spec and contracts while this work remains pending. Updating the open pull request or marking it ready requires a fresh per-workstream delivery approval and owner signing, never a pre-authorized publication.

## 8. Scheduler

### 8.1 Controllers per state

The service runs one controller per role kind, each reconciling its own input state against the tracker and sharing one pool of slots.

| Controller | Watches | Capacity |
|---|---|---|
| architect | `handed`, amendment requests | one per workstream |
| shed | `in-shed`, amendment rounds | committee members per proposal, `max_shed_rounds` |
| mason | `ready`, `implementing`, conflict resolution | `capacity.masons`, plus a per-workstream cap |
| checks | unit `checking`, final review and session checks | `capacity.checks` across the factory (default 2) |
| reviewer | `reviewing`, `assembled` | `capacity.reviewers` |
| foreman | `approved`, landing events, upstream cadence | one lander per workstream, independent feature branches land concurrently |
| manager | every member's outbox and your messages | one turn at a time per workgroup; background turns share `capacity.manager` across the factory (default 3), your messages take no slot |
| archive on merge | `delivered` workstreams whose own pull request outcome is recorded `merged` (section 5.1) | no model turn, no pull request lookup |

### 8.2 Level-triggered

Controllers reconcile against the current state. Events only wake them early. A missed event costs latency and never correctness. Crash recovery is restart, re-read state, resume. A turn that was running when the service died is found by its session directory and its thread is given a turn saying so.

Each project also runs a conversation path alongside reconciliation. It owns manager turns, shared workgroup managers, design conversations and exploratory sessions, including background event, answer, contest, amendment and follow-up turns. Enqueuing a turn wakes this path directly. Every few seconds the path also reads the follow-ups of the manager threads it owns from records, queues the turn of each that is due and schedules the check-back of each completed turn on a stall notice that did not end its quiet (section 6.6). It durably dispatches the oldest unfinished turn per thread, reconciles captured replies without another backend call, and settles completion hooks before admitting the next turn. Hooks can run again after errors or restart and deduplicate each durable effect. Conversations take no workstream workflow reservation and no mason, reviewer, committee or check slot. Background manager turns, meaning event, follow-up, check-back, contest, amendment and answer-delivery turns on a workstream's manager thread or a shared workgroup manager's thread, take a slot from the factory-wide `capacity.manager` pool (section 8.4); turns you start, meaning your messages and replies and design or session conversations, take none and never wait for one. Manager turns ignore owner pauses while abandonment, joining fences and provider limits remain in force. Queued conversation entries expose a reason naming an earlier turn, “waiting for a manager slot” or “starting”. Shutdown joins the conversation path before closing its traces.

Workflow operations run beside the reconciliation pass, one at a time in each workstream. This ordering covers architect drafts, shed replies and redrafts, amendment drafts and replies, final reviews, seal, build, land, rebase, drift and publish. Different workstreams may run these operations concurrently. Mason, reviewer and committee turns and check runs retain their scheduler order and capacity; they do not reserve the workstream's workflow ordering. Conversations follow only thread order. When an operation's workstream is busy or its kind's capacity is full, admission leaves it pending and scans other eligible operations without waiting.

| Lock | Covers |
|---|---|
| Thread | Turns in oldest-first order, including completion hooks |
| Workstream | Workflow operations only |
| Repository clone | Git worktree creation, removal and pruning, including scratch worktrees; local jj steps |
| Shared documents | Existing short entity map, charter, workgroup approval and change writes |
| Project trace | Short bookkeeping writes; no model, Git or GitHub call |

Each replay has its own scratch worktree. Git operations on different refs proceed independently; fetch retries shared-ref collisions. A jj local step opens and settles its checkpoint within one hold of the clone lock, so recovering an interrupted step preserves other completed operations. Fetch, push, GitHub and model calls run outside that lock and checkpoint.

Landing is per workstream: it waits for that workstream's unit rebases, and advances its own feature branch. Independent landings may run concurrently. The factory never writes upstream. Repository operations and remote polls share the project's `capacity.git_operations` limit, default 4. Polls bypass workflow ordering; scheduling steps consume their recorded evidence. Scheduling steps, operations and lock waits exceeding the diagnostic threshold log their project, workstream where applicable, step or operation or lock, and duration. Shutdown drains all operations and observers before closing traces.

### 8.3 Finish before start

A freed slot is offered to review before implementation, implementation before debate, debate before drafting, so the factory finishes work rather than widening it. Within a stage, the slot goes to the highest-priority workstream with something ready, and round-robin breaks ties across workstreams and projects.

### 8.4 Capacity, priority and pause

Model-session slots are also bounded per client: each client's one slot count is a second limit next to the role limits below (§8.5).

Check runs share a separate factory-wide pool, configured by `capacity.checks`
(default 2). Unit, final-review and session checks take a slot before selection
and Dagger work, across every project and workstream. Runs wait cancellably in
arrival order when all slots are occupied; waiting consumes no `checks_timeout`
budget and records no incomplete run. Every exit releases its slot. Check slots
do not count against mason, reviewer, committee or per-workstream limits, and
waiting leaves other work free to dispatch. Reload resizes the pool for new
admissions while executing runs finish; restart begins with no slots held.

Background manager turns share one more factory-wide pool, `capacity.manager` (default 3), which bounds how many run at once across every workstream and project, so a notice sent to every workstream starts at most that many manager sandboxes. A background turn takes a slot when it is admitted and every exit releases it: completion, failure, interruption, abandonment, shutdown and a turn that ends `waiting`. A turn that finds the pool full stays queued in its own thread, in order, with the reason “waiting for a manager slot”, and later turns in that thread stay behind it. Other projects' conversation paths, your own turns and all other work keep running. A freed slot goes to the oldest eligible waiting turn across the whole factory, whichever project it belongs to. A waiting turn is eligible when it is the oldest unfinished turn of its thread and no gate other than the pool holds it; a turn held by thread order, a provider limit, abandonment or another admission rule does not block younger eligible turns, and a later arrival never takes a slot ahead of an older eligible waiter. Your turns take no slot, with one exception: when you message a workstream whose oldest unfinished turn is a background turn waiting for a slot, that turn runs at once without one, holding none, so finishing it frees none, and your message follows straight after it in thread order. A background turn already running ahead of your message finishes first. The pool can therefore be exceeded by one turn for each workstream you are messaging; no other background turn runs without a slot, notice waves and turns resumed after a restart included. Manager slots do not count against mason, reviewer, committee, check or per-workstream limits. Reload resizes the pool for new admissions while running turns finish; restart begins with no slots held, and the interrupted background turns and the continuation turns recovery gives their threads queue for slots like any other background turn.

Capacity is per role kind and global across every workstream on every project. A per-workstream work-in-progress cap keeps one feature from taking everything when it is alone. No repo reads another repo's trace to share a limit: each repo's passes count the slots it holds, the turns waiting for one and the day's spend from its own trace and publish them to the service, which enforces the shared limits and reports capacity and the daily budget from what the projects last published. Each project's conversation path likewise counts the manager slots it holds, and the service admits background manager turns against the total across projects under one lock, so projects admitting at the same moment never hold more than `capacity.manager`. A published total follows each project's next pass, so it can briefly overstate a slot that was just freed, never understate one in use.

Model workflow operations reserve their role's slot before inspection and keep it through result recording. Final and delivery reviews run no check, so they take no check slot. Each attempt reserves its committee slot at admission and keeps it through the reader turn and result recording; an attempt that finds the pull request's Dagger Cloud statuses not ready ends at once and returns it, and the next attempt waits for its time like any retry. Their runner threads use that reservation rather than taking a second slot, and leave the per-workstream allowance for worker turns available. Final reviews share the committee limit with committee turns. The architect retains one runner per workstream, without a global role limit; the capacity view reports their active counts alongside the globally bounded roles.

Active workstreams have a priority order you set, or ask the manager to set. A paused workstream, project or factory dispatches nothing new. Turns in flight finish, and a hard pause stops them too. Paused units stay where they are, their slots go to what is not paused, and resume picks up with nothing to reconcile. The manager stays reachable while everything is paused, so "pause everything, I'm travelling" and "resume dagger only" are messages. Pause state persists across restart and is shown with who set it and why: you, the daily budget, a provider's usage limit, or the loop guard.

### 8.5 Clients and placement

Model sessions run on clients. The service's own machine is the built-in **local client**, and any other machine on the tailnet joins by running `osmia client --server <url> --slots <n>`, which connects out to the service's tailnet API and takes turns from it. With no other client connected, and `capacity.local_slots` unset, every session runs on the local client, in this process, and scheduling and turn behaviour are what they are without clients: each turn is recorded as run by the local client, and nothing else changes.

*What stays on the service.* The trace, scheduling, every git write, every capture and delivery, the service's own Dagger check runs, pull-request watching and all telemetry. A client only runs model sessions, for any role that runs one: masons, reviewers, committee members, architects, the manager and design sessions. Service check runs and pull-request check watching are never sent to a client. A client writes no trace record, holds no trace store, has no `[telemetry]` configuration and exports no span; the service writes every record and emits every span for a remote turn from what it holds: the turn request, the relayed tool calls, the heartbeats and the returned result.

*Identity and trust.* Tailnet membership is the only trust: there are no tags and no enrollment. A client is identified by its tailnet node's stable identity, which the service uses to place work, to show the client in status and to record it in the trace and on its spans as an allow-listed attribute. It never refuses a client for who it is. One client runs per node: a second connection from a node is refused while that node's first connection holds a lease. Clients connect out, and the service never needs a client's address. The protocol is versioned, and the service refuses a client whose protocol version differs from its own, naming both versions.

*Credentials stay on each machine.* A client runs sessions with its own machine's model-provider login (`sbx login`, `sbx secret set`) and its own Dagger engine or Dagger Cloud setting. The service never sends a provider key, the Dagger Cloud token or any other secret to a client. A missing provider login is not checked in advance; it shows as a failed turn, which status ties to the client it ran on.

*Profiles and capabilities.* When a client connects, and again after every reload, the service sends it its profiles and what each role needs: backend, model, sandbox mode, image, size, domains, skills and, for masons, the Dagger mode and version, without secrets. The client checks each profile with the tool checks `osmia doctor` runs (the backend's `--version`, `sbx` or the container engine, `dagger`, and that the skills can be fetched) and reports what it can and cannot run, with the fix for each missing item. Clients have no profile settings of their own. The service sends a client only turns whose main profile it reported it can run; on that client, a fallback profile it cannot run is skipped, and status shows the skip. A client that can run nothing stays connected and takes no turns, with status saying why, so the machine can be fixed without restarting anything.

*Capacity.* The `capacity.*` limits per role stay factory-wide ceilings across every client. Each client declares one slot count, usable by any role. A turn starts only when its role has room under the ceiling and the client it is placed on has a free slot. The local client adds no cap beyond the ceilings unless `capacity.local_slots` gives it a count, and `0` runs no session on the server's machine, which makes the service a pure control plane while it still runs checks, captures and deliveries.

*Placement.* New turns go round robin over the connected, non-draining clients that have a free slot and can run the turn's main profile. The local client has one place in the rotation, as does every client however many slots it has, so a bigger client fills up later and is not picked more often; placement never weights clients by size or speed and never prefers a client that can run a whole fallback chain. The role ceiling is checked first, so a turn it holds back does not advance the rotation. A turn that resumes a thread's saved session, whether a follow-up, a bounce-back, a resume from another workstream, a hill climb or any other resume, goes back to the client the trace records as holding that session, for as long as that client is connected, the lease's grace window included. It waits for a slot there and holds no role slot while it waits; both limits are checked when it starts. When a slot frees on a client, the turns waiting for that client take it before any new round-robin turn. When the session's client has lost its lease, is draining or is the local client with no slots, the turn is placed round robin and the thread replays its own log, the fallback that already exists. The trace records the client that ran each turn and the client that holds each thread's session, so pinning survives a restart.

*Files.* A turn starts from a commit and ends as a new commit recorded by service code, and the agent sees only a directory of files with no `.git`. A remote client therefore needs only the turn's files, a relay for its tools and a way to return the finished files. The service serves each registered project's clone through a read-only git route on its tailnet API, which allows a fetch, including a turn's starting commit, and refuses a push. A client keeps a cached clone per project, fetches the starting commit incrementally and exports the selected paths into a view built as the service would build it. A view built from trace documents, which is not in git, goes to the client as an archive, and so does a mason's view under the Git workspace backend, whose unit workspaces keep a turn's starting files in the worktree rather than in a commit; under Jujutsu every turn starts from a recorded commit that the client fetches. The finished view comes back as an archive, and the service records the commit through the capture path a local turn uses, with the same content for the same files. An archive with an entry that escapes the view root is refused and records nothing.

*Tools.* The client opens a local MCP listener for the sandbox, so the sandbox's network rules are the ones it has today, and forwards each call to the service under the turn's own bearer token. The service handles, authorises and audits each call as for a local turn. The tools that act on the turn's view or its role's skills (`file_read`, `file_write`, the view tools and absolute skill reads) are carried out on the client's view and the client's own prepared skills, through requests the service queues for the client to collect, under the same path rules and never against a copy on the service: a read returns a file as the session last changed it, and a write is seen by the session and is in the returned view.

*Leases and reattach.* A client holds a lease for its connection and keeps it with heartbeats that carry each running turn's progress, which feeds the activity registry, so live status and stall detection work for remote turns. When the connection drops or the service restarts, the client keeps its sessions running for the lease's grace window of about two minutes and reattaches them by turn ID, and each turn finishes and is recorded once. After a restart the service holds the turns it recorded as running on a client for that window, hosts their tools again and gives the client a new token. Past the window the client cancels its sessions, keeps each mason's view and any unsent result on disk and keeps sending them until the service answers.

*Lost clients and late returns.* When a lease ends, the service waits a bounded time for the view the client returns, then starts the existing recovery of an interrupted turn, from the returned files when they arrived and without them otherwise. A lost client adds no owner gate. Every result and view names its turn, and the service answers each definitively: accepted, already recorded or superseded. A view or result that arrives after recovery began is not captured and never overwrites work recorded since; the service answers it superseded and records that it arrived. A return sent again, after a lost acknowledgement or a restart, is answered already recorded and records nothing new: each turn records at most one outcome and at most one commit from its returned view. The service stores a returned view and a returned result on disk, flushed, before it answers accepted, and a restarted service rebuilds an unfinished turn from both and records its original outcome once, so a client never discards a return the service could lose.

*Drain.* The first Ctrl+C or SIGTERM on a client starts a drain: it takes no new turns, keeps its connection and heartbeats, lists the turns still running, waits for them to finish and send their results, then exits, while the service marks it draining and uses none of its free slots. A second Ctrl+C cancels the running sessions and still sends each mason's files, as a lost connection does, and the existing recovery picks the work up.

*The command.* `osmia client` takes flags only and reads no configuration file. It runs in the foreground, on Linux and macOS: there is no background or detached mode, asking for one is an error and Osmia ships no unit file for it; the owner keeps it running with the machine's own tools. See [running](running.md#client-machines) for setting a machine up.

### 8.6 Cost, retries and degradation

A per-session cost cap protects the infrastructure. A per-unit cost is a signal: passing it files an amendment request saying the unit is bigger than planned. A daily budget across the factory pauses dispatch when reached.

Nothing the service repeats on its own repeats without a bound. Send-backs, clean turns, rounds and drift resolutions have their limits, and so do reviews the service refuses as stale, check runs that do not complete, reminders to remove conflict markers, continuations of interrupted turns and redelivery of notices the manager's turns keep failing on. Final reviews are bounded too: once three have found something blocking, further revisions of the assembled plan are the owner's. Each limit ends in a decision someone can take: a contested unit, a held drift rebase, an amendment in your inbox, or notices held until you message the manager. A manager's recovery instruction does not count as progress. Behind them all, the loop guard watches each workstream for sessions without progress, meaning a change of state of the feature, a unit, the shed, an amendment, the final review or the publication, a drift rebase that moved the branch, or anything you did. A workstream that runs `loop.max_sessions` of them pauses with the loop guard as its source and enters your inbox, and resuming it starts the count over. Failures are classified as infrastructure or behavioural: infrastructure failures retry, then fall to the profile's fallback; behavioural failures are outcomes and go back into the state machine. Streaks of failures show in the status so broken plumbing is visible rather than silently expensive.

## 9. Agents

### 9.1 Durable threads

An agent is a persistent, resumable thread: an id, a role, a workstream or shared workgroup scope, a backend session id, an owned message log, and at most one active turn. A process runs only while a turn is in flight and is recovered automatically. Messages to an agent are turns, whether from the scheduler, the manager or, for the manager, from you. A message that arrives mid-turn queues as the next turn.

Durable threads are why a reviewer remembers what it found last round, a committee member argues round three better than a debate record could tell it, and a mason that asked a question picks up where it stopped.

### 9.2 The owned message log

Every turn's request and final response is captured by the service, per agent, in `agents/<id>/log.jsonl`, with provenance: what caused the turn and at what depth. The service does not read the agent binary's own transcript files. Their schema is unofficial and versioned, and owning the log is what makes a thread survive a profile switch: when the next turn cannot resume the backend session, it starts a fresh session with a bounded replay of the owned log. manager event and owner conversation turns also receive a project briefing with governing rules and decisions, references to the retrievable entity map, latest stored status and open inbox escalations, so durable context remains available when bounded replay omits the tool calls that recorded it. One capture path per backend, since each exposes turn results differently.

### 9.3 Profiles

A profile names an agent binary, model, effort, optional fallback profile, timeout and turn limits. The `fallback` setting refers to another named profile, so a fallback can change the model or the agent binary. Unknown references and fallback cycles are configuration errors. Roles bind to profiles in configuration, and the committee's members may each be assigned a profile of their own. The binding can be overridden per role while the factory runs, from the web interface or the command line, effective for every new turn on every workstream. Turns in flight finish on the profile they started with. A switch that stays on the same agent binary resumes the thread as it is. A switch across binaries starts the next turn fresh from the owned log.

When the service sees a provider's usage limit, the role falls to its profile's fallback automatically and the status says so. A manual override wins either way.

Provider limits persist in `runtime.json` by agent backend. New turns of roles bound to a limited backend use the first profile in their fallback chain with an available backend. A role with no available fallback is paused with provider attribution. A reported reset time releases the limit when it passes; the owner can also clear a limit with `osmia profiles clear-limit <backend>`. A limit without a reset time remains until cleared. An owner profile override takes precedence while a limit is active.

One limit is not a provider's. Every sbx sandbox is created from a kit that `sbx` resolves from Docker Hub through the machine's one Docker account, whatever the agent backend, so when Docker Hub refuses a create for its pull rate limit the turn reports a registry limit instead of an infrastructure failure to retry. It is kept under the key `sbx` for ten minutes, since Docker Hub reports no reset time. While it holds, every role whose sandbox is sbx is paused with the reason "Docker Hub's pull rate limit", whatever its fallbacks and whatever profile override it has, because every fallback's sandbox would make the same request; the failed turn tries no fallback for the same reason, and is otherwise treated as a usage-limited turn with no fallback. Roles outside sbx are not affected. `osmia profiles clear-limit sbx` lifts it early.

### 9.4 What a session sees

A session receives a scoped plain-file view with the Osmia MCP server and a bundle. A mason works in a disposable writable copy; the service captures its changes into the unit workspace. A reviewer receives a read-only export of the exact candidate commit and separate writable scratch space. A reviewer's next turn replaces its export, and the export is discarded when the unit merges or the workstream finishes. Session records and authoritative repositories remain service-owned. A workstream's session directories, including each agent's own transcript, last until it is delivered or abandoned and its turns are done; they are then removed with its workspaces, and its trace keeps every turn's request and final response. It additionally receives a Hearsay MCP server when that integration is enabled and available.

### 9.5 Sandboxes

A role runs on the host or in a container, per profile. In a container the workspace is bind-mounted and the MCP servers are reached over HTTP from the host. Native tools follow role capabilities: reading tools for read-only roles, editing tools for file writers, and a shell only for implementation turns with execution permission. Native delegation and arbitrary MCP discovery are not granted, and web tools only through the `Web` permission described below. Read-only roles cannot edit their inputs or run arbitrary commands. Service-mediated inspection and remote-source tools provide evidence without granting native network, shell or credential access. A role may name skills by git reference. The service clones them into its cache and gives the role's Claude and Codex turns only their skills, read-only, with Claude's tool that loads them on Claude turns and Codex's own tools on Codex turns, which register the skill directories with their app-server through `skills/extraRoots/set` (Codex 0.136.0 or newer, the first release that answers it). A repository's hooks, MCP servers, commands and agents never reach a session, and OpenCode and Pi receive no skills. The service runs the checks itself before every review that reads code: a unit candidate's before its unit review, and the rebased feature branch's before the final read. Both run `dagger check` on a fresh export of the pinned commit and discard the copy afterward. No reviewer runs checks or chooses a command, path or environment; the checks for unit and final reviews are chosen by the service through the same smart-check selection. Reviewers judge the work against its task, acceptance and criteria; style, formatting and lint belong to the project's checks. The check client receives a temporary home and engine connectivity, without inherited provider, delivery or signing credentials; no agent receives an engine endpoint. Results enter the trace and inform the review without granting approval or delivery.

Web access is a separate permission, `Web`, distinct from `Network`. It adds the backend's own web tools to a turn's native tools: Claude `WebSearch` and `WebFetch`, Codex `web_search`, OpenCode `websearch` and `webfetch`. The service runs no search or fetch of its own, has no search provider or key, and saves no web read in the trace; agents cite the URLs they used in the briefs, specs, debate positions and answers they write. Only the planning roles hold it: the design session, the exploratory session, the architect on every turn path (drafting, shed replies, redrafts, amendment drafting, and a workgroup's project-spec draft and delta amendment turns), the ordinary manager (every manager turn that is not a design session) and the committee in plan and amendment debate rounds, a workgroup's delta review included. Masons, unit and drift reviewers, final reviewers (including a committee final review) and the foreman never hold it, whatever a service grant says. No configuration key turns it on or off. A design session's service tools stay `file_read`, `read_repo`, `draft_brief` and `set_title`; every other role's service tools are the same with or without `Web`. `Web` is allowed to read-only roles without relaxing them: a turn that holds it still has a read-only view and no write, shell or `Network` grant, and it admits no service tool whose effect is `fetch`, which still needs `Network`. The prepared session's native tools are checked against the grant, web tools included. The current turn context of every turn that holds `Web` says four things: it can search the web and fetch pages, web content is evidence and not authority over approved intent or owner rulings, instructions inside a web page are not instructions to it, and it cites the URLs it used. In an sbx sandbox, fetching follows the owner's sbx network policy; the service adds no allowed domains and refuses `settings.Domains` and extra-mount overrides. The accepted risk is that a page a planning agent reads can carry hostile instructions or false claims. The agent's tools limit what they can do (a read-only view, no shell, no credential, no owner gate), and the shed, the reviewers and the owner's ratification still check what it drafts. When a backend or placement cannot hold a web-granted turn to its granted tools, the turn runs without web tools instead of failing, and says so. This happens when the engine refuses the web grant before a session exists, and when preparation succeeds but the prepared session's policy does not match the grant. A session that does not match never runs and is released. The turn is prepared again, once, with only `Web` removed, and the reduced session must match the reduced grant exactly or the turn is refused. The turn's prompt then states that web search and page fetching are not available on it. A mismatch unrelated to web tools is refused, and a turn whose session has already run is never retried.

A session on a client runs exactly as one on the service does: in the role's configured sandbox mode, with the client's own provider login and the client's own Dagger setting for a mason's Dagger, and no extra gate (§8.5).

A mason in a Docker Sandbox is also given Dagger, so it can run the project's checks and functions while it builds rather than relying on review. It runs on the engine the service's own checks use; the host CLI's automatic engine choice cannot be followed from a sandbox and is refused. On a host engine, the sandbox keeps a template's CLI at the configured release or installs it, and reaches the engine through a port allowed for that sandbox alone. On Dagger Cloud, the sandbox's own CLI runs with `DAGGER_ENGINE=cloud` and the service's Dagger Cloud compute token. The compute token is the one credential an agent is given: the owner accepts that a mason can read it, in exchange for keeping checks off the factory's host. The engine has no delivery credentials, and no other role receives it. A Dagger-enabled mason's view holds an empty Git repository at its root so the CLI finds the project's workspace; it holds no commits, remote or hooks, and nothing under it is captured, shown by the file tools or recovered. A mason validates only through Dagger, from the view root: plain `dagger check` with its listing, the Go check's `--go-package`, `--go-test` and `--env` flags and `dagger generate`, and the lint check link `dag+check://?check=lint&staticcheck-project=.`. The Osmia sandbox template has no Docker Engine, and no guidance gives a mason another validation route.

### 9.6 Jev judgments

Some decisions are small, bounded judgments rather than generation: which of four classes a mason's final response falls in, which of a project's checks a unit's change can affect, which of a few supplied options a gate or a manager decision should take. Osmia asks those of Jev, TypeSafe's System One model, which takes textual state and typed questions and returns typed answers with probability distributions: a Choice selects one supplied option, a Score rates against supplied levels, and a Noul is the probability that a proposition holds. Larger generative models remain responsible for implementation, planning, explanations and review. Jev is the decision maker for the bounded decisions listed below: where it is confident its pick is the decision, not advice about one.

Jev is required: no setting turns it off. The service starts without Jev's API key, in which case Jev is unconfigured, `osmia doctor` fails its Jev check and every judgment falls back. The service reaches Jev through a TypeSafe-compatible API, OpenRouter by default, with a credential referenced through an environment variable that no session receives. Jev holds no tool, no version control and no delivery credential; a judgment sees only the state its question needs.

Every judgment has a supported fallback, which is the workflow as it runs without Jev's answer. A judgment falls back when its credential is missing, the provider times out, is rate limited, unavailable or refuses the request, the response does not answer the questions in the shape they require, or the judgment's own acceptance, such as a confidence threshold, declines the answers. Thresholds are per judgment and tuned against a pinned model version; the check selection's is a global Jev setting, 0.5 by default, every decision's is one global `[jev] decision_threshold`, 0.9 by default and valid in (0, 1], except the owner's own decisions (below), whose is `[jev] owner_threshold`, 0.9 by default, valid in (0, 1] and independent of `decision_threshold`, and the others are fixed in code. Confidence is derived from the answer's distribution and is never treated as a verified probability of being correct. Requests are bounded by a short timeout and at most one retry of a transient failure. A rate limit, or repeated outages, cools every judgment down together, so an outage falls back at once rather than producing a retry storm.

Judgments run inside turns, inside the service's check runs, or in a gate worker of their own, never on the scheduling path and never on an inbox, status or open-decision read. A classification or check selection is advice to the code that asked. A decision judgment is different: a pick at or above its threshold is the decision, recorded as the ordinary record of its kind and carried out through the path an owner's command or the manager's tool takes. No answer bypasses an outcome tool, a reviewer's, the committee's or a final review's verdict, service-owned version control, or the rule that Jev writes no text (below).

**Owner gates.** Five kinds of owner gate are put to Jev, each with its own task name and version and only the options the gate lists: a ratification (ratify), an amendment that changes approved intent (approve or decline), an escalated question (the options the manager wrote), and an escalated contested unit or escalated blocking objection (the options their cards offer that need no text of the owner's). The judgment starts when the item reaches the gate, in a worker of its own beside the scheduler, with the state the card or packet shows: the records, the packet, the rulings, the charter, and the manager's write-ups and evidence. Jev reads no code. One slow or hanging judgment delays only its own gate. At or above the decision threshold the pick is recorded as the gate's decision with Jev as its actor and a link to the judgment, carried out the way the owner's command would be (a ratified workstream is sealed and built), and relayed by the manager the way it relays your ruling; no card waits in the inbox. Below the threshold, on a deferral or on a fallback, the card goes to the owner, its recommendation is Jev's pick with its confidence when Jev gave one and the manager's own only when it gave none, and the card is not judged again while it waits. If you decide a gate first, your decision stands and Jev's result is not applied. If the service refuses the transition a confident pick calls for, the item goes to your inbox carrying Jev's judgment and Jev is not asked about it again.

A gate is finished only when its decision has been carried out or you have it. After a restart the gate worker visits every reached gate that is not finished: with no result it judges, with a confident pick recorded but not applied it applies that same pick once with no new request, with a Jev decision partly carried out it finishes carrying it out, and a card that already went to the owner or a gate the owner decided is left alone.

**The owner's own decisions.** Six more kinds are the owner's own decisions, put to Jev through the same gate worker with their own task names and versions and only the options their cards offer: the delivery card (approve: **Mark ready for review**, **Accept findings and mark ready for review** or **Update pull request**), a charter proposal (ratify the rule the manager wrote, or decline it), a conflict between projects' charters (the options the manager wrote for the escalation, or dismiss or overrule for the committee objection), an architect's escalation such as "this project needs no change" (the options the manager wrote), the impact summary of a cancellation of a workgroup or a member (approve and close the open pull requests, approve and leave them as drafts, or reject), and the owner's own objection at the ratification gate (dismiss or overrule). A pick of these is binding only at or above `[jev] owner_threshold`; the five owner gates above keep `decision_threshold`. A binding pick is recorded as the decision with Jev as its actor and carried out through the owner's own path: a delivery approval pins exactly the review identity the owner's approval sends (the final review, its revision, the reviewed commit and the draft's hash), publishes the presented text through the same marking, and the commits stay signed and pushed under the owner's identity and key. Below the threshold, on a deferral or on a fallback, the card reaches the owner with Jev's pick and confidence as its recommendation. A cancellation recorded in a cross-repo workgroup's own trace stays the owner's. While Jev is unconfigured these decisions are not put to it at all and record no fallback. The manager's `decide` refuses these subjects: the manager never takes them, and the gate is where Jev decides them.

**Delivery route.** The delivery of a workstream on a project whose `delivery` is `jev` is a sixth owner gate, the `delivery-route` decision, with the options `land`, `pull-request` and `defer`, keyed by the workstream, the final review round and the pushed commit and judged against the decision threshold. Jev is asked only when the delivery is clean: the project delivers through its own upstream, the final review left no blocking findings, checks passed on the exact pushed commit, and no hard-block or merge-order dependency still waits to merge. Otherwise the route is not asked, and the "Mark ready for review" card appears and is put to Jev as the delivery approval at the owner threshold, exactly as on any other project. Its state holds only what the card shows: the spec summary, the final review report, the check results, and the number of files and lines changed with the entities they touch. It holds no code and no diff. A confident `land` calls the landing entry point of section 5.5 as a fixed router move with Jev as the deciding authority: a refused push is delivered as the draft marked ready, a held move is applied once the hold clears, and neither raises an owner card. A confident `pull-request` marks the existing draft ready. A pick below the threshold, a deferral or a fallback leaves the draft a draft, and the card offers "Mark ready for review" with "Approve and land" beside it, showing Jev's pick as the recommendation. Only when the service refuses to apply a binding pick, before anything is pushed, does the card go to the owner with Jev's judgment, and Jev is not asked about that delivery again. Jev's answer about a state change never crosses the delivery gate.

**Jev writes no text.** An option that is carried out with text is offered to Jev only when the manager already wrote that text: an escalation's options, the manager's drafted rule for a charter proposal, the presented pull request description. An option whose text the manager has not written, such as sustaining an objection, revising a contested unit with the owner's direction, editing the delivery description, or abandoning at ratification, is never offered, and a decision with no such option left produces no request and keeps its route to you.

**One decision per subject occurrence.** Each decision judgment is about one occurrence: a specific ratification of a specific set of drafts, an amendment, a question, a contest (a unit contested again is a new contest), an objection, a discovery, a blocking finding of one final review, a delivery card for one final review, revision, commit and draft, a charter proposal, or a cancellation's impact summary at the revision it was presented. A confident pick is kept and returned without a new request whenever that occurrence is asked again, after a restart and when the request's text, options, model or threshold changed since. A pick below the threshold is that occurrence's nonbinding result: it supplies a card's recommendation and is never enforced. A fallback is not a decision; it is recorded with its reason, never returned as Jev's, and a later ask for a pending occurrence asks again.

**Records and labels.** A decision Jev makes is the ordinary record of its kind (a ruling, ratification, amendment decision, contest resolution, objection decision, discovery disposition, triage, delivery approval, charter decision or change decision) with Jev as its actor and a link to its judgment, never a new record type. Status, the API and `docs/openapi.json` expose the actor; the command line labels those decisions "decided by Jev". The feed and `osmia trace` label a state change "decided by Jev" only when Jev departed from the default next state, so a gate decision Jev applied as it was authorised shows nothing extra. Hearsay posts a decision whose actor is Jev on the work source with no owner author, never as your ruling (section 12).

**Transition routing.** A state change of a routed machine does not name its own next state. The caller raises an exit to the transition router: the trigger, the default today's code would take, the legal targets with a line on each, the evidence and the authority the exit carries, if any. The router keeps the targets that pass the hard prerequisites (a candidate exists, for the targets that need one; no landing, rebase or publication in flight; budgets and pauses; merged only after a landing). `approved` is a target only on an exit that carries a satisfactory reviewer verdict for the current candidate or an owner decision, and an owner gate (ratification, delivery approval and publication, abandonment, a unit approved without independent review, an intent change) only on an exit that carries an owner decision or one of Jev's existing gate decisions; a manager's move and a `decide-transition` answer carry neither. An exit that carries an owner decision, a gate decision of Jev or a manager's move or ruling is a pinned move: the router checks the prerequisites, commits exactly that target with its shared effects, records the authority as the transition's `decided_by` (`owner`, `jev_gate` or `manager`, which the trace stores as `chief_of_staff`) and sends no request. The manager works outside the loop the router runs, so its decisions are never judged; a manager move that names an owner gate or `approved` is refused that target and waits as a pending owner decision.

Every other exit with at least two legal targets sends Jev one `decide-transition` request (a versioned task on the decision pattern) holding a summary built from records only and capped at 72 KiB, with every count and duration computed by code, and these narrow questions, answered in parallel: whether the default fits, which target fits (asked twice, with the options in two orders), whether the subject is stuck, whether acting would change approved intent, and the trigger's own questions. A versioned table in code, which the transition records with the row that chose it, turns the answers into the next state: the two orders disagreeing holds the subject; a pick that is the default, or a default judged to fit, commits the default; a way forward that would change intent goes to the owner; and a pick commits as a departure only at or above its bar, which is a modest 0.7 for a retry or a send-back and the global `[jev] decision_threshold` for a redraft, a reopen, another debate round, a return to delivered and a dropped dependency, and only when the trigger's own answers corroborate it. A hold moves nothing and sends the manager one notice for the occurrence with Jev's view; an unresolved hold becomes a stall. With one legal target the router keeps the default itself and asks nothing.

The router waits for Jev where the transition is committed today, up to Jev's timeout; an exit raised on the scheduling path is handed to a worker, and Jev is never called on that path. A request that fails (a timeout, a cool-down, an outage, a request too large) commits the default, marks the transition and the route span `fallback`, and shows Jev as degraded in the status; a failed request never blocks a transition. Each occurrence, an exit's subject, state version, trigger and the record that raised it, is asked once, its asks serialised, and its answer is reused after a restart; a pick recorded but not applied when the service restarts is applied on recovery: the service rebuilds the exit from its route record, checks the hard prerequisites again and applies it with no request, and an exit its machine cannot rebuild is finished by the pass that raises it again. Every target is checked against the hard prerequisites again when it is applied, whoever chose it (a Jev pick, a degraded default, a recovered pick, a manager's move, a pinned decision, a card), since a budget or an operation can change without the subject's state version changing. A target that has become illegal, or whose effects cannot be carried out, records `Refuse` on the judgment, commits nothing, runs no effect and leaves the subject held with one notice. The transition records `decided_by`, the judgment and the default it departed from, and each exit sends one `osmia.transition.route` span. A target's side effects (a mason's fresh allowance, a fresh check run or review, the approval record, notices) are defined once in a shared registry and are the same whoever chose the target.

**Unit exits.** Every state change of a started unit is an exit of the unit machine: a mason's report (`unit.mason_done`), a mason turn that ended clean, a turn that failed or was interrupted again and again, a check run that passed, failed or did not complete, a reviewer's verdict (`unit.review_approved`, `unit.review_rejected`), a review the service refused or that ended without a verdict, a unit sent back to its checks, a rebase that left conflicts, rebases of a unit that kept being refused (`unit.rebase_refused`), a rebase or a landing that was recorded, a landing that was refused (`unit.landing_refused`), a question the unit waits on, the owner's moves and rulings and the manager's moves and rulings. Each caller supplies its trigger, the state today's code would enter (the default), the targets the trigger can enter, and the records of the trigger. The default is entered with its usual records and reason, and its transition adds `default_to` and `decided_by`; any other target, however chosen, is entered through the shared effects of a unit move (the move record with its note, the mason's fresh clean-turn allowance, the candidate a fresh check run or review works on, the approval record, the notice to the manager). A default is exempt from the in-flight landing and rebase check, as it always was; a move and a departure are not.

A satisfactory reviewer verdict is the authority for `approved`: the review-approved exit offers `approved` as its default and records the verdict's document and revision as the authority; the router checks again when it enters the state that the verdict is still the unit's latest and still reviews its current candidate, base, spec, plan and report, so a verdict for a superseded candidate does not approve. Jev is asked only whether that default fits, and a departure from it goes to another target without altering the verdict. An owner's move or ruling, and one of Jev's gate decisions on a contest, is a pinned move that enters exactly the target it authorises; a unit approved without independent review is the owner's alone. The manager's own move or ruling is a pinned move too, and never authorises `approved`. A landing that was refused raises the exit whose default is to check and review the unit again when the approval no longer holds, and to land it again, as the next attempt of the same approval, when the refusal was a failure of the landing itself; a mason contest with no candidate offers only the targets that need none, so its revise target stays reachable.

A scheduling pass hands its exits to the router's worker and goes on; a pass the scheduler does not run, a command and a tool wait on the router in place. Routing an exit on the scheduling path is refused, so Jev is never asked there. An exit that is held stays where it is, and the pass that raised it raises it again until the subject moves or the stall watchdog and the recovery card take it. The router's own journal subjects are bookkeeping and are left out of the feed, the activity of a unit and the trace of a workstream.

**Stall watchdog.** A pass of the scheduler also runs the stall watchdog, which is code only and reads the records at most once a minute, and not in the first minute after the service starts, while it is still resuming the turns and operations that explain a quiet. For each unit and each workstream that has not progressed for `[loop] stall_after` (45 minutes by default, `"0"` turns the watchdog off) it raises one `stalled` exit (`unit.stalled`, `ws.stalled`) to the router's worker, unless one of these explains the quiet: an open owner card about the subject, a pause that covers the subject, a running or queued turn of a worker younger than the window, an operation in flight, or a dependency wait on an upstream that is itself progressing. A card explains only its own subject: a unit's quiet is explained by a card about that unit, or by a card of its workstream that holds the whole workstream's work (its ratification, a held drift rebase, a park on its base, a loop-guard pause or the selection of its projects), never by any other card of the workstream; a shared workgroup the owner has not approved explains the quiet only while the owner is asked for its approval, which is once the inbox lists every member's ratification card, and only before the workstream is ratified; a member still sketched, in the shed or waiting for the workgroup spec is watched like any other workstream. A turn is younger than the window while the latest time it was queued, claimed or attempted is, so a turn stuck in its queue is a stall. A dependency wait explains the quiet only while one of its live upstreams has progressed within the window or is explained itself; an upstream that is alive but stalled explains nothing, so its dependents stall too, while a delivered upstream, which waits on its pull request, and an upstream in another project's records still explain it. Progress is what the loop guard counts, with three differences: nothing the manager did counts, neither does the router's own bookkeeping, and neither does a drift rebase, which moves the branch onto upstream on its cadence but no work of the workstream on. An operation in flight explains the quiet only while its latest claim, observation or retry is younger than the window and its consecutive failures are below the limit at which the operation is given up; a hold on an operation (for example a git-operation hold) explains it only when its own cause is a pause, an open owner card or a live dependency wait, and a hold for any other cause, such as a missing credential or a role switched off, does not. The window is counted from the later of the subject's last progress, the end of its last worker turn, the router's last hold of it and the last time something explained it, so a lifted pause or an answered card starts it over. A router hold that stands for the window is a stall of its own. Each stall is one occurrence, identified by the progress the subject has been quiet since, so a stall is raised once however many passes find it, and a stall the router has decided is not raised again. The default of a stalled exit leaves the subject where it is (nothing moves) and tells the manager once, with the evidence: how long the subject has been quiet and since when, what its last progress was, and, for each operation without a result, its consecutive failures, its latest attempt and its last failure, a recovery failure of the workspace included. The notice ends by telling the manager that its turn must end with an action whose result shows queued work, a `follow_up`, or a `set_status` attention item for the owner; a turn on the notice that ends with none of them gets the service's check-back at the window (section 6.6). Jev may instead send a stalled unit back to its mason or to a fresh run of the stage it waits in, a stalled assembled workstream to a fresh final review, and a stalled building workstream with nothing left to build (every unit merged, no discovery open and no revision being drafted, debated or applied) to assembled for a fresh final review, at the modest bar. The watchdog also watches each workgroup change in the journal its host keeps: a change being drafted, debated, answered, presented to the chat or applied that has not moved in its journal for the window, with no pause on its host, no delta turn of it running or queued younger than the window and no delta turn operation in flight, raises one `ws.stalled` exit on its host whose one target leaves it where it is and tells the manager, with the state it sits in, for how long, and why it is held when a failure holds it. So does the first project amendment request of a workgroup that has not been drafted into a change while no change is ahead of it. A cross-repo workgroup keeps its journal and its amendment requests in the workgroup trace, whose host is no workstream of a project: the pass of the project whose member leads the workgroup, its least member that is not archived, watches them there, with the pauses of that member, and raises the stall, the notice to the manager and the recovery card on that member; a workgroup trace another process holds is read at a later pass. A change presented to the owner waits on the owner and is not watched. The same `[loop] stall_after` is the window a landing, rebase or publication that keeps failing is retried for; with the watchdog off that window stays 45 minutes, so operations still end.

**The recovery card.** A subject that no one moves ends on one inbox card, "Approve this recovery move", so no hold stays silent. It opens in two cases. A stall that neither Jev nor the manager cleared (the router decided the `stalled` exit, the manager was told, and the subject has not moved for a further `stall_after`) pins the move that starts the stalled stage again: the stage it is in again for a unit, a kick for a unit that has not started, a fresh final review for an assembled workstream, the move to assembled for a building workstream with nothing left to build, and ending a workgroup change that sits in its draft or debate as failed, so a new one can be requested; a subject with no such move (a building workstream with work still open, a change being presented or applied) has no card, and its stall stays with the manager; a stall that Jev held, whose hold stood for the window and which the unit raised again and Jev held again, ends on the same card at the next window instead of being asked a third time, so a Jev that keeps holding a stall cannot keep it silent; a held exit from a dependency wait that stands as long pins dropping the dependency. A move that belongs to the owner (a manager's move that needs a gate and has no card of its own, or a move Jev judged would change what the owner approved) pins the target it named. Each occurrence has one card. The card shows the exact move: the subject, the state and version it was read at, the target, why, and where the move came from (a stall, the owner's or an intent change). Approving it, with one click on the page, `POST /v1/recovery/{workstream}` or `osmia recover <workstream> [unit]`, submits that move and nothing else through the owner's own path for its machine (the unit move, the workstream move, the dependency drop), which hands it to the router as a pinned owner decision (a workgroup change is ended in its journal, at the state and revision the card pins): Jev is asked nothing, the apply-time check and the target's shared effects run, the transition records the owner as its decider and authority, and the route span says `followed`. Dropping a dependency is the same `DropDependency` effect as Jev's drop, so the waiver, the Hearsay decision and the unblocking are the same. A card whose subject has moved on since (another state or version) is stale: approving it is refused as a conflict and nothing is applied, and the request must name the move the card shows. The feed keeps the card where it opened, as open, approved or stale, identified by its occurrence; the inbox lists only the open ones.

**Contest, objection, dependency-wait and drift exits.** A ruling on a contested unit is a unit exit (`contest.owner_ruling`, `contest.jev_ruling`, `contest.chief_ruling`): the owner's ruling, one of Jev's gate decisions on a contest and the manager's own ruling are pinned moves. The manager's decision on a committee objection (`objection.chief_decision`) is an exit of its own subject, `objection-<id>`, which has no state while the objection stands. The manager's decision, `dismissed` or `escalated`, is a pinned move entered as the manager made it. Jev's binding pick on the objection, from the manager's `decide`, is a pinned move that enters exactly the decision it picked, and the decision's record names Jev as its decider with the judgment. A dependent that waits on a cross-repo edge (`edge-wait`) or on its same-repo base (`base-wait`) enters the wait as code does, since an unresolved edge or an unavailable base leaves nothing to choose; the wait ending is an exit (`dep.edge_resolved`, `dep.base_available`) whose default ends the wait as the wait pass always did and whose one other target keeps the dependent waiting for the observation that resolved it, at the modest bar and only when the trigger's own question shows the dependency is not yet usable. The wait is read again from records on every pass, so Jev is asked once for an observation and a wait it kept is not asked about again until the observation changes. The owner moving a parked workstream onto upstream (`dep.base_integrated`) is a pinned owner move that commits the release together with the base observation. A drift rebase whose conflict resolution stops (`drift.review_rejected` after `shed.max_bounces` send-backs, `drift.turn_failed` for a mason or reviewer turn that failed, was interrupted again and again or left conflict markers, `drift.held` for a reviewer turn that recorded no verdict) is an exit whose default holds the drift rebase for the owner, entered as it always was; the other target asks for the drift rebase again from the start, entered through a shared effect that publishes the next drift rebase's operation, at the modest bar and only when the trigger's own answers show a transient failure that does not repeat, or findings the mason can act on that are converging. The operation of the held drift rebase ends with whichever target the router entered, and an exit the router holds without moving leaves it pending for another attempt. The other state changes of a drift rebase and of a wait (a request, a replay that conflicted, a rebase that was recorded, a skip) have one possible next state and are recorded as the code default, with `default_to` and `decided_by` of `code` and no request.

**Dependencies that cannot be met, and the waiver.** A dependent waiting on a cross-repo edge, or parked on its same-repo base, can wait on something that will never merge: the upstream was abandoned, its own pull request was closed unmerged, or its changes reached the project's base branch without a merge the factory recorded. The edge poll reads this into the dependent's own edge observation (`ended`: `abandoned` or `closed`; `integrated`: the base commit that holds the upstream's changes, only for an upstream that ended or was delivered and whose branch holds changes of its own). The same-repo base check runs on the base-exit cadence, for a parked dependent whose direct base was abandoned. Each raises an exit on a subject of its own in the dependent's trace, `dependency-<upstream>-<type>` (the type is the edge type, or `base`), so a decision about one dependency never moves the wait itself.

- `dep.upstream_terminal` (cross-repo edge) and `dep.base_unavailable` (same-repo base): the default is `kept`, what the factory always did, and the other target is `waived`, at the global `[jev] decision_threshold` and only when the trigger's own question (`works_without`) corroborates it. Jev's other pick, an intent change, goes to the owner as for any exit.
- The intent Jev reads with a dependency exit is built from records, never code. It holds the dependent's sealed intent (the spec's Intent section, or the text before its acceptance criteria when it has none) and its acceptance outcomes; the contracts and edges of the shared project spec and the units of the dependent's sealed plan that rely on the upstream (those that serve a contract section of the dependent's slice or name the upstream or a contract, and on a same-repo base every unit); and the upstream's planned deliverables (the units of its plan, with their states) and its final outcome (its workflow state and the reason, its delivery record and its latest final report). Every count in it is computed by code. Each section has its own byte bound, together far inside the 72 KiB of the request, and what a bound cuts is counted in the section (`[cut: 12 of 300 acceptance outcomes shown]`). A record that is missing, such as an upstream with no plan or no final report, is stated in the summary and never fails the exit.
- `dep.upstream_integrated` and `dep.base_integrated`: the same evidence check the owner's move onto upstream uses (the base branch is fetched and the upstream's held changes are tested for being in it). The default is `adopted`: the dependent goes on without a workgroup change, by recording the edge merged at the base commit that holds the changes, or, for the base, by pinning the base observation to upstream as the owner's move does. `kept` is the other target at the modest bar, corroborated by `integration_in_doubt`.

**Soft policies and hard limits.** Four limits set the router's default and no longer stop it. A mason's turns that ended without a report reaching `mason.max_clean_turns`, the send-backs of failed check runs and rejected reviews reaching `shed.max_bounces`, and the final reviews that found something blocking reaching `maxFinalRounds` each make the policy's outcome the default of the exit (a contested unit; a workstream left where it is for the owner, with the final review's findings untriaged), and the other legal targets stay on offer: the mason's turn with a fresh clean-turn allowance, the checks or the review again, a reopened workstream. A dependent whose upstream is not yet usable keeps waiting by default, and dropping the dependency is the departure. Jev may depart from the default at the target's bar, and a departure records its reason in the transition (the table rule and the judgment) and in the route record. None of these limits binds the manager: its move to reopen a workstream whose final reviews found something blocking `maxFinalRounds` times, to return one to delivered, or to take a unit out of a contest it raised or already ruled on is its own pinned decision. The other counters stay hard limits, as the owner approved: the incomplete check runs (`maxIncompleteChecks`), the stale reviews (`maxReviewRefreshes`), the interrupted turns (`maxRecoveries`), the architect's drafts (`MaxDrafts`), the debate rounds (`shed.max_rounds`) and the review rounds of a drift rebase's conflict resolution. At each of them the default is a contested unit or a held subject and the retry target is not offered, while every other legal target is still routed, so a limit never parks a subject silently. The draft limit counts one run of drafts: after `MaxDrafts` refused drafts drafting stops by itself, the workstream stays handed and the manager is told. A move of that workstream to sketched, by the manager or the owner, or the owner's redraft of it, starts a new run of `MaxDrafts` drafts, recorded with who asked and the note; every draft of the run carries the note, and its first draft's prompt says why the last draft was refused. A move of it to in-shed, and every other shed action on it, is refused with where drafting stands, and a sketched member of its workgroup that waits for the workgroup spec is told which member is not sketched and why. Budgets and the loop guard stay hard too, for the moves Jev routes. Every request to Jev is a session of the workstream in the ledger the loop guard counts, so the moves Jev routes count toward `loop.max_sessions`; a pause in force on the workstream (the owner's, the daily budget's, a provider's usage limit or the loop guard's), or the loop guard's limit reached before its pass has paused the workstream, stops the targets that start agent work, whatever way the target was reached: they are not offered to Jev, and a target that fails the limit when it is applied (a Jev pick, a degraded default, a recovered pick, a default whose caller supplies its own entry effects, a manager's move or an owner's pinned decision, the recovery card's included) is refused: `Refuse` is recorded, nothing is committed, no effect runs and the manager gets one notice. A pinned move keeps its authority and skips only the request to Jev, never the limits. The owner's own pause is not a limit but a hold: an exit whose target starts agent work is held without recording anything or dispatching any work, and is offered again once the pause lifts. A unit's targets also wait for a landing or rebase of the unit to end, except the one whose completion raised the exit. Routed exits that move nothing, a hold or a followed default that stays where it is, are no progress, so the sessions they cost keep counting.

Dropping a dependency is one shared effect for Jev's pick and for the owner's decision (`DropDependency`, a pinned owner move that asks Jev nothing and records the owner as the decider). It writes one waiver, `edge-waivers.json`, in the dependent's own trace, ends the dependent's wait in the same commit when no other dependency still holds it, and, for the base, pins the base observation to upstream. It never edits the shared project spec or the workgroup, and it is never merge evidence: the observation never records a waived edge merged, and no reader reports it as merged. A waiver is a decision, posted to Hearsay once from the waiver record: Jev's decision on the work source with no author when Jev dropped it, the owner's when the owner did.

Every reader of dependency edges reads them through one definition, the effective edges (`EffectiveIncomingEdges`): the edges of the workgroup's project spec minus those a waiver in the dependent's trace drops. Readiness and edge-wait blockage, wait reconciliation and polling, merge-order publication (the draft body, the approval gate, `MarkReady`) and status all read it, so a waived edge stops blocking everywhere together, is not polled again, and cannot be re-parked by a later reconciliation or a restart. A genuinely unresolved second edge is still an effective edge and keeps blocking. The project pane and the context bundle list the shared graph's edges as the spec names them, and mark the edges their dependent dropped as dropped, never as merged. A merge-order edge dropped after the dependent published its pull request as a draft makes that draft pending a fresh maintenance review and delivery approval, as a merge would; the final review pins the waived edges (`edge_waived`) beside the merged ones (`edge_resolved`), so a review read before the waiver is stale.

**Step journals are not routed.** Project registration and creation, the workgroup-change journal, publication operations, outbox delivery and turn admission only recover from crashes or record an operation's outcome. They commit their next step from the records and the disk, never raise an exit and never call Jev; a test fails when the code of one of them imports the router or Jev. The stall watchdog reads the workgroup-change journal and raises the stall of a change that sits too long, as it does for any subject; the journal's own steps stay unrouted.

**Workstream and final-review exits.** A workstream's choices are exits of the router too. The owner's gate decisions are pinned moves that the existing cards and commands authorise and the router applies: ratification (the owner's, or Jev's own gate decision, which is judged as it always was and applied with its judgment recorded) enters `ratified-<round>` with the ratification file; abandonment, whether the owner's command or the owner's approval of a workgroup cancellation applied to a member, enters `abandoned` (the cancellation hands its exit to the router's worker when its pass runs on the scheduling path and goes on once the worker has decided it); delivery approval, the pull request marked ready on its host and a merge the owner records enter `delivered` with the records each has always written; and the owner's move of a workstream enters exactly the state it names. Each records the owner, or Jev's gate decision, as the transition's `decided_by` and its authority, asks Jev nothing and sends a `followed` route span. A manager's move never carries that authority: a `move_workstream` to `ratified` or `abandoned` commits nothing, leaves a pending owner decision that names the ratification card or the recovery card, and sends the manager one notice; its other moves, and its requests for a redraft or another round, are pinned moves entered as it made them; a `decide-transition` answer that names a gate is not among the options Jev is offered, so it cannot be picked. The rest are routed with Jev: after a debate concludes the default leaves the decision to the owner; when none of the architect's drafts was accepted the default stops drafting, with no other draft on offer (the draft limit is a hard limit, below); a failed sealing, a final review's request and the assembly of a building workstream have one way out, which the router keeps without a request. A final review's round records its report whatever the router decides: the default records the report and leaves its findings to be triaged (or its failure to the manager), and Jev may instead reopen the workstream for repair units at the strict bar or ask for a fresh review at the modest one, each with the workstream move the owner's command records; a round the router holds records the report as the default does, and the hold stands for the manager and the stall watchdog.

A departure from a default is Jev's decision and is posted to Hearsay on the work source with no author, under the rules of [Jev's decisions](hearsay.md#jevs-decisions); a default that was followed, a fallback and a pinned move are not posted.

The mason classification asks, of a mason turn that ended cleanly without an outcome tool, which of four classes its final response falls in (a question asked in prose, a completion claim, giving up, or unclear) and, for each class but unclear, which sentence of the response supports it. The answers are used only when the class reaches its threshold, which is stricter for giving up because that contests the unit, and a sentence supports it. That sentence is the recorded evidence; an unclear class records its probability instead, never an invented explanation. Otherwise the code rules classify the response, and an unclear ending gets a clarify continuation that counts toward the clean-turn bound like any other. A Jev class has the effect of any other: a completion claim still needs `done`, a prose question still needs `ask`, and the clean-turn bound and contested-unit rulings apply. The classification records what classified it and the judgment it rests on.

The manager's `decide` tool asks Jev for one decision about one subject occurrence the manager may decide: the routing of a question (answer within intent, route an amendment, escalate), the ruling on a contested unit (review, revise, escalate), a committee objection (dismiss, escalate), a plan-only amendment (approve, decline), a discovery's disposition (assign, decline, retain), or one blocking finding of the current final review (needs code in the next plan revision, or left to the owner). The service checks from the subject's records that the manager may decide it today before Jev is asked: a conflict between member charters, the owner's own objection and an amendment that changes approved intent are refused, with no request and no judgment, as is a finding that final reviews made the owner's by finding blocking problems three times. Final-review triage asks one judgment per blocking finding; Jev never replaces the reviewers', the committee's or the final review's verdict. It builds the state from the records and the manager's short evidence summary; Jev reads no code. A pick at or above the decision threshold is binding: the subject's outcome tool (`answer`, `escalate`, `route_amendment`, `resolve_contested`, `resolve_objection`, `decide_amendment`, `record_discovery`, `triage_finding`) records only the picked outcome, with the manager's own text, and refuses every outcome until `decide` has a result for that same subject. A pick below the threshold, a deferral or a fallback leaves the manager to decide. The result belongs to the question, contest, objection, amendment, discovery or finding of one final review, so the same unit contested again is judged on its own, and a recorded pick is returned without a new request in later turns and after a restart. A decision made on a binding pick is recorded with Jev as its actor and the judgment it comes from. When the service refuses the transition a binding pick calls for, the subject goes to the owner with Jev's judgment and is not judged again: a discovery stays open as an inbox entry of its own, an amendment appears as its amendment card, and a finding is left to the owner on the delivery card.

The check selection runs breadth → depth → ranking over the changed files and, when it fits, the diff. `dagger list checks --format=link` defines the top-level checks, with collections unexpanded; `dagger list checks --all --format=link` supplies the expanded links. Broad links are excluded: no-filter or check-name-only roots that cover other listed links, and links holding the same checks as such a root, including a module root in a one-module project or a collection's only package when narrower tests are listed. Coverage among the original listing's leaves decides this for both query-name and path link shapes, independent of check names; links covering each other count as one check. Standalone checks with nothing narrower listed stay options. For attribution, Dagger lists each top-level check's expanded items with `dagger list checks --all --format=link '<top-level-link>'`. An expanded link belongs to the root whose scoped listing uniquely returns it. Ambiguous or unmatched links bypass breadth and depth and reach ranking; no expanded option is lost through attribution.

Breadth (`check-breadth` v1) asks one Noul per top-level check whether the change could affect it or any of its items, keeping roots at or above `jev.check_threshold`. If no root reaches the threshold, all are kept. Kept standalone checks go to ranking; kept collections go to depth (`check-depth` v1). Depth derives a hierarchy from the expanded links' filter order and asks one Choice per collection with at least two offerable levels. Broad levels are shown with a reason but are not offered; a single offerable level needs no question, and inconsistent filter orders keep the finest links. Jev's top choice is used without a confidence threshold or deterministic override. Links are cut to the chosen level and deduplicated, so the options cover every leaf of the kept checks. Choosing a coarse level changes granularity without dropping checks: a selected link runs everything beneath it. Prompt guidance usually favors `go-package` over module or test granularity for Go.

If more than 1024 options remain, narrowing collapses collection items, the largest first. It measures coverage against the original `--all` listing's leaves and never introduces broad links, including unlisted roots or bare `dag+check://`. Links unable to narrow to 1024 without a broad link use the `too_many_checks` full-run fallback without asking ranking. The fixed cap bounds request time and per-judgment cost, not an API limit. All stages receive the same link guide, process overview, changed files and diff when it fits in 72 KiB, with the process text counted against the bound. Each request is sequential and has its own `jev.timeout`.

A breadth failure, including an unavailable or failed top-level or scoped listing, restores the full expanded candidate path for narrowing and ranking. A depth failure keeps breadth's result: every finest-level leaf of the kept collections, kept standalone checks and uncovered links proceeds to narrowing and ranking; excluded roots stay excluded. During cool-down every stage falls back immediately. A failed expanded listing remains `unlisted`. Ranking (`check-selection` v4) asks one Noul per remaining link whether the change can alter its result. Links at or above the configured threshold run. If none reaches it, global `[jev] check_fallback_picks` (a non-negative integer, default 0) can select that many highest-scored candidates from the same answers, however low their probabilities. Equal scores follow sorted candidate order; fewer scored candidates run all scored links, and no usable score runs every check. Zero retains the full run when none reaches the threshold. This applies to unit, final-review and smart session runs; an explicit full run stays full. Ranking failures and selected links refused by Dagger run every check. Picks are recorded as selected links with a fallback-picks marker, and their summary and feed say that no check reached the threshold and the highest-scored checks ran. Narrowing to a collection item means one pick may run that part of a collection, but never a whole collection or an equivalent module root. This option risks missing an affected check that a full run would catch. The local `smartcheck --fallback-picks` has the same meaning and default. Every check run it starts uses `--parallel 4`, which callers cannot override.

Each stage is recorded and billed separately and reused on restart or final-review retry by its task, version and exact request identity. Optional selection fields `breadth_judgment`, `depth_judgment`, `roots`, `kept_roots` and `levels` retain the stage evidence; older records remain readable. The summary adds clauses such as "within 2 of 5 top-level checks, by go-package". [Smart checks](smart-checks.md) describes each stage's request and fallback and the local command's verbose hierarchy and probabilities.

Dagger evaluates one command under one filtered workspace view and refuses addresses with different types or dimension filters. Selected links combine only when their union selects exactly the same checks; otherwise they run in separate commands. The service and `smartcheck` run those commands sequentially, each with `--parallel 4`, keeping at most four checks running at once. The service shares one export and one `checks_timeout` across the commands, reruns and any refusal fallback, and records one result with every command's output. Failed checks get one rerun; those that pass it are listed as flaky, their command finishes any cancelled work, and later commands continue. A refusal is judged on the command that produced it: a later command refused after earlier commands passed still triggers the service's full-run fallback. The finished selection then describes a full run with reason `refused` and no picks marker, retaining earlier reports and flaky checks; start evidence keeps the chosen links. `smartcheck` stops on the first non-zero exit without reruns or a full-run fallback.

With `[dagger] check_fallback = "cloud"` and an engine other than `cloud`, unit and session check runs retry on the Dagger Cloud engine, with the compute token `cloud_compute_token_env` names, what did not finish locally: a local attempt that reached its time budget, lost its engine session or exited non-zero without a reported failed check. Checks the local output reports as passed stand, a reported failure never moves to cloud, and a refusal of the selected links keeps the full-run fallback as a local attempt. One operation has one local and one cloud budget, each `checks_timeout`, and the cloud attempt runs inside the check slot the operation holds. Unit and final-review check run records state in an optional `engines` field which links or invocations ran locally and which on cloud, and why (`timeout`, `engine_failure` or `memory`). A link that needed cloud in a workstream, as those records show, goes straight to cloud in that workstream's later check runs; memory is derived from the records alone and is not shared between workstreams. The selection description, the reviewers' and final reader's check evidence and the transition reasons say when cloud was used. A cloud attempt that does not finish leaves the run incomplete under the unchanged unit retry, contest and final-review backoff.

The trace records each judgment under its workstream: the turn that asked, the task and its question version, any configured threshold and fallback-picks value it applied, the source record revisions its state was built from, the request, the configured and resolved model versions, the answers with their distributions, the outcome and any fallback reason, and usage. A classification or check judgment is identified by its cause, task, version, configured acceptance values and exact request, so after a restart the workflow reads back the decision it already used instead of asking again, and changed inputs are a new judgment. A decision judgment is identified by its subject occurrence instead, as above, and records the decision threshold as its acceptance value. A judgment records its start before its request; a start without a result is an interrupted attempt, distinguishable from an accepted one, and a judgment interrupted twice falls back. Usage enters the ledger under the `jev` role and counts toward budgets; a cost the provider does not report is unknown, as for an agent. Status reports Jev as unconfigured, ready or degraded with its latest failure.

### 9.7 Verification

A project whose repository has a *lever*, a Dagger function that drives the running build and returns a report with evidence, sets the [verification setting](configuration.md#verification). Review then judges from evidence the service records rather than from the mason's own claims. Everything below is absent for a project without the setting: no `verify`, no reminder or pointer for the mason, no verification section in a bundle and no measure.

The lever contract, version 1, is described once in [testing](testing.md#verification-lever-contract): the invocation and the service-generated run ID, the freshness each run obliges the lever to keep, the Directory and `report.json`, flow tags and attribution, `list`, `inconclusive`, the limits, evidence retention and the shared web-driver module. This section describes only what each role does with it.

**Feature map.** The product keeps a behaviour-level [feature map](testing.md#the-feature-map) in the configured directory, one file per feature naming its `paths` and the lever `flows` that exercise it. The service matches files to it by plain glob matching, with no model call.

**Pointers.** The mason's bundle names the feature files that apply to its unit, and reminds it to keep the lever and the map current in the same change and to list the lever invocations it verified with. Before a candidate exists, the unit's footprint decides: entity IDs resolve to paths through the entity map, path globs are used as written, the `repo` entity matches every feature, and a pattern that names no existing file still matches a feature whose globs share its literal prefix. On rework the candidate's changed files are matched as well. A pointer is a hint, so naming an extra feature is better than missing one.

**Declared invocations and reruns.** A mason's done report may list the lever invocations it verified with, as a list of argument lists in `invocations`. The mason's own Dagger runs are not evidence. After the mason reports, the service reruns up to five of them, in the order declared, on the captured candidate, each under its own run ID and a `capacity.checks` slot. It records each skipped or refused invocation with its reason. The reports and their retained evidence go into the unit review bundle as service-recorded evidence, apart from the mason's own claims, and into the reviewer's view.

**`verify`.** Unit reviewers (their candidate), the final reviewer (the feature-branch head) and the manager (a member's feature head or a named unit's candidate) can call `verify` with a lever argument list they write: a named flow, or ad-hoc steps the mason never ran. Masons are never offered it. Each call is a fresh run under its own run ID, recorded in the trace with its target commit, arguments and run ID, so it can be reproduced. Replaying a recorded call after an interrupted turn returns the recorded result and runs nothing. Failures and refusals come back as limitations that do not fail the turn. Review guidance tells reviewers that a result is evidence they judge, that they should try paths the mason did not, and that a missing, failed or inconclusive result on a user-visible acceptance item is a finding.

**Send-backs.** A reviewer's `verify` results go to the mason in full with a send-back, and the retained evidence of those runs is readable from the mason's view for its rework turn. This is not a holdout: nothing is withheld or summarised away.

**Review bundle.** The unit review bundle shows the features the diff touched and, for each of their flows, the status the service-recorded runs on that candidate gave it by the flow attribution rules, or that no run covered it. It shows untagged claims, unlisted flow tags and rejected reports as such. It adds structure-check notes, which are a header that does not parse or a flow missing from the lever's `list`, and a flag when the diff touches the lever's source globs or the map directory. Notes and flags ask the reviewer to look closely and reject nothing. When the unit passes review, the service records its feature association: the features its approved candidate's diff touched and their flows.

**Final sweep.** The final reviewer's bundle lists the union of all `flows` in the feature map read from the feature-branch head, once each, in the order the map's `README.md` lists the features, with the structure-check notes. The reviewer runs them with `verify` on that head.

**Measures.** The trace and [telemetry](telemetry.md#verification-measures) record, per unit, the verify runs and their results (service reruns and reviewer calls alike, with `inconclusive` counted apart from `pass`), the flows its mason declared against the flows its reviewers ran, and whether its diff touched the lever or the map. For each final review round, each failed flow, by its worst status across that round's runs on the reviewed head, is attributed to every approved unit whose recorded feature association names it. When more than one unit is associated, the record is marked shared and lists them all, and the failure counts once at the flow level. A failed flow no association names, and a failing untagged claim, are unattributed final failures. An `inconclusive` final flow is attributed the same way but recorded as a separate measure and never as a failure. A unit counts as passing unit review but failing at final review when at least one failed flow is attributed to it.

**No gate.** Verify results, structure-check notes, lever and map flags and measures never move a unit or a workstream between states. The reviewer decides.

## 10. The service

### 10.1 One process

The process owns the factory-wide check-slot pool (`capacity.checks`, default 2).
Status reports a `checks` entry alongside mason, reviewer and committee slots,
with its limit, slots in use and waiting runs. Each waiting run names its project
and workstream plus its unit, final review number or session. Admission, release
and reload publish capacity events so the web slot display updates as runs
queue, start and finish. This accounting reads the in-memory pool without
opening a project's trace.

One long-running process holds the scheduler, the threads, the event bus, the tracker and the runtime state. It serves an HTTP API and the web interface on a unix socket for the local command line, optionally on a loopback TCP address for a browser on the same machine, and, through embedded Tailscale, on your tailnet for everything else. Tailnet membership is the security boundary: no in-app authentication, one trusted user. The same tailnet API carries the client protocol, the read-only git route and the view routes that machines running `osmia client` use (§8.5). The command line, the web interface and the manager's factory tools all call the same handlers.

Reads the web interface calls on first load and on every refresh, such as the project list, the workstream list and a workstream's feed, answer without waiting for a factory operation's effect: an agent turn, check run, rebase, merge or delivery claims its durable intent with a short bookkeeping write and runs inspection and effects without holding a project-wide lock, so a read or an owner action against any workstream of that project takes only the brief write lock and is never held up by the effect in progress, on that workstream or any other in the same project. A read reuses its last scan of the trace whenever nothing has changed since, rather than re-walking it. When a commit lands between the separate reads a response assembles together, the next attempt retries from scratch, so it always returns state from one generation and never a mix of old and new; every commit still takes the write lock briefly, so a read can wait that long, but never for an operation's effect. All of this runs inside the one process described above; there is no separate API process.

Workflow operations (model-session work and seal, build, land, rebase, drift and publish) reserve only their own workstream until reconciliation records a result or retry and the attempt finishes. Worker operations, including mason, reviewer and committee turns and check runs, keep their scheduler order and capacity without taking that reservation. Conversation operations follow their own thread order and also bypass it. The controller can run any class beside its pass. It claims in priority order through short bookkeeping, leaves an unavailable workflow or kind limit pending, and continues admitting independent work; later workflow operations on that workstream wait their turn. Scheduling holds no project-wide lock, so a scheduling step never excludes a claim or result write. Operation completion wakes admission again. Shutdown joins every admitted operation before closing the trace. Operations and bookkeeping lock waits exceeding one second produce logs naming the project, workstream, operation or lock, and duration.

Remote observers run beside scheduling: archive pull requests, dependency edges, base refresh and own pull request outcomes, and workgroup change application. Drift schedule reads also run beside the pass. They share the project’s Git/GitHub capacity and never reserve a workstream’s workflow order. Observers retain their configured polling cadence across reloads; failed lookups supply no merge evidence. After an interrupted lookup, restart reads durable evidence before repeating it. Project shutdown cancels and joins every observer before closing its trace.

The service also keeps one in-process activity record of what it is doing: every reconcile-controller operation (a seal, build, land, rebase, drift or publish, a unit's checks, an agent turn), and startup or project recovery, reports its start, its current phase and, when measurable, its progress, and finishes the entry on success or leaves it recorded as failed. The record is a small, separately locked structure, not the trace: reporting to it and reading it never wait on the trace's write lock or a workflow operation's workstream reservation, so it stays visible and prompt even while the effect it describes is still running or stuck. A fresh start of the same operation, keyed by its own stable identity, supersedes whatever that key last reported, so a repeatedly failing operation never grows the record and a stale failure never outlives the operation that caused it. A failure also expires on its own after a bounded time if nothing retries it under the same key, so an operation keyed by the trace event that requested it rather than by a retry-stable identity (an abandoned workstream, or a check run a later run number never supersedes) cannot leave the record, or health, reporting a failure forever. Only kinds whose own reporting is expected to keep moving (Git and workspace operations, recovery) count toward the no-progress stall; an agent turn or a check run reports only its start and finish and may legitimately run for minutes, so elapsed time alone never marks one of those degraded.

Every core read (status, a workstream's status, config, runtime, the inbox, a conversation, a feed, trace views and the event stream's resync) is bound to answer within a short fixed latency, whatever a Git operation, a check run, an agent turn, reconciliation or recovery is doing at the time, because it never waits on anything but a short, validation-sized critical section of the trace or runtime lock. Of these, status alone keeps a fallback for the case where a fresh read still cannot finish inside that bound: it answers with the last snapshot it already had, marked with an `X-Osmia-Stale: true` response header, rather than block the caller further; the refresh it started keeps running underneath and the next request sees its result once it lands. A read that does assemble fresh state never mixes two generations of the trace or the runtime store: it retries from scratch, rather than returning a partial mix, when a commit lands between the separate reads it combines. A request that is cancelled or times out stops the read's own blocking work where that work can be cancelled, rather than continuing to hold anything on the caller's behalf.

Every owner-action write (hand-in, ratification, a shed action, an amendment decision, an answer, a move, delivery approval, abandon, pause, priority and archive) answers promptly with one of three outcomes: accepted, meaning the command is durably recorded before the response is sent; rejected, with the reason, when the request or the current authoritative state refuses it outright; or temporarily unavailable, naming the specific backend operation the activity record (above) shows is in the way, when a resource the write needs is held by an operation still in flight. A long-running accepted action, such as a drift rebase or a delivery, is a durable operation whose progress and outcome are reported back through the API and the event stream the same way any other operation is, not invented as a parallel mechanism. Before a write takes effect it is checked against current authoritative state and, where the client's request names the revision or version it was shown, against that revision: a stale view is refused with no effect, never silently applied against newer state and never treated as still current because a snapshot read once said so. A command carries or derives a stable identity, such as a hand-in key or a trace transition's expected version, so resubmitting it, including after a restart recovers an interrupted write, reaches the same durable result rather than applying twice; an accepted command's effect is reconciled from that durable record before anything is retried, never dropped silently.

### 10.2 The API

- Workstreams and their status. An event stream, which also announces a change to the backend activity record.
- The backend activity record: every operation in flight or failed, with its kind, the project and workstream it concerns when relevant, its phase, its progress when measurable, the time of its last progress and any failure.
- Health, read apart from the trace so it always answers promptly: whether the API is available, which it is whenever this response is sent at all, separately from whether the backend is ready, not yet ready (startup or project recovery is in progress) or degraded (an activity entry has failed or made no progress for a time), naming the operation when it is not simply ready.
- The conversation per workstream: send a message, list turns.
- The inbox: open questions across every workstream, answer one.
- Pause and resume at factory, project and workstream level. Priority order.
- Profile bindings: get, override, clear. Usage per provider.
- Configuration: what is loaded and its digest, reload, last error.
- Projects: register one repo per project, list projects through configuration, edit each charter, and remove eligible projects. Workstreams: hand in with an ordered project list, abandon and permanently archive.
- Project design: open, list, converse, read the brief and start a workgroup in one owner action. The manager opens a new thread from the brief and the design transcript for status, escalation and amend/cancel impact decisions.
- Sessions: open, list and read; send a message, stop a turn; read changes, commit, check, push and end (section 6.8).
- Trace: walk a workstream's record.

### 10.3 Runtime state is not configuration

Profile overrides, pause states and priority live in `runtime.json` under the root, persisted so they survive a restart and untouched by a reload. Configuration says the defaults. The runtime says what you changed since. Clearing an override returns to the configuration.

### 10.4 Reload

Reload is explicit. It reads the top-level configuration only, validates it, and applies it together with each project's effective settings only if it passes. A bad file leaves the old configuration running and the error in the interface. Profiles, capacity, budgets, review settings, Hearsay and Jev settings apply live. Reload never adds or removes a project and never adopts a project's stored settings: those change through the Settings page, the API, the offline repair command and a restart, and a saved revision the service could not apply stays pending until the project's next save or a restart. Listen addresses, the tailnet identity and the root need a restart, and the interface says so. The charter needs no reload because bundles read it at turn time. The loaded digest is shown, so "did the reload take" is checkable.

### 10.5 Notifications

A new question, a contested unit, a delivery, a budget pause or a landing can go out through a configured webhook so the inbox reaches you without the page open. One key, optional.

### 10.6 Service tests

`internal/service`'s own `TestMain` applies the shuffle default to that package's test binary before running it, on top of the Go check's global flags in `dagger.toml`, which stay the same for every package. Unless the caller passes `-test.shuffle` explicitly, it turns shuffling on, so the binary prints the seed it drew and a failing order-dependent run replays with `-test.shuffle=<seed>`. It leaves `-test.timeout` unchanged, so the Go check's 30-minute timeout applies to this package as it does to the others. The service's `checks_timeout`, which defaults to 15 minutes, bounds the whole check run. Its browser tests share a pool of headless Chromium processes, at most one for each test the package runs at once. A test holds one browser while it runs, opens its own tab on it rather than a separate browser context, and closes the tab through `t.Cleanup` before its fixture tears down, so its tab stays the visible, focused one even beside other parallel tests.

A new test in this package follows these conventions:

- Wait for the state an assertion checks, with a bounded deadline, instead of sleeping a fixed duration or counting a fixed number of ticks; drive reconciliation passes explicitly when the assertion depends on how many have run.
- Prove a negative only after observing the pass, turn or write that would have caused it, for example by blocking a reconciliation pass on a channel and confirming it ran before asserting that a second service lifetime never raced it.
- Release every browser context, fake server, event stream and service through `t.Cleanup`, never a bare `defer`: cleanups run in last-registered-first-run order, so a fixture created before the browser tab opens tears down after the tab closes, not before.
- Keep a test helper shared across test files safe for concurrent callers, since parallel tests can call it at the same time.
- Consider `t.Parallel()` for a slow top-level test, where running it beside others shortens the package's run. A test that depends on process-wide state, such as an environment variable set with `t.Setenv`, a package-level variable or hook, the working directory, a fixed port or a process-wide measurement, stays serial.
- Never retry a failed assertion or rerun a test until it passes; a flake is a bug to find, not a wait to lengthen.

## 11. Interfaces

Preview and session images are trace records: bytes belong only to the workstream shown or the exploratory session, never to a workgroup trace or a loose image store under the root. Only PNG and JPEG are accepted, up to 5 MiB per image, with actual image bytes matching the declared type. SVG and other formats are refused; there is no aggregate cap. Shared manager conversations retain only a member workstream and image ID. Archiving a member deletes its images with its trace, and destroying a session deletes its images. The archive's pinned presentation retains no image bytes. Shared references to archived members resolve to `image removed when <member> was archived`. Image bytes never enter Hearsay or notification webhooks.

`GET /v1/images/{workstream}/{image}` serves the stored bytes with their stored content type, `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`. The read-only route is available on every listener under the existing Host and network boundary rules, is listed in `service.Routes` and OpenAPI, and never serves SVG or HTML. Workstream, shared workgroup and session feeds carry image metadata as an `image` entry kind, announced through the event stream and ordered by the existing equal-timestamp rules.

### 11.1 Web

Built for a phone as much as a laptop. Embedded in the binary, one page, fed by the event stream. The project pane is the entry point: each one-repo project lists its workgroups and member workstreams, plus design and exploratory sessions outside workgroups. It offers Create project, Hand in a feature, Open a design session and Open an exploratory session through shared forms, offered by the header's New menu, the only place that offers Create project; the project pane leads with a cross-workstream Needs you list built from the inbox, and the sidebar rows show a state glyph and a needs-you count. The design form's **New project** option opens a session for a project that does not exist yet. Project-card actions preselect the project; global actions ask for it. Hand-in offers a multi-select of all active projects. A cross-project workgroup appears under every member's project card and sidebar group row; member labels use project names only. The Osmia heading returns to the project pane. The configuration and runtime reads list the active projects by the creation time of each project's newest workstream, newest first, with ties and projects without a workstream in registry order, so the pane, the pickers and the CLI's project listings show the project worked on most recently first; `effective.active_projects` follows the registry's order. The page shows the order it receives.

The design view exposes the read-only live Brief panel and revision-pinned Start described in §6.7. Settings is one view with sections for projects, priority, profiles and usage, configuration and the Dagger engine, opened from the cog. Project management, in its Projects section or opened from a project card, shows that project's charter rule count, revision-pinned read/edit/save controls, and an editable project settings form. Rebase workstreams and removal act on that project and show their outcome there. Removal is refused while any member remains unresolved. The settings form lists every effective setting of the project's stored settings (`name`, `upstream`, `fork`, `clone`, `base_branch`, `landing`, `upstream_rebase`, `pull_request_poll`, `checks_timeout`, `capacity.per_workstream`, `capacity.git_operations`, `hearsay_scope`, `hearsay_declare_repo`, `hearsay_entities`), names the stored revision, holds the pin of the revision it read and marks omitted settings as defaults, with the inherited top-level value for `capacity.per_workstream`. A setting whose stored value differs from the loaded value, because a revision was saved but could not be applied, shows as not yet applied beside the value in effect. Stored settings that do not load show the loader's error and the offline repair command and offer no save. Save records the changed keys as a new revision, a text edit of the pinned revision, through `PUT /v1/projects/config/{project}`, and the service applies them without a reload; clearing a field removes its setting. A refused save keeps the draft and shows the field error or reason; a stale pin keeps the draft with a changed-elsewhere notice until the owner explicitly reads the settings again; a save that recorded the revision but could not apply it shows as saved with the values pending at the returned pin, until that project's next save or a restart. An untouched form follows configuration events live. Previews are requested through the manager conversation and have no project settings form. The pane, choosers and management view follow API changes live. An untouched charter editor follows a new revision; a dirty editor keeps its draft and original pin with a changed-elsewhere notice. A stale save keeps the draft and refusal until the owner explicitly reads the charter again.

Workstream labels are planning, ready, building, paused, blocked, PR open, delivered (merged) and cancelled. Blocked work names the service's edge or merge wait without adding an inbox entry. An open pull request stays PR open until a recorded merge. Pause and priority controls retain each project's scope.

A multi-member workgroup has its own view, selected from a clickable sidebar group row titled with its goal, with a direct `#workgroup=<id>` link. The row counts everything waiting in the group and marks unread shared conversation. The view shows the one manager conversation, statuses and actions from `GET /v1/workgroups/{id}/feed`, with project names on entries concerning a member. Its Waiting for you list contains shared decisions and each member's own decisions, labelled by project and retaining their recorded inbox identity and answer targets. One card per member shows its project, state, unit counts, wait reason, pull request and running indicator; opening it selects that member. Archived members remain as cards marked archived from their pinned archive identity. Once every member is archived the group stays in the Archived list and its row still opens the view for as long as the shared thread survives: the conversation is read only, with no composer and no member to address, and the view says "This workgroup is unavailable." only when the group or its shared feed is gone. The dependency graph appears when there are edges. A pinned composer sends to the whole group through `POST /v1/workgroups/{id}/conversation`, without a member-addressing note. On a phone, member cards stack above the conversation. Member detail events never appear in this conversation.

Members of multi-member workgroups show only their own activity and decisions: transitions, worker sessions, check runs and final reviews, with Documents and Trace tabs. Shared questions, the chat thread and its composer belong to the workgroup view. A slim header line shows the manager's latest status and an “Ask the manager about this repo” link. The link opens the workgroup composer with an “About: <repo>” chip; sending with that chip uses `POST /v1/conversation/{workstream}`, retaining the member note and displaying the reply in the shared conversation. Clearing the chip sends to the whole workgroup. Member sidebar rows use project names, count only their own decisions and ignore shared conversation and manager status for unread tracking.

Single-member workgroups keep the member's conversation, composer and decisions and have no workgroup row or view. When a second member joins, existing events refresh the open member into the trimmed shape without reloading, removing cached shared conversation, composer and shared questions. The earlier conversation stays readable in the workgroup view. Conversation and status events for any member refresh an open workgroup view. Each view keeps its own action outcomes across navigation. The project pane's Open inbox and workgroup block open the workgroup view for multi-member groups; starting a multi-member workgroup from a design session follows the adopted conversation there. Direct design-session links also follow that conversation after start.

Workgroup, workstream, design and exploratory conversation feeds scroll to their newest entry when opened, including direct hash links and returning to the Conversation tab. If entries arrive after opening, scrolling waits for them to render. Every new displayed entry scrolls the conversation to its end even when the owner has scrolled up; an exploratory message's local echo counts once, and its recorded replacement does not count again. Reads and renders without new entries preserve the scroll position. Hidden feeds and other views do not scroll in response to entries, and the composer keeps its focus and draft text.

Each conversation composer offers an icon-only microphone immediately before Send when transcription is configured (`effective.transcribe.url` of `GET /v1/config` is non-empty) and the page is a secure context in a browser with `MediaRecorder` and `getUserMedia`; otherwise it is hidden, and a plain-HTTP tailnet page still offers the link to its HTTPS address. Tap it to ask for the microphone and record; the button turns the accent colour while recording. Tap again to stop: the composer shows that transcription is in progress, the clip goes base64-encoded in the JSON body of `POST /v1/transcribe`, and the returned text is appended to the end of the textarea after whitespace (as is when the textarea is empty), never replacing a selection or any existing text. Recording and transcription never send automatically; Send and Enter keep their ordinary path. A refused microphone, an empty recording, transcription being off and a transcription failure appear in the composer's outcome line and leave the draft unchanged. A recording belongs to the composer and conversation where it started; sending or leaving that conversation stops it and discards any later transcription.

The sidebar groups multi-member workgroups with each member labelled by project name. The newest member activity orders each group, and selection preserves that order. The adopted design host is omitted from the workstream rows. Archived members retain their grouping in the archive list.

- **Active work.** Every workstream with its goal and its units counted by state, and the capacity view: slots used per role kind, who is waiting, every client with its identity, slots used and total, lease health, draining state, the profiles it can and cannot run with their fixes, the fallback profiles it skips, why it takes no new turn, the turns running on it and the turns that failed on it (the local client included), and every pause in force with its reason.
- **Inbox.** Every open question, contested unit and ratification packet the manager has raised across workstreams and projects, each with the manager's rephrasing, the options and its recommendation, answered inline, and every publication that keeps failing, with its last failure. An entry is written to be decided at a glance: the decision asked of you in a sentence or two, each option as one sentence saying what it does, and the recommendation with its main reason. What the roles asked in their own words is folded under the rephrasing, a contested unit carries the manager's note once, and repeated identical failures are described once. The evidence behind an entry stays in the feed and the trace.
- **Conversation and Activity.** Each workstream has two tabs built from its feed. Conversation is the default and holds owner messages, the manager's replies and actions, images, delivery briefs, the outcomes of owner commands and only the latest manager status, with decision cards above the composer. Machine events appear in it only as one-line milestones: the workstream becoming ratified, building, assembled or delivered, and each final review's result; a milestone opens Activity at its entry, and sessions, unit transitions and check runs, failed ones included, never appear. Activity holds every event below, with the reasons and details they carry, folds consecutive routine events into an "N events" line that opens in place, filters by unit only, and marks the latest status current while older ones recede. The tab, the unit filter and the opened entries are kept in the page's location hash, so loading it restores the view. Unread markers count Conversation only. The feed holds, for each workstream, its own activity in the order it happened: every claimed worker turn with its role, profile and outcome (including final-review readers), and every recorded workflow state change with its subject, previous and new state, and reason. Each unit check run appears once its selection is recorded, with its unit, run number and state: running, passed, failed with the failed check links, not completed with its error, or superseded. Smart runs keep their selected-of-judged counts while running and after completion ("checking 3 of 113"), plus the total listed when narrowing reduced the candidates; historical runs omit totals they never recorded. Full runs say every check ran and give the fallback reason. Final check attempts show the same selection counts and fallback reasons as unit runs, with the selection sentence from their recorded evidence. Each final review includes every check attempt, its reader's turn and its outcome: blocking finding and uncovered criterion counts, or a failure reason. Final checks appear as running only from durable attempt start evidence, after rebase/export and retry delay; a request alone shows no running checks. An incomplete attempt and its started retry stay separate. Historical final results without start evidence still appear. Unfinished starts survive restarts without implying a passed or failed result. Workstream events refresh the open feed as these records arrive. Captured check output remains in the trace. Single-member feeds also include the manager conversation, actions, statuses and turns. Multi-member feeds exclude these shared entries, so a member's Activity holds its own machine events.
- **Controls.** Pause and resume at every level, priority order, the profile switcher with usage per provider beside it, and a reload button that lights when the file on disk differs from what is loaded.
- **Backend activity.** A header button, marked whenever an operation is in flight and distinctly when one is blocked or has failed, opens a popover listing every entry in the activity record: its kind, the workstream or project it concerns, its phase and progress, and any failure. An entry whose last progress is old enough, or that carries a failure, is shown as blocked whether or not a fresh read has arrived since.

Submitting a feed action, such as a ruling on a contested unit or ratifying a proposal, removes its card from the feed at once, before the server has responded. The card stays off the feed through any refresh that still lists the action as outstanding, since the backend may not have processed it yet, and comes back as actionable if the backend is still listing it 120 seconds after it acknowledged the submission, so it can never stay hidden for good. A failed submission (a non-success response or a network error) brings the card back at once with the error shown and the owner's entered values kept. Dismissing one card never hides or changes another. Every form that submits an owner action, including new project, archive and the feed's own action forms, clears to its default values once its submission succeeds; a failed submission leaves the form as the owner left it, with the error shown.

Agent-authored conversation replies and actions, manager status notes and attention, and expandable session reports render Markdown in the page. The shared renderer supports paragraphs, line breaks, headings, emphasis, code, nested lists, quotes, safe links and pipe tables. Wide tables and code blocks scroll inside their own boxes. Raw HTML and malformed or unsupported syntax remain literal text; only HTTP, HTTPS and mailto links are clickable. Design responses retain their Assumptions disclosure, including its expanded state when new messages arrive in the selected conversation. Owner messages, inbox cards, packets and delivery views retain plain text. Stored conversations and API responses retain the agent's original text.

Images render as inline thumbnails in workstream, shared workgroup and session feeds. A thumbnail opens the full-size image endpoint in a new tab; workgroup entries are attributed to the member's repository. An archived-member reference renders its placeholder text without an image request or broken image. Image entries arriving over the event stream use the same feed selectors, scrolling and snapping rules as other entries.

### 11.2 Command line

The following is the full design; see the [command line](cli.md) for supported
commands. The service runs in the foreground or with `serve --detach`, which
returns after the service acknowledges readiness; that launcher's own
terminal output, the "ready" line and a readiness failure, stays
human-readable text. The service process itself writes only structured,
JSON-lines records to its own standard output and standard error, detached
output appended to the private `service.log` under the root; see the
[service log](running.md#service-log). A failure that stops a running
service is one such record, naming the project whose work failed, with
credentials redacted. `osmia stop` requests shutdown over
the local Unix socket.

```
osmia serve [--detach]               the service, foreground or detached
osmia stop                           stop the local service
osmia client --server URL --slots N  run model sessions on this machine for the service, foreground only
osmia doctor                         check what the service needs, and how to fix it
osmia project add dagger --upstream dagger/dagger --fork kpenfound/dagger --clone ~/github.com/dagger/dagger
osmia edit charter <project-id> [--from <file>]   the charter in $VISUAL or $EDITOR, as a new revision
osmia edit spec|plan <workstream-id> [--from <file>]   the draft spec or plan before ratification
osmia design open <project-id>       discuss before handing off
osmia design start <design-id>       hand the brief to the architect once
osmia design destroy <design-id> [--json]   permanently remove an open design session; no archive
osmia handin <project-id> ./design.md [--with PROJECT-ID]...   a workgroup from a document, an issue URL, or stdin
osmia status [workstream]            the status, or every workstream's goal and attention
osmia inbox                          open questions
osmia answer <n> "..."               a ruling
osmia move <workstream> <state> "..."          a workstream to another feature state, with a note
osmia move <workstream> <unit> <state> "..."   a unit to another state, with a note
osmia send <workstream> "..."        a message to the manager
osmia pause|resume [all|<project>|<workstream>]
osmia archive <workstream>      permanently delete a terminal workstream’s trace; retain its title
osmia profiles [set <role> <profile>|clear <role>]
osmia reload
osmia trace <workstream> [unit|criterion|commit]
osmia packet <workstream> [--json]   read the packet and workgroup spec, including revision pins
osmia ratify <workstream> [--project-spec-revision N --spec-revision N --plan-revision N]   use the pins displayed by packet for cross-repo work
osmia merged <workstream>            an assembled branch you merged into upstream yourself, recorded delivered
osmia land <workstream>              approve and land an assembled workstream on a project whose delivery is "jev"
osmia session open <repo-id> --profile default   a session for exploratory work; chat happens on the web page or the API
osmia session commit <session> "..."          commit every worktree change onto the session's branch
osmia session check <session>                 check the session's head commit
osmia session push <session>                  push the session's branch to the project's remote
osmia session end <session>                   end the session, releasing its worktree

```

Every command is an API call except `serve`, `doctor` and `client`, which connects to the service's tailnet API as a machine that runs sessions. Doctor checks what the service needs before one runs, so it reads the root and configuration the way `serve` does; no other command reads state files directly.

CLI feed output renders an image as `[image: URL]`. A removed shared image renders `image removed when <member> was archived` instead. The manager chooses each preview Service from the member's committed code and supplies its call and port to the tool; no CLI project setup is needed.

## 12. Hearsay

Hearsay is an optional external context and memory service. It is not an orchestrator, has no work-unit model, delivers no agent messages and synthesises nothing at read time. The state machine, the plan, the mailbox and the documents of record stay in Osmia. Hearsay ingests source records (L0), distils them into memory (L1), and serves scoped bundles of decisions and source pointers. The integration is optional; the complete local workflow must remain usable without it.

### 12.1 What lives there

Hearsay is the record of how decisions are made about each project Osmia runs. Factory internals stay in Osmia.

- **Decisions.** The owner's rulings, charter revisions, specs the owner's ratification sealed, charter-proposal outcomes and accepted final-review findings are ratified records, posted to an owner source. The manager's logged assumptions, intent and scope answers, scope calls and plan-only amendments are inferred records, posted to the work source. A decision Jev made, whose record has Jev as its actor and links its judgment, is never the owner's ruling: it is a work-source record with no owner author, and a spec sealed by Jev's ratification or by an amendment Jev decided is a work-source document with no author too.
- **The shape of the project.** Projects, workstreams with their states and pull request outcomes, workgroup contracts and structural changes to the subsystem map.
- **The outside.** For a project like dagger, the scope also ingests the repository's GitHub activity and its Discord channels, so a mason on the engine gets what the maintainers said about the engine, not only what your factory learned.

The role notes shrink to what is private to a role's craft. The manager's memory of how you decide is your stance history.

### 12.2 Publishing

Osmia posts to Hearsay's `work` push source; Hearsay does not read Osmia's trace. Only deterministic service code posts, from lifecycle steps, entity map re-seeds and the owner's own gates. No model turn writes and no agent tool writes. Posts are reconciled from the committed trace by per-artifact digests: the first pass backfills, an unchanged artifact is not reposted, and an outage leaves digests unrecorded so a later pass retries without affecting local work. Record ids derive from Osmia ids and are stable. Authority comes from the source the record arrives on, not from its author: the owner's decisions go to the owner source with the owner named as author through the publisher agent, and everyone else's stay inferred on the work source. Projects are posted without `repos` unless a project opts in, so only the owner reads them. Turns, tool calls, costs, check output, plans, mason reports, subsystem notes and anything that came out of a Hearsay bundle are never posted. [Hearsay integration](hearsay.md) lists what is posted and where.

### 12.3 Bundles

The service assembles each turn's task context and a project briefing with applicable charter rules, decisions and owner-policy notices. The full entity map and informational notice history remain available through bounded project-context retrieval. Optional scoped Hearsay pointers accompany the briefing, with detailed evidence available through its tools. Roles map to agent classes: architect, committee and mason are workers, the manager is an orchestrator over several scopes with a watch, the foreman is an observer, and you are the steward. The effective principal is always the agent's grants intersected with yours.

### 12.4 Watching

The manager watches the project scope. A Discord thread that decides something about a subsystem an in-flight unit touches, or an upstream change that supersedes a stance the plan relied on, becomes an amendment request, notice or question. A maintainer's review on a delivered pull request becomes a notice or question and may lead to a new owner-requested workstream, as described in section 5.5. A watch never grants permission to change a ratified spec or restart terminal work.

### 12.5 Without Hearsay

Osmia runs without it. The null provider uses the charter, local entity map, spec, plan, questions, notices and trace decisions. Footprint checks and scheduling still work. File-based context is a supported operating mode, not an error; status reports it explicitly. If Hearsay is configured but unavailable, status reports degraded memory and the same local path continues to work.

A ruling is written locally first and posted to Hearsay by the publisher afterwards, so an outage loses nothing: a later pass posts it. Workstreams archived before publishing was configured are not reconstructed. File-based context is the supported provider. Hearsay integration requires entity resolution, stance history, assert, agent classes, watch and the decision log. Jujutsu and multi-project support must work without Hearsay.

```toml
# A project's stored settings, kept as revisions in <root>/project-store/
version = 1
name = "dagger"
upstream = "dagger/dagger"
fork = "kpenfound/dagger"             # optional; omit to push feature branches to upstream
clone = "~/github.com/dagger/dagger"

Edges come from the ratified graph, with no release-signal, tag or package configuration.

Every key has a default, validation, a documented meaning and a test. The configuration carries a version, adding keys is not a breaking change, and the loader refuses a key it does not define.

## 14. Bootstrap

### 14.1 Adding a project

`osmia project add` records one repo's upstream, optional fork and clone, creates the project's trace with the charter template and the entity map seeded from the clone, and runs no agent turn. Optionally write that project's charter with `osmia edit charter <project-id>` or in the web UI. Register every other repo as a separate project with its own charter. Projects can be added while others run; removing one is refused while it has an unresolved member in any workgroup. Startup splits grouped registrations and preserves their IDs and in-flight authority as described in §4.5.

### 14.2 Handing in a workstream

`osmia handin <project-id> <file|issue-url|->` records one immutable `handed/` input as the brief. Repeat `--with <project-id>` to add projects in order. The API accepts ordered `projects`, with `project` retained as a one-element shorthand; the web hand-in form offers all active projects in a multi-select. The first project is home and hosts the shared manager and conversation. Go validates the list before allocation: empty, duplicate or inactive projects are refused, while paused projects are allowed. No design session is required.

One selected project uses ordinary drafting and ratification. Multiple projects allocate and join one member per selected project without a model selection turn. The architect drafts each member's spec and plan and the workgroup spec, contracts and graph; a project it judges needs no change is escalated to the owner and remains selected. Every member receives the immutable brief. Allocation, join and conversation adoption recover across interruption without duplicate members or replacement groups.

Every architect spec, plan, amendment or workgroup spec delivery returns the same verdict the service would give all documents delivered in that attempt if the turn ended now: valid, invalid with problems, declined or unchanged. The architect can correct a draft before ending its turn. The committee debates the draft and one owner ratification seals the entire packet. The chosen project set cannot change before ratification; changing it requires abandoning and handing in again. Amend and cancel remain available after ratification.

`--kind <kind>` and the API field `kind` name the workstream kind and default to `feature` (§5.6). `--skip-debate` applies to all members and retains ratification. `--base` must name a workstream in a selected project and applies only to that project's member. Each member retains its own final-review acceptance, delivery approval and owner signing. Project pause, capacity and Git permits hold only that project's member, subject to graph edges. From here the lifecycle in §5 runs and the manager presents the packet when ready.

### 14.3 First run

Git worktrees and Jujutsu share the workspace interface. The service supports multiple projects and workstreams, with a web interface on the tailnet and file-based context. Cross-workstream bases and the optional Hearsay publishing, bundles and watches are separate capabilities; neither is required for independent workstreams to run and deliver features.

## 15. Security

- Tailnet membership is the boundary for the web interface and the API. The unix socket is the boundary locally, and the loopback interface is the boundary for the optional web listener, which binds no other address and refuses requests whose `Host` is not loopback or whose writes are not JSON. The tailnet listener refuses requests whose `Host` is neither an IP address nor one of the node's names, and writes that are not JSON, except the git fetch request and the upload of a finished view, which carry their own content types, still pass the `Host` check and are granted no cross-site preflight. There is no in-app authentication and no multi-user isolation.
- Recorded audio goes from the page to the service as a JSON write (`POST /v1/transcribe`, subject to the same `Host` and JSON rules) and on to the owner's configured Whisper server; it and its transcription are transient, never stored or written to a trace, log or event, and the Whisper bearer key is read from the environment and never leaves the service.
- Sessions never hold a version control tool, so a session cannot push, force-push or rewrite history. A client never pushes, commits or writes to any git store: the git route it fetches from is read-only, and the service alone captures and records what a client returns.
- The service never sends a client a provider key, the Dagger Cloud token or any other secret. Each client uses its own machine's provider login and Dagger setting. An archive a client uploads cannot write outside its turn's view, a tool call for a remote turn cannot read or write a file outside that turn's view, and the git route serves nothing but registered projects' clones.
- Web access is granted to the planning roles alone (§9.5). A page they read may carry hostile instructions; this risk is accepted because those roles hold no write, shell, credential or owner-gate capability, and the shed, the reviewers and the owner's ratification check what they produce. In sbx, the owner's network policy decides which hosts a fetch reaches.
- GitHub credentials reach the foreman's push and pull request calls as environment variables, never as arguments, and never reach a session.
- The service alone uses the owner's configured signing key or signing agent for owner-approved delivery commits. Private keys and signing credentials never enter runtime-agent sandboxes, context bundles or the trace.
- No factory state is committed to the target project. Its repository sees the feature's code and tests through the branch and pull request.
- Every bundle served by Hearsay is an audit event: who asked, on whose behalf, what was filtered.

## 16. Defaults and deferred choices

1. Per-role or per-workstream override of profiles. The design has per role, global. Per workstream would let one feature run on a cheaper provider, and complicates the switcher.
2. Several workstreams in one project when both touch the same subsystem. The default is an advisory, with owner pause and priority controls. Automatic refusal across workstreams is deferred. Within a workstream overlapping or unresolved footprints are serialized.
3. Committee membership. Per workstream in the design, with project memory arriving through Hearsay. Per project would accumulate arguments in the thread instead. Revisit when the first workstream has run.
4. What counts as acceptance. Acceptance states observable conditions; evidence demonstrates those conditions. Reviewers may use equivalent or stronger evidence and applicable historical evidence with an explanation, but cannot weaken approved outcomes. Shared quality obligations come from the charter and service checks. The charter determines what a project requires, and the reviewer records how it verified the acceptance. A passing service-owned check gate is the evidence that required tests ran and passed, including whole-suite, scoped and named-test acceptance. Reviewers never raise a finding solely because only a smart-check selection ran, a named test is unseen, or they cannot run tests; they still judge whether requested tests exist and exercise the behaviour. There is no mechanical coverage score that substitutes for that judgement.
5. Unit-scoped parallelism. A unit is one mason. Whether a wide unit may fan out into several masons with a squash step, as an assembler, is deferred until a real feature needs it.
6. The spec format. Markdown with a numbered list of criteria. The service parses numbered criteria and checks newly submitted acceptance for whole-suite check obligations; reviewers judge whether the implementation satisfies the criteria. The footprint is declared in the plan by the architect and used to schedule units, never derived from the spec.
7. **Integration gate edge remains unresolved.** “Neither PR is marked ready until a combined test of both branches passes” needs an owner ruling on the combined-test mechanism. Integration-gate edges are not implemented and the architect must not propose them until that mechanism is accepted.

## 17. Component boundaries

**`github.com/kpenfound/agentcore`** is the reusable Go dependency for agent execution and backends, session sandbox primitives, review, retry classification, ledger and budget primitives, capacity, event wakeups, the MCP host and the workspace interface. Osmia consumes a pinned module version. Reusable extensions belong in that dependency; Osmia-specific workflow policy remains here. A sibling checkout must not be required to build or test Osmia.

**Osmia owns the workflow.** Its Go controllers own feature and unit state, the plan, seals, footprints, scheduling policy, questions and fixed message routes, role notes, prompts, ratification and delivery gates. Durable threads wrap the core runner with an owned log and turn queue. The core's wakeup bus does not replace the durable outbox, and its workspace or VCS-access flags do not by themselves enforce the isolation required in sections 7 and 15. Adapters must verify those contracts explicitly.

**Hearsay** is optional memory, reached through a provider boundary. Osmia's service posts decisions to it. Bundles and watches augment the local record; Hearsay never becomes the workflow tracker, dispatcher or owner of the specification. Section 12 defines the integration and fallback contract.

**Jev** is the judgment provider, reached through a TypeSafe-compatible API. Osmia owns the questions, their interpretation, the thresholds and the fallbacks. Jev is the decision maker for the bounded decisions of the owner gates and of the manager's `decide` tool: a pick at or above the decision threshold, or the owner threshold for the owner's own decisions, is recorded as the decision with Jev as its actor, and Jev never writes text. The service owns every transition. Section 9.6 defines the contract.

## 18. Feature guarantees

The workflow builds on durable local state, planning and owner ratification before implementation and delivery. Concurrency, alternate workspace backends and multi-project operation preserve those guarantees. The web interface exposes the same owner decisions as the local API. Optional memory integration must preserve a complete file-based workflow.

| Feature | Scope | Required behavior |
|---|---|---|
| Durable local service | Core integration; personal service, configuration and local API; per-repo, workgroup and workstream trace databases; durable records and outbox; isolated durable threads. | A role receives successive turns and survives a restart with an inspectable record. |
| Planning and ratification | Project onboarding and the entity map; manager and inbox; feature intake and planning; debate and ratification. | An owner can hand in a design and ratify a buildable plan using local context. |
| Feature delivery | Sequential implementation; exact-candidate review; serial landing; final review and delivery; trace navigation. | A small feature reaches an owner-approved pull request with a complete trace. |
| Concurrency and recovery | Parallel workstreams, each in its own trace database, and shared capacity; amendments and standing rulings; concurrent landing and drift; archive cleanup; budgets, profiles, pause, reload and recovery. | Several workstreams on one project progress through interruptions, questions and conflicts, and through another workstream's archive cleanup, without lost work, duplicate landings or waiting on another workstream's storage. |
| Phone operation and notifications | Embedded web interface; tailnet access; notifications and the product's installation, release and first-run experience. | The full lifecycle and every owner decision are available from a phone, with local context. |
| Jujutsu workspaces | Jujutsu provider; rebase and interruption recovery. | The complete lifecycle works with either workspace backend. |
| Projects and workgroups | One-repo projects, per-project charters, cross-project workgroups, read-only design intake, briefs, shared manager, workgroup specs and protected slices; merge-only edges, amendments, cancel and two-level retention. | One owner start and ratification cover cross-repo work; each PR has its own delivery approval, and shared context lasts until all members resolve. |
| Project memory through Hearsay | Reconciled decision publishing; scoped memory bundles; ruling reconciliation and watches. | Memory enriches the workflow while outages lose no decisions and local operation remains supported. |
